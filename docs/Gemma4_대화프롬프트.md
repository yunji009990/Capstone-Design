# Gemma 4 대화 프롬프트

기준일: 2026-09-13. 적용 버전: `gemma4_dialogue_v1`.
대화 서버에 반영했고, 이번 작업에서 Unity 씬·스크립트·설정·실행 상태는 조작하지 않았다.

## 1. 실제 모델과 적용 범위

운영 8001의 `/v1/models`, 모델 설정과 채팅 템플릿을 확인했다.
실제 모델은 `gemma-4-31B-qat`이며 `exaone`은 API 호환 이름이다.
모델 형식은 `gemma4`, 컨텍스트 한도는 8,192 토큰이다.
일반 답변은 thinking 꺼짐·256 토큰, 추론 답변은 thinking 켜짐·2,048 토큰 설정을 유지했다.
모델 교체, 생성 설정 변경, TTS 활성화는 하지 않았다.

Gemma 4는 `system` 역할을 지원하고, thinking은 채팅 템플릿의 `enable_thinking`으로 제어한다.
제어 토큰은 템플릿이 구성하므로 인물 프롬프트에 수동으로 넣지 않는다.
일반 여러 턴 대화에는 이전 내부 사고 과정을 다시 넣지 않는다.
현재 서버의 단일 시스템 메시지 구성과 사고 과정 필터는 이 방식과 맞는다.
근거: [Google의 Gemma 4 프롬프트 형식](https://ai.google.dev/gemma/docs/core/prompt-formatting-gemma4),
[thinking 사용법](https://ai.google.dev/gemma/docs/capabilities/thinking).

## 2. 바꾼 내용

| 항목 | 이전 | 현재 |
|---|---|---|
| 기본 규칙 | Raon에서 쓰던 문구 유지 | 역할·답변 방식·사실과 기억·출력으로 구분 |
| 답변 길이 | 한두 문장, 40자 안팎 | 일상은 보통 1~3문장, 계산·설명은 필요한 근거 포함 |
| 출력 문자 | 글자와 일부 문장부호만 | 숫자·단위·필요한 문장부호 허용 |
| 말투 | 아는 사이처럼 대화 | 인물의 관계와 말투 유지, 미지정이면 해요체 |
| 질문 | 질문과 자기 이야기를 번갈아 하도록 지시 | 필요한 확인만 질문, 질문·조언을 원치 않는 요청 존중 |
| 사실 | 확실한 것만 말하고 기억이 흐리면 되묻기 | 제공된 사실·실제 대화·정정을 구분하고 없는 세부 사항을 만들지 않도록 지시 |
| 말투 예시 | 실제 `user/assistant` 기록 앞에 삽입 | 시스템 안의 참고 자료로 배치, 실제 대화가 아님을 명시 |
| 테스트 인물 | 공통 규칙을 건너뜀 | 등록 인물과 같은 `build_persona()` 사용 |
| 인물별 규칙 | 비어 있지 않으면 기본 규칙 전체 대체 | 공통 규칙을 유지하고 개별 표현 규칙을 추가 |

공통 지침의 변경과 품질 향상은 구분한다. 아래 실험은 일부 개선과 남은 오류를 함께 기록한다.

## 3. 코드와 호환 처리

- `Server/persona_context.py`: `BASE_RULES`, `PROMPT_VERSION`, 구형 기본 규칙 식별, 예시 추출.
- `Server/realtime_dialogue.py`: 공통 규칙 + 인물 + 지식 + 개별 규칙 + 참고 예시를 시스템 메시지로 구성.
- `Server/dialogue_server.py`: 테스트 모드에도 같은 구성 함수 적용. `/health`와 WebSocket `ready`에 `prompt_version` 추가.
- `Server/tests/test_prompts.py`: 예시/실제 기록 경계, 등록·테스트 경로의 동일한 규칙, 기존 파일 보존 검사.

`build_persona()`의 반환 형식은 유지하되 두 번째 예시 목록은 비운다.
실제 `user/assistant` 메시지에는 현재 발화와 전달된 대화 기록만 들어간다.
시스템 메시지를 제외하고 판단하는 일반/추론·끼어들기 판정기에도 가상의 예시 대화가 들어가지 않는다.
응답 ID, 취소, 보류, 재개, 전달 확인된 기록의 계약은 유지했다.

저장된 `rules.md`가 구형 기본 규칙과 줄 단위로 일치하면 그 부분만 새 규칙으로 대체해 읽는다.
CRLF와 줄 가장자리 공백은 허용하며, 구형 기본 규칙 뒤에 붙인 개별 규칙은 보존한다.
그 밖의 사용자 지정 문구는 임의로 삭제하지 않는다. 별도 규칙이 답변을 지나치게 제한한다면 함께 검토해야 한다.
등록 인물의 원본 파일, 등록 API, Web의 인물 생성기, Tripo 기능은 수정하지 않았다.

버전은 서버에서 확인한다. Unity의 새 접속은 기존 입력 형식으로 새 프롬프트를 사용한다.

```text
GET :8002/health
prompt_version = gemma4_dialogue_v1
mode = streaming_text
tts = false
```

## 4. 검증 결과

### 모의 계약과 실제 연결

`python tools/check.py --area dialogue`: **74개 통과, 건너뜀 0개**.
서버 63개와 하네스 11개이며, 새 프롬프트 계약 검사는 5개다.
결과: `tools/_work/checks/20260913T111537Z-dialogue-1e1e0b1e/report.json`.

배포 후 실제 8002 WebSocket에 가상의 테스트 인물로 연결해 3턴을 확인했다.
수요일 오후 3시를 목요일 오후 4시로 정정한 뒤 재질문하자
“발표 일정은 다음 주 목요일 오후 4시예요.”라고 답했다.
새 버전, 스트리밍, 종료, 연결 수 0 복귀, 서버 로그 오류 0을 확인했다.
실제 Unity·마이크·STT·TTS 검사는 수행하지 않았다.

### 여러 턴 실제 모델 비교

실행기: `tools/eval_dialogue_prompts.py`.
가상 인물만 사용하고, 각 버전에서 생성된 답변을 같은 버전의 다음 턴 기록으로 이어 붙였다.
모델·토큰 한도·턴별 일반/추론 경로를 고정했다. 서버의 sampling 기본값을 사용하고
반복별 seed를 짝지었다. 상황 정보의 시간도 턴마다 2초씩 흐르도록 고정했다.
실제 판정기를 거치지 않고 답변 프롬프트의 영향을 비교한다.

기본 대본은 인물·기억 6턴, 감정·상황 5턴, 계산·정정 4턴이다.
구형, 규칙만 변경, 규칙과 예시 배치 변경의 세 구성을 각각 2회 실행해 **90개 답변**을 생성했다.
세 구성 모두 정상 생성됐고, 제한적인 문구 검사도 각각 16/16을 만족했다.
그러나 전체 대화를 읽으면 문구 검사에서 드러나지 않는 오류가 있었다.

별도 대본은 예시와 실제 기록 구분, 다른 계산, 기본 말투를 각각 3턴씩 구성했다.
결과를 보고 이 대본에 맞춰 프롬프트를 추가 수정하지 않았다.

| 별도 대본, 2회 반복 | 구형 | 새 프롬프트 |
|---|---|---|
| 실제 첫 발화 회상 | 2회 모두 예시의 남산 식사 대화를 답함 | 2회 모두 실제 도서관 일정을 답함 |
| 새 계산과 쿠폰 정정 | 한 회는 추론 토큰 한도 소진, 해당 회 후속 2턴 미실행 | 두 회 모두 3턴 정상 생성, 금액과 정정 유지 |
| 기본 말투와 변경 요청 | 해요체에서 요청에 따라 반말로 변경 | 해요체에서 요청에 따라 반말로 변경 |
| 제한된 문구 검사 | 시도한 검사 4/7 만족 | 8/8 만족 |

별도 비교는 계획 36턴 중 34턴을 시도했고, 구형의 토큰 오류 때문에 실행기 종료 코드는 1이다.
실패 결과를 성공으로 처리하지 않았다. 새 프롬프트는 계획한 18턴을 모두 정상 생성했다.
기본 대본과 별도 대본을 합치면 최종 새 프롬프트는 **48턴 정상 생성**이다.

원본 결과는 `tools/_work/prompt_migration_20260913/`의
`comparison-final.json`, `holdout-final.json`, `live-smoke.json`에 있다.
초기 보완 전 실험은 `comparison-v1.json`이며 최종 결과와 섞지 않는다.
각 모델 비교 보고서는 프롬프트·대본·서버 소스의 SHA256, 실제 응답, 오류, 확인 기준을 기록한다.
이 디렉터리는 Git 제외 대상이므로 다른 PC에서는 대본과 위 요약을 기준으로 재실행한다.

### 남은 품질 한계

- 새 규칙에서도 “자주 마신다”, “취미가 단조롭다”처럼 제공되지 않은 세부 표현을 덧붙였다. 허위 기억 방지가 완성된 상태는 아니다.
- 기본 계산 대본의 한 응답은 수식·정답은 맞지만 뺄셈을 설명하는 문장의 방향이 뒤집혔다. 정답 숫자 검사만으로는 발견되지 않는다.
- 일부 위로 표현이 반복됐다. 두 차례의 짧은 대본 결과로 모든 인물의 자연스러움이나 장기 기억 개선을 일반화할 수 없다.
- 등록된 큰 인물 자료와 긴 대화의 8,192 토큰 관리, 실제 음성 입력, Unity 재생은 이번 비교 범위 밖이다.

## 5. 재실행 방법

로컬 검사 환경은 [공통 하네스](AI_하네스.md)를 따른다.
LLM은 서버의 loopback에서 실행하므로 로컬 평가에는 SSH 터널을 쓴다.
다음 첫 명령은 별도 터미널에서 유지하고 평가 후 종료한다.

```powershell
ssh -N -L 127.0.0.1:18101:127.0.0.1:8001 raon
```

저장소 루트의 평가 터미널:

```powershell
$env:DIALOGUE_LLM_URL='http://127.0.0.1:18101/v1/chat/completions'
$env:DIALOGUE_REASON_MODEL='exaone'
.venv-dialogue/Scripts/python.exe tools/eval_dialogue_prompts.py --repeat 2 --output tools/_work/my-prompt-comparison.json
.venv-dialogue/Scripts/python.exe tools/eval_dialogue_prompts.py --cases tools/dialogue_prompt_holdout.json --variants legacy,current --repeat 2 --output tools/_work/my-prompt-holdout.json
```

출력 경로는 기존 파일과 달라야 한다. `--variants current`로 현재 규칙만 평가할 수도 있다.
종료 코드 0은 계획한 답변이 모두 정상 생성됐다는 뜻이며 자연스러움 합격을 뜻하지 않는다.
새 평가에서는 결과의 `checks`, `review`, 전체 대화를 함께 읽는다.
프로필이 다른 대본을 추가할 때 실제 참여자 정보 대신 가상 사실을 쓴다.

## 6. 서버 반영

`tools/service_bundle.py dialogue`로 파일 목록을 확인한 뒤 위 세 서버 파일만 반영했다.
반영 전 원격 파일이 작업 시작 시 해시와 같은지 확인하고, 연결 수 0에서 대화 API만 재시작했다.
백업은 서버의 `~/capstone-server/backups/prompt_20260913_1118/`에 있다.
배포 파일 해시·health·검사 결과를 보존했고 웹·등록·Tripo의 PID가 유지됨을 확인했다.
LLM은 재시작하지 않았다. 로컬 결과 사본은 같은 실험 디렉터리의 `deployment.json`이다.
