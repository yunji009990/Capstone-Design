> [테스트 디버그 사용법](테스트_디버그_사용법.md)에 있다. Unity 진단 메뉴로 로컬 보고서를 만들고,

## 지금까지 확인된 것과 아직 아닌 것

### 처음 문제와 지금 상태

**시작할 때 0.6초 무음이 먼저 재생되던 결함은 고쳐졌다.**
예전 `AudioClip.Create(stream:true)` 는 200 ms 만 들어와 있는데 800 ms 를 미리 요청해
600 ms 를 0 으로 채웠다. 클립 없이 필터가 직접 출력을 만드는 방식으로 바꿔 그 선읽기가 사라졌다.

**남은 것은 다른 문제다.** 공급이 실제로 드문드문 들어오거나 늦게 도착하면
렌더러는 아직 오지 않은 PCM 을 만들어 낼 수 없다. 그 구간은 여전히 무음이 된다.
아래 `quiet-gap`·`quiet-stop-restart` 가 그 한계를 잰 회차다.

**모든 검사에서 underrun 이 0 이었다고 말하면 안 된다.** `quiet-gap` 은 600 ms 공급 중단을

전송 지터가 함께 작용한 결과다. 실시간 속도 회차의 underrun 도 전송 지터에서 온다.

`quiet-stop-restart` 의 품질 실패는 **그대로 남겨 둔다.** 뒤이은 `quiet-stop-restart-buffered`
회차는 공급을 넉넉히 해 **Stop 계약만 따로** 확인한 것이고, 앞 회차의 공급 부족 실패를
고치거나 지운 것이 아니다. 실시간에 가까운 드문 공급과 지터는 **잰 한계로 남아 있다.**

일정의 출처가 두 가지로 다르다.

- `fixed-network-*-*` 9회는 **실제로 잡아 둔 도착 일정**을 그대로 다시 재생한 것이다.
- `quiet-fast-v2`·`quiet-pause-resume-buffered`·`quiet-stop-restart-buffered`·`quiet-gap`·
  `quiet-stop-restart` 는 **검사를 위해 일부러 구성한 일정**이다.

두 경우 모두 파형은 합성이며 실제 음성 품질이나 이어폰 청취를 확인한 것이 아니다.

### 조용한 검사가 조용한 이유

진단 설정의 `audible` 은 기본 `false` 다. 이때 출력 탭이 **원본 PCM 을 먼저 재고 나서
출력 버퍼를 0 으로 지운다.** 그래서 보고서의 수치는 지우기 전 값이고 실제로 뒤로 나간 것은
무음이다. 위 조용한 회차 모두 `postPeak=0` 으로 확인됐다.
탭이 없으면 소리를 보내기 전에 검사가 먼저 실패한다.
운영 재생 경로와 전역 볼륨은 건드리지 않는다.

초기 `source.mute` 기반 회차가 실패했던 것은 **계측 쪽 한계**였다(렌더러는 정상,
탭이 0 만 봄). 지금은 탭이 재고 나서 지우는 방식이라 해소됐다. 운영 회귀가 아니었다.

### 실제 Unity 통합 1턴

`unity-live-validation.json`. `AI_Response_Test` 에서 공개 `ko.wav` → STT → LLM →
Qwen TTS → 클라이언트 렌더 → `playback.done` 까지 이어졌다.
(`/health` 의 모델 별칭은 `exaone` 이다. 그 뒤에 실제로 어떤 모델이 올라가 있는지는
이 검사의 범위가 아니므로 여기서 단정하지 않는다.)

- 원본 128,640 샘플, 기록된 underrun·rebuffer **0**
- Unity 와 서버가 같은 `trace`(`78b7f0dfb357`)·같은 `turn`(1)을 남겼고 `connection.close` 는 1회
- 사용자 마이크나 이어폰 청취는 없었다
- 실행 중 음소거 요청이 MCP 오류로 거부돼 **음소거 상태를 확인하지 못했다.**
  그러므로 이 회차를 **조용했다고도, 소리가 났다고도 말하지 않는다.**
  (합성 진단 회차는 위처럼 실제로 억제되고 `postPeak=0` 으로 확인됐다.)
- 이후 Play 는 중지했고 Scene_2 는 원래 상태로 되돌렸다.

**이것은 1턴이다.** 사용자가 처음 겪은 "두 번째 턴부터 안 된다"는 증상은
**아직 확인되지 않았다.** 실제 마이크로 5~10턴을 다시 해 봐야 한다.

## 로그 두 곳

### Unity 클라이언트

체험 한 번에 파일 하나. JSONL 이며 한 줄이 한 사건이다.

- 편집기: `.dialogue-work/logs/dialogue-<UTC>-<trace>.jsonl` (프로젝트 루트 기준, Git 제외)
- 기기: `Application.persistentDataPath/dialogue-logs/`
- 파일당 2 MB, 최근 8개 보관. 넘으면 그 파일은 더 쓰지 않는다.
- 저장에 실패하면 **로거만 스스로 꺼지고 대화는 계속된다.** 이때 `TraceLogAvailable=false` 다.

남는 값: UTC 시각, 단조 ms, 가명 `trace`, 사건 이름, 원인 코드, 숫자.
사건은 `experience.start/end`, `dialogue.fail`, `main_thread.stall`, `audio.config_changed`,
`response.started/done/cancelled/paused/resumed`, `playback.sample`(2초 주기)다.
숫자는 received/consumed/buffered/rendered/ended/underrun_frames/rebuffers/callbacks/
audio_packets/resp_packets/resp_audio_span/max_packet_gap/paused_gap/max_frame_stall/
cfg_changes/paused/listening/dsp_rate/dsp_buffer/dsp_buffers/turn 이다.

### 대화 서버

코드 기본값은 비어 있어 꺼짐이지만, **운영 서버에는 2026-09-16 배포 때 이미 켜 두었다.**
다시 설정하거나 API 를 재시작할 필요가 없다. 새 서버에 올릴 때는 `dialogue.env` 에 넣는다.

```
DIALOGUE_DIAGNOSTICS_LOG=/home/crc_unity/capstone-server/logs/dialogue-diagnostics.log
```

`~` 는 셸이 확장하지만 `.env` 파일 값은 확장되지 않는 경우가 있으므로 **절대 경로로 적는다**
(서버 계정이 `crc_unity` 가 아니면 그 계정의 홈으로 바꾼다). 서버 코드는 `~` 를 만나면
`expanduser` 로 풀지만, 셸에서 `export` 할 때는 따옴표 없이 써야 확장된다.

```bash
export DIALOGUE_DIAGNOSTICS_LOG=~/capstone-server/logs/dialogue-diagnostics.log   # 확장됨
export DIALOGUE_DIAGNOSTICS_LOG="$HOME/capstone-server/logs/dialogue-diagnostics.log"  # 확장됨
export DIALOGUE_DIAGNOSTICS_LOG='~/capstone-server/logs/...'                      # 확장 안 됨
```

- 파일당 2 MB, 백업 5개(`RotatingFileHandler`).
- 전역 로깅 설정을 건드리지 않는다. `dialogue.diagnostics` 로거에만 붙고 `propagate=False` 다.
- **경로·권한 오류는 서비스를 막지 않는다.** 진단만 꺼지고 대화 API 는 그대로 뜬다.
- 실제로 켜졌는지는 `/health` 의 `diagnostics.file` 로 본다. **설정 문자열이 있다는 뜻이 아니라
  파일 핸들러가 실제로 붙었다는 뜻이다.**

사건: `connection.open/close`(사유 + `code`), `heartbeat`, `input.candidate`(started/closed/accepted),
`input.verified`(`asr_ms` + 입력 품질 집계),
`input.rejected`(no_speech/no_text/weak_text/verify_failed/dropped/too_long),
`turn.started`(route), `turn.done`, `turn.cancelled`, `turn.held`, `turn.resumed`.
집계: audio_chunks, vad_start/end/too_long, max_input_gap_ms, asr_calls/avg/max,
resp_packets/resp_samples/resp_span_s/resp_max_gap_ms, answer_audio_sec, weak_text 등.

`input.verified`·`input.rejected` 양쪽에 같은 모양으로 붙는 `no_speech_pct`·
`avg_logprob_x100`·`compression_x100`·`text_segments`·`weak_segments`의 뜻과 읽는 법은
[말버릇·잡음 응답 개선](말버릇_잡음_응답_개선.md)의 「로그에서 확인하는 법」에 있다.

### 남지 않는 것

사용자 발화·모델 답변 원문, 모델이 만든 자유 문장, 실제 세션 ID, 등록 인물 정보,
토큰·URL·파일 경로, PCM, 환경변수, 오디오 장치 이름.

현재(Unity `v=2`, 서버 `dialogue_diag_v4`)는 양쪽 모두 **화이트리스트 대조**를 한다.

- **Unity**: 사건·원인·수치 이름을 `DialogueTraceLog` 의 `Events`/`Reasons`/`Names` 목록과
  대조한다. 목록에 없는 사건·원인은 `other` 로 접고, 모르는 수치 이름은 값을 버린 뒤
  버린 개수(`unknown_names`)만 센다.
- **서버**: 같은 방식으로 **사건·원인 화이트리스트**에 대조해 목록에 없으면 `other` 로 접는다.
  덧붙는 숫자 항목의 이름도 미리 정해진 것만 받는다.

어느 쪽도 예외 메시지를 파일에 넣지 않는다.

> Unity `v=1` 때는 목록 대조 없이 **허용 문자**(`[A-Za-z0-9_.-]`, 콜론 없음)만 남기는 정제였다.
> 그래서 영어·숫자로만 된 서버 문자열이 그대로 통과할 수 있었다(예: `response.started` 의
> `reason` 은 서버가 준 route 문자열이었다). 위 설명은 v2 기준이고, 이 문단은 v1 로그를
> 읽을 때만 해당한다.

## 같은 trace 로 양쪽을 맞추기

Unity 가 연결할 때 12자리 16진수 `trace_id` 를 만들어 `start` 에 실어 보내고,
서버는 그 형식일 때만 그대로 쓴다(아니면 서버가 새로 만든다).
**실제 세션 ID 가 아니다.** 양쪽 로그에서 같은 `trace=` 와 같은 `turn=` 을 찾아 붙여 읽는다.

끊김이 어디서 생겼는지는 대체로 이렇게 좁혀 간다.
**한 줄만 보고 단정하지 말고 앞뒤 줄과 함께 읽는다.**

| 관찰 | 좁혀지는 범위 | 함께 볼 것 |
|---|---|---|
| 서버에 `turn.started` 가 있는데 Unity 에 `response.started` 가 없다 | 전송·연결 구간일 수 있다 | 같은 `trace`·`turn`, `connection.close` 사유 |
| 양쪽 다 있는데 Unity `max_packet_gap` 이 크다 | 도착 간격(네트워크·TTS 생성) | 서버의 `resp_max_gap_ms`. 두 값이 함께 크면 보내는 쪽 |
| 도착은 촘촘한데 `rebuffers`/`underrun_frames` 가 는다 | 재생·메인스레드 구간 | `max_frame_stall`, `buffered` |
| `max_frame_stall` 이 크다 | Unity 프레임 지연 | 같은 시각의 `underrun_frames` |
| `ended=0` | **그 자체로는 결함이 아니다.** 선버퍼 대기, 일시정지, 공급 부족, 아직 진행 중인 답변 모두 `ended=0` 이다 | `response.started`/`response.done` 위치, `paused`, `buffered`, `received`−`consumed` |
| 서버 `vad_start` 가 늘지 않는다 | **마이크 고장의 증거가 아니다.** 조용했으면 당연히 늘지 않는다 | 같은 구간의 `audio_chunks`. 그것도 멈췄는지 본다 |
| `vad_start` 는 느는데 `accepted` 가 없다 | 입력 검증에서 거절됐다 | 같은 줄의 `reason`(`no_speech`/`no_text`/`weak_text`/…) |
| `reason=weak_text` 가 반복된다 | 전사는 나왔지만 Whisper 지표가 비음성을 가리켰다 | 같은 줄의 `no_speech_pct`·`avg_logprob_x100`, 정상 입력의 `input.verified` 분포 |
| `heartbeat` 는 오는데 `audio_chunks` 가 멈췄다 | 연결은 살아 있고 **입력이 멈췄거나 막혔다** | Unity 의 `listening`, `dialogue.fail` 사유. 파일 주입 검사 모드에서는 원래 마이크를 열지 않으므로 정상이다 |

Unity 의 종료 원인 코드도 구분해서 읽는다. `ui_finish…` 는 UI 단추 또는 코드가 부른
`Finish` 경로, `control_disabled` 는 컴포넌트가 꺼진 경우, `fail_…` 는 실제 실패다.
`ui_finish_space`·`ui_finish_enter` 의 접미사는 **Toggle 시점에 그 키가 눌려 있었다는 관측**일
뿐이며, 그 키가 종료를 일으켰다는 증거는 아니다.

## 다시 시험할 때

서버 진단은 이미 켜져 있고 Scene_2 도 원래 상태로 돌아가 있다.
서비스를 다시 시작하거나 설정을 바꿀 일이 없다.

1. **Scene_2 에서 Play** 를 누른다.
2. 등록된 인물로 **체험 시작** 을 누른다.
3. **5~10턴** 이어서 말한다. 짧은 답(`네`, `응`), 긴 문장, 끼어들기를 섞는다.
   잡음 구간(의자·종이 소리, 주변 대화)도 넣어 본다.
   **키보드 Space·Enter 는 누르지 않는다.** 시작 단추에 초점이 있으면 그 키가
   단추를 눌러 체험이 끝날 수 있다(입력 설정은 그대로 두었다).
4. 증상이 나면 **Play 를 그대로 켜 둔 채** 몇 시 몇 분, 몇 번째 턴인지만 알려 준다.

무슨 말을 했는지 적을 필요도, 로그를 넘길 필요도 없다.
메인이 편집기 폴더와 서버 로그를 직접 읽고 `trace` 와 `turn` 으로 붙여 위 표대로 범위를 좁힌다.
Unity Console 에는 `[Dialogue] 체험 종료 reason=… trace=… log=…` 한 줄이 남는다.

Console 에 보이는 MCP client-handler 예외는 도구 쪽에서 관찰된 오류이며 이 작업 전부터 있었다.
제품 C# 컴파일 오류는 관찰되지 않았고, 그 예외가 사용자 증상을 일으켰다는 근거도 아직 없다.
무관하다고 단정하지는 않는다.

## 개발용 검사 메뉴

Unity 편집기 메뉴 두 개가 있다. 둘 다 씬·서버·마이크·등록 인물을 건드리지 않고
자기 오브젝트만 만들었다 지운다.

| 메뉴 | 용도 |
|---|---|
| `Tools/Dialogue/Run resampler core check` | 리샘플 코어를 결정적으로 검증 |
| `Tools/Dialogue/Run playback buffer diagnostic` | 실제 오디오 콜백에서 재생을 계측 |
| `Tools/Dialogue/Run speech tail output check` | 주어진 WAV 와 Unity 출력 파형을 대조 |
| `Tools/Dialogue/Compare last reply/…` | 방금 들은 답변의 **수신 PCM** 을 두 경로로 다시 듣기 |

설정은 `.dialogue-work/playback-diagnostic-config.json`, 결과는
`tools/_work/audio_incident_20260916/` 아래에 쌓인다(Git 제외).
보고서의 `passed` 는 실행이 끝났다는 뜻이고 품질은 `qualityPassed` 로 따로 본다.
`audible` 기본값 `false` 에서는 탭이 재고 나서 출력을 지우므로 소리가 나지 않는다
(`postPeak=0` 으로 확인). 탭이 없으면 소리를 내기 전에 검사가 먼저 실패한다.
앞의 두 메뉴는 합성 파형이며 **사람이 들어 확인한 결과가 아니다.**

### 같은 답변 다시 듣기 (비교 재생)

`Tools/Dialogue/Compare last reply/Stream renderer` 와 `.../AudioClip` 은 **방금 끝까지 재생된
답변의 수신 PCM** 을 각각 실제 대화와 같은 스트리밍 경로와 클립 경로로 다시 들려준다.
같은 문장을 다시 합성하면 음성이 달라질 수 있어 이 대조가 필요하다.
자세한 사용법은 [말끝 오디오 진단](말끝_오디오_진단.md)의 「같은 답변 다시 듣기」에 있다.

- 순서: 문제 답변을 **끝까지 듣기** → **체험 종료**(Play 는 켜 둔 채, **`대화 초기화`는 누르지
  않는다**) → 두 메뉴를 **각각 수동으로** 고르기 → Console 의 `turn=`·`gen=` 이 같은지 확인.
  종료 뒤 연결 정리에 잠시 걸릴 수 있어 거절당하면 몇 초 기다렸다 다시 고른다.
- 두 경로 모두 잘려 들리면 수신 PCM·공유 출력 단·장치를, 한쪽만 다르면 그 경로와 그때의 조건을
  조사한다. **원인 확정이 아니다.** 일정한 간격으로 공급하므로 **원래 도착 시간을 재현하지 않는다.**
- 보관은 메모리뿐이다. 최대 60초 완료본 1개, 완료 후 10분(에디터 시간) TTL, 새 응답·새 체험·
  대화 초기화·등록 인물 변경·비활성·Play 종료에 지운다. **끝까지 재생된 답변만** 남으므로
  중간에 끊긴 답변은 다시 들을 수 없다.
- 원문·PCM·세션·토큰을 파일이나 Console 에 쓰지 않는다. 기본값에서 **자동으로 소리가 나지 않는다.**
- Editor 전용이며 서버·모델·응답 속도·제품 재생 계약은 바뀌지 않았다.

## 말끝 오디오 조사 (2026-09-16)

"문장 끝 음절이 소리에서 빠진다"는 별도 보고는 [말끝 오디오 진단](말끝_오디오_진단.md)에서 다룬다.
그 조사에서 이 문서의 계측 체계를 그대로 썼고, 결과는 아래와 같다.

- 엔진 출력(공개 참조 18회), 엔진 SSE 수신 파서(3문장, 5가지 chunk 경계 재생),
  Unity 출력(공개 합성 WAV 9개)에서 **표본 손실이 나오지 않았다.** 세 검사는 서로 다른 회차이며
  개수를 합산하지 않는다.
- Unity 출력 검사는 새 메뉴 `Tools/Dialogue/Run speech tail output check` 로 돈다.
  이 문서의 두 메뉴와 마찬가지로 씬·서버·마이크·등록 인물을 쓰지 않고, 기본값에서는
  탭이 파형을 잰 뒤 출력을 0 으로 지워 **소리가 나지 않는다.**
- **원인은 확정되지 않았다.** 사용자가 들은 증상은 아직 재현되지 않았고,
  실제 이어폰 청취·출력 장치 지연은 검증하지 않았다.
- Scene_2 실제 클라이언트에 공개 WAV를 주입한 별도 검사 **35/35 통과**:
  수신=소비 30,720표본, underrun 0, 종료·캐시 바이트 일치·캐시 삭제 조건과 이동 버튼 동작 확인.
  `replay-integration.json`이며 실제 서버·마이크·청취 판정을 대신하지 않는다.
- 같은 회차의 수신 PCM 을 다시 듣기 위해 `Tools/Dialogue/Compare last reply/…` 를 추가했다
  (위 「같은 답변 다시 듣기」). `DialogueVoiceClient` 에는 Editor 전용 연결점만 붙였다.
- 서버·생성 설정·재생 계약은 바꾸지 않았다. 추가된 것은 진단 도구뿐이다.

## 제한

- 이 기록은 원인을 가르는 자료이지 원인 판정이 아니다.
- **공급이 드문드문 들어오거나 늦으면 무음이 남는다.** 렌더러는 아직 도착하지 않은 PCM 을
  만들어 낼 수 없다. `quiet-gap`·`quiet-stop-restart` 가 그 한계를 잰 회차이며 해결된 것이 아니다.
- 실제 음성 통합은 **1턴만** 확인했다. 두 번째 턴 이후의 원래 증상은 아직 재현·확인되지 않았다.
- 실제 마이크·이어폰 청취·스피커 반향(AEC 없음)·Quest 기기는 아직 검증하지 않았다.
- 통합 1턴 회차는 음소거 상태를 확인하지 못했다. 조용했다고도 소리가 났다고도 말할 수 없다.
- 서버 진단은 운영 서버에 켜져 있다. 다른 서버나 새로 올린 인스턴스에서는 따로 켜야 한다.
- Unity 로그는 저장 권한이 없으면 조용히 꺼진다. `TraceLogAvailable` 로 확인한다.
