# 실시간 텍스트 대화 — 1차 구현

> 2026-09-10 보관 기록: Raon은 제거했고 음성 출력은 Qwen3-TTS로 전환했다. 아래는 이전 단계의 조사·구현 이력이다. 현재 운영은 [서버 음성 대화 구조](서버_음성대화_구조.md)를 참고한다.

2026-09-10. Unity → 연속 음성 → STT → LLM → 텍스트 스트리밍.
TTS는 호출하거나 로딩하지 않는다. 기존 음성 서버와 별도 프로세스로 실행한다.

## 현재 상태

- 서버와 Unity 클라이언트 작성, Python 동작 검사 및 Unity 컴파일 확인.
- Unity의 실제 `DialogueTransport`에서 공개 한국어 WAV를 전송하고,
  SenseVoice와 서버의 Gemma를 거쳐 텍스트가 스트리밍되는 것을 확인했다.
- Unity 행동 정보가 LLM 입력에 포함되고, 늦게 도착한 이전 응답이 표시되지 않는 것을 확인했다.
- 별도 대화 서버를 `~/dialogue-server`에 배포하고 8002 포트로 실행했다.
  기존 Raon 8000과 vLLM 8001은 기존 프로세스를 그대로 사용한다.
- 등록 없는 테스트 프로필, 직접 텍스트 입력, 기록 초기화를 포함한 Python 검사
  20개가 로컬 Python 3.9와 서버 Python 3.12에서 통과했다.
- [AI 응답 테스트 씬](AI_응답_테스트_씬.md)에서 등록 절차 없이 마이크·텍스트 입력을 시험할 수 있다.
- 헤드셋 마이크로 체험 버튼을 누르는 실사용 검증은 남아 있다.

## 동작

1. `ExperienceControl.Begin()`이 `RaonVoiceClient.BeginExperience()`를 호출한다.
   마이크와 WebSocket은 체험 시작 때 열고, 종료·앱 일시정지·인물 변경 때 닫는다.
2. Unity는 무음을 포함해 16 kHz, mono, PCM16 little endian 음성을 80 ms씩 전송한다.
   서버의 STT나 LLM이 실행 중이어도 전송한다.
3. 서버의 WebRTC VAD가 20 ms 프레임으로 시작과 끝을 판단한다. 최근 10프레임 중
   8프레임의 음성을 시작 조건으로 쓰고, 기본 700 ms 무음을 종료 조건으로 쓴다.
   시작 전 300 ms와 끝부분 200 ms를 인식에 남긴다.
4. SenseVoiceSmall INT8를 sherpa-onnx CPU 실행기로 호출한다. 말하는 중 약 1.5초마다
   누적 구간을 다시 인식해 임시 자막을 보내고, 발화 끝에서 최종 인식을 한다.
   **네이티브 스트리밍 ASR이 아니라 구간을 나누어 호출하는 방식이다.**
5. 최종 인식 결과에 등록된 인물·사전지식·대화 예시·최근 대화·Unity 관찰·음성 태그를
   합친다. 관찰 정보에 모델이 주지 않는 값을 지어내지 않는다.
6. 추론 모델이 설정되어 있으면 일반 모델에 `normal`/`reasoning`을 분류하게 한다.
   분류 실패는 알리고 일반 모델로 진행한다. 추론 모델 자체의 실패는 오류로 전달한다.
7. 최종 답변 텍스트만 조각별로 보낸다. `reasoning_content`와 `reasoning`은 전달하지
   않고, `<think>` 및 Gemma의 thought channel이 content에 포함될 때도 제거한다.
8. 새 발화가 감지되면 진행 중인 STT 대기·분류·LLM HTTP 스트림을 취소한다.
   실제 CPU 추론 하나는 끝날 수 있지만 결과를 버리며, 같은 인식기에 추론을 겹쳐 실행하지 않는다.
   Unity는 이전 응답 식별자의 조각을 무시한다.

한 번의 체험은 하나의 연결과 대화 기록을 갖는다. 연결이 끊기면 체험을 종료하고,
다시 시작하면 새 기록으로 시작한다. 등록된 인물 자료를 삭제하는 `/session/end`는 호출하지 않는다.

## 서버 준비

기존 Raon/vLLM 환경과 분리된 Python 환경을 사용한다. 새 서버 코드는 예를 들어
`~/dialogue-server`에 두고, 기존 등록 자료 `~/server/sessions`는 읽기만 한다.

```bash
python3 -m venv "$HOME/venv/dialogue"
"$HOME/venv/dialogue/bin/python" -m pip install -r "$HOME/dialogue-server/requirements-dialogue.txt"
"$HOME/venv/dialogue/bin/python" "$HOME/dialogue-server/setup_dialogue_models.py"
```

`dialogue.env.example`을 `dialogue.env`로 복사하고 `DIALOGUE_TOKEN`을 Unity의 Token과
맞춘다. 모델·키·등록 자료는 저장소에 넣지 않는다. 모델 다운로드 경로는
`~/dialogue-models/sensevoice`이며 기존 `~/models`를 수정하지 않는다.

```bash
bash "$HOME/dialogue-server/dialogue_start.sh"
curl http://127.0.0.1:8002/health
```

`status=ready`, `llm_ready=true`를 확인한다. 기본 주소는 8002 포트이며 기존 8000/8001
서비스를 재시작할 필요는 없다. 한 번에 한 연결이 기본이다.

| 설정 | 기본 또는 예시 |
|---|---|
| `DIALOGUE_TOKEN` | Unity와 같은 인증 토큰. 외부 접속을 허용할 때 필수 |
| `DIALOGUE_SESSIONS_DIR` | `~/server/sessions` |
| `DIALOGUE_MODEL_DIR` | `~/dialogue-models/sensevoice` |
| `DIALOGUE_LLM_URL` | `http://127.0.0.1:8001/v1/chat/completions` |
| `DIALOGUE_LLM_MODEL` | `exaone` — 현재 실제 모델은 Gemma 4 31B QAT |
| `DIALOGUE_REASON_URL`, `DIALOGUE_REASON_MODEL` | 별도 추론 모델의 주소·이름 |
| `DIALOGUE_LLM_EXTRA`, `DIALOGUE_REASON_EXTRA` | 모델별 채팅 템플릿·추론 설정 JSON |
| `DIALOGUE_REASON_TOKENS` | 2048. 일반 답변의 256과 별도 |
| `DIALOGUE_SILENCE_MS` | 700 |
| `DIALOGUE_MAX_CONNECTIONS` | 1 |
| `DIALOGUE_ALLOW_TEST_MODE` | 코드 기본값 0, 예시 및 테스트 서버는 1 |

예시 환경 파일은 **같은 Gemma의 추론 모드**를 사용한다. 별도 모델로 교체하려면
추론 주소와 이름을 바꾼다. `DIALOGUE_REASON_MODEL`이 비어 있으면 일반 모델만 사용한다.
실제 Gemma에서 일반/추론 분류와 각 모드의 답변 생성이 동작함을 확인했다.

## Unity 연결

`RaonVoiceClient`의 `Use Realtime Text`가 새 경로를 선택한다. 새 필드의 기본값은 켜짐이다.
기존 `Server Url`은 등록 세션·3D 모델 조회에 쓰고, `Dialogue Server Url`은 비워두면
같은 호스트의 8002 포트를 사용한다. 서버 준비와 인물 등록이 모두 확인되어야 체험을 시작한다.

인식 문장은 중간 자막으로, 답변은 생성 중인 기록으로 표시된다. 완료 시 기록을 한 번만 확정하고,
중단된 답변은 받은 부분에 `(중단)`을 표시한다. 자막을 숨겨도 STT는 계속 수행한다.

장면 이름은 자동 전송한다. 의미 있는 물건에는 `DialogueContextObject`를 붙이고
`Display Name`을 `가족 사진`, `찻잔`처럼 지정한다. 같은 오브젝트에 Meta `Grabbable`이 있으면
집기·놓기를 자동 전달한다. Collider가 있으면 머리 정면의 대상과 거리도 전달한다.
이는 시선 추적 센서의 측정값이 아니다. 다른 동작은 `ReportUnityAction(string)`이나
`ReportUnityState(string)`을 기존 UnityEvent에 연결할 수 있다.

## 프로토콜과 TTS 연결 지점

WebSocket `/dialogue`에 `X-Token` 헤더를 설정하고 첫 메시지로 다음 JSON을 보낸다.

```json
{"type":"start","protocol":1,"session":"등록된 세션 ID","sample_rate":16000,"channels":1,"format":"pcm_s16le"}
```

`ready` 이후 바이너리 PCM과 JSON 제어 메시지를 같은 연결로 보낸다.

| 방향 | 메시지 |
|---|---|
| Unity → 서버 | 바이너리 PCM, `context` (`kind: state/action`, `text`), `cancel`, `reset`, `stop`, `ping` |
| 서버 → Unity | `ready`, `speech.started/stopped`, `transcript.partial/final` |
| 서버 → Unity | `response.started/delta/done/cancelled/skipped`, `routing.fallback`, `error` |

응답은 `turn_id`와 `response_id`로 구분한다. `response.delta.text`는 새 텍스트 조각이고,
`response.done.text`는 완성된 답변이다. `response.started.speech_style`은 별도 발화 스타일
필드이며 현재 기본값은 `tone: natural`이다. 이후 TTS는 이 텍스트·스타일을 받고,
같은 `response_id`의 취소를 따르도록 연결하면 된다.

## 검증과 남은 한계

```powershell
.\.venv-dialogue\Scripts\python.exe -m unittest discover -s Server/tests -v
```

검사는 무음·짧은 잡음·문장 중 쉼, 구간 상한, 인증·형식·중복 접속, 상황 만료,
STT 중 끼어들기, LLM 중 끼어들기, 연결 종료 후 결과 폐기, 잘린 HTTP 스트림,
추론 문자열 제거와 실제 WebSocket 경로를 포함한다.

Unity의 `Tools/Dialogue/Run loopback integration check`는 로컬 18002 포트의 테스트 서버와
`.dialogue-work/models/sensevoice/test_wavs/ko.wav`를 사용한다. 등록 ID는 `smoke`,
테스트 토큰은 `local-test`이며 이 서버는 반드시 localhost에만 바인딩한다.
검사 결과는 `.dialogue-work/unity-smoke.json`에 쓴다. 실제 검사에서 한국어 입력과
답변 조각 18개가 왕복했고 이전 응답 무시 검사도 통과했다. 이는 마이크 하드웨어 검사는 아니다.

- 답변 시점은 현재 VAD의 무음 기준이다. 문장 의미를 이용하는 차례 종료 모델은 아직 없다.
- 한국어 STT의 정확도는 대상 사용자의 실제 녹음으로 별도 평가해야 한다.
- 30초를 넘는 연속 발화는 잘린 문장에 답하지 않고 오류를 알린 뒤 무음을 기다린다.
- 최근 기록의 상한은 30턴이며, 별도 요약·영속 저장·연결 복구 후 기록 복원은 하지 않는다.
- TTS·재생 큐·AEC는 이번 단계에 포함되지 않는다. 음성 출력 도입 시에는 실제 재생한
  범위와 취소를 연결하고, 헤드셋의 재생음 재유입을 검사해야 한다.
