# Tripo 담당자와 AI를 위한 작업 지시서

기준일: 2026-09-29. 프로젝트: **다시, 봄 / Capstone-Design**. Unity 2022.3.62f2.
이 문서는 팀원이 자기 PC의 AI 코딩 도구에 전달하는 구현 지시서다. 대화 기록 없이 읽을 수 있도록 작성했다.
현재 실행 방법은 [개발환경 실행 가이드](Tripo_개발환경_실행가이드.md)에 있다.
현재 구현은 [머리 생성 파이프라인](Tripo_머리_생성_파이프라인.md), 서버·검사 범위는 [현재 구현 현황](현재_구현_현황.md)을 따른다.

## 1. 맡은 일과 최종 결과

팀원의 현재 제작 경로는 **사진 → 얼굴·머리카락·목 추출 → Tripo 머리 생성 → 고정 몸체 결합 → Unity 검사**다.
대화 AI 담당자는 `AI_Response_Test`에서 마이크·STT·LLM·응답 처리를 별도로 개발한다.
당분간 `Scene_1`, `Scene_2`의 체험 기능은 작업 대상에서 제외한다.

현재 운영 진입점은 설문·참조 음성·선택 사진을 받는 **등록 웹**이다. 사진만 받는 독립 제작 화면은 아직 없다.
머리 경로의 생성·결합 코드는 배포됐지만 신규 등록부터 완성·체험까지 실측과 품질 검수가 남았다.
전신·T포즈·9개 동작 실험은 유지한다. 6~7장의 독립 제작 웹·API는 이전 확장 설계이며,
현재 구현됐다고 설명하거나 사용자 지시 없이 새 우선 작업으로 삼지 않는다.

## 2. 먼저 확보할 기준 코드

9월 29일 기준 `hj`의 `e476eac3`까지 `jw`의 `135fd4da`로 병합됐다. 새 작업은 실제 원격·브랜치를 확인한다.
머리 기능은 최신 Git clone을 기준으로 준비한다. 기존 `tripo_handoff.py`의 파일 선택에는
`Survey/blender/`, `tools/head_*`, 새 머리 문서·몸체 자산 일부가 포함되지 않으므로 ZIP만으로 준비 완료라고 판단하지 않는다.

기존 ZIP 인계 방식을 사용할 때의 기준 Git 커밋은 `manifest.json`에 있는 `base_commit`이다.
이전 인계의 `ba1504a`를 새 묶음에도 고정해서 사용하지 않는다. 묶음을 만든 시점의 미커밋 변경도 포함될 수 있으므로
해당 커밋의 새 clone에 ZIP을 적용한다. `START_HERE.md`의 적용 절차와 파일 해시를 확인한다.
묶음의 대화 코드도 컴파일 의존성을 재현하는 기준 자료다. 이것이 대화 기능 수정 권한을 뜻하지는 않는다.

각 담당자는 자기 clone과 작업 브랜치를 사용한다. 다른 사람의 Unity가 열고 있는 폴더를 같이 편집하지 않는다.
인수인계 기준 적용과 새 기능 변경을 별도 커밋으로 구분하면 통합 시 변경 범위를 확인하기 쉽다.
`.meta` GUID는 보존한다. Unity 패키지 갱신이나 대규모 폴더 이동을 이 작업에 섞지 않는다.
공통 규칙은 [AGENTS.md](../AGENTS.md), 검사 실행 방법은 [AI 하네스](AI_하네스.md)를 따른다.
기본 대화 AI 작업선과 별개로, 이 문서를 명시적으로 받은 팀원 세션은 아래 Tripo 담당 범위에서 작업한다.
팀원 AI의 도구·읽기·쓰기 가능 여부는 실제 실행 환경으로 확인한다.

서버가 같아도 개발 폴더·포트·데이터·가상환경을 별도로 둔다. 실행 가이드의 개발용 18500/18000 예시를 따른다.
운영 폴더에서 실험 worker를 하나 더 실행하면 운영 작업을 가져갈 수 있으므로, 개발 DB와 `.env`부터 분리한다.
운영 대화는 `DIALOGUE_TTS_URL=http://127.0.0.1:8003`을 사용한다. 제작 작업에서 이를 비우거나
대화·LLM·TTS 프로세스를 재시작하지 않는다. Tripo 작업자에 대화용 GPU 패키지를 설치할 필요가 없다.
Tripo 생성은 외부 서비스가 계산한다. head 작업자는 CPU 전처리와 Blender 정리·결합도 담당한다.
Tripo 리깅·동작 요청은 full 경로에만 남아 있다.

## 6. 현재 확인 순서와 이전 확장 설계

현재 head 경로는 다음 순서로 확인한다.

1. 키 설정 여부, 작업자 online, 몸체 GLB·Blender·분할/얼굴 모델과 실제 선택 경로를 확인한다.
2. 격리된 입력으로 전처리에서 얼굴·머리카락을 보존하고 옷·어깨를 제거하는지 본다.
3. 승인된 실제 생성 범위에서 머리 생성·정리·몸체 결합·등록 전달까지 기록한다.
4. Unity에서 목 위치·피부색·머리 방향·크기·본 연결과 기존 몸체 클립을 검수한다.
5. 실패·재시작·전달 재시도에서 유료 제출을 중복하지 않는지 확인한다.

아래 A~D는 **9월 15일 독립 제작 웹·전신 동작 팩 확장 설계**다. 아직 구현되지 않은 계약을 포함하며
현재 head 운영 경로의 완료 조건과 구별한다.

### 단계 A — 사진만으로 독립 제작

현재 `/publish_direct`는 음성·인물 등록을 포함한다(`/publish`는 삭제됨). 독립 제작 화면을 구현할 경우 별도 진입점을 둔다.
기존 웹 안에 `/tripo` 제작 화면을 추가하고, 라우터·처리 코드는 전용 모듈로 둔다.
예시 위치는 `Web/tripo_studio/`, `Survey/tripo_studio/`이며 현재 없는 폴더는 이 단계에서 만든다.
`Web/app.py`에는 라우터 연결만 최소로 추가한다.

- 사진을 업로드하면 독립적인 `job_id`가 생긴다. 원본, 입력 해시, 생성 설정과 생성 시각을 기록한다.
- 기존 `session_id`나 전역 `current.json`을 제작 작업 식별자로 쓰지 않는다.
- 원본 사진과 T포즈 이미지는 서로 다른 파일로 저장한다. 재작업은 이전 성공 결과를 덮어쓰지 않는다.
- 기존 관리자 인증을 재사용하거나 같은 인증 경계에 제작 API를 둔다. 운영 비밀번호를 코드에 넣지 않는다.
- 완료 기준: 음성·설문·등록 서버 없이 사진 업로드·작업 목록·상세·상태 조회가 동작한다.

### 단계 B — T포즈 준비와 확인

T포즈 변환은 2026-09-14 Tripo API 의 `generate_image`(`t_pose: true`)로 연결했다
(`Survey/core/tripo.py` 의 `submit_tpose_image`). 별도 공급자·키는 필요 없고 같은 Tripo 크레딧을 쓴다.
실험 도구는 `--tpose`, 작업자의 full 경로는 `TRIPO_TPOSE=1`로 같은 단계를 거친다. head에는 적용되지 않는다.
검증 결과와 명령은 [T포즈 전처리 실험](Tripo_T포즈_전처리_실험.md)의 2026-09-14 절에 있다.
다른 공급자로 바꾸려면 `submit_tpose_image` 와 `image_url` 만 교체하고 파일·해시 기록 계약은 유지한다.
준비된 T포즈 이미지를 직접 쓰려면 `TRIPO_TPOSE=0` 으로 끄고 그 이미지를 원본 자리에 넣는다.

- 정면 전신, 수평으로 뻗은 양팔, 팔과 몸통의 분리, 손끝·발끝 포함, 다리 사이 간격, 단순 배경을 요청한다.
- 얼굴·나이·머리·복장 특징을 유지하도록 요청하되 실제 결과의 인물 유사도도 확인한다.
- 원본과 전처리 결과를 웹에서 나란히 보고, 재시도 또는 결과 선택이 가능해야 한다.
- 3D 생성은 선택한 T포즈 이미지의 해시와 설정으로 명시적으로 시작한다.
- 완료 기준: 키 없이 수동 T포즈 업로드로 다음 단계까지 개발할 수 있고, 자동 편집과 수동 업로드가 같은 계약을 쓴다.

### 단계 C — 생성·리깅·9개 동작

`tools/tripo_trial.py`의 검증된 요청 설정과 `tools/tripo_motion_pack.py`의 팩 구성을 재사용한다.
실험의 출발점은 v3.1-20260211, 목표 50,000면, PBR·텍스처 사용, detailed 텍스처,
original_image 정렬, 이미지 자동 보정 끔, 리깅 v1.0-20240301, spec=tripo다.
정확한 요청 필드·시드는 `tripo_trial.py`의 `config`와 `identity`를 읽는다. 최신 기본값으로 조용히 바꾸지 않는다.

동작은 **앉기, 주변 둘러보기, 인사, 작별인사, 동의, 박수, 포옹, 웃기, 흐느끼기** 9개다.
Tripo 프리셋 ID는 `tripo_motion_pack.py`의 `MOTIONS`와 T포즈 실험 문서에 있다.

- 3D 생성 → 리깅 가능 검사 → 리깅 → 동작별 처리 → 팩 구성 순서를 저장한다.
- 같은 리깅을 재사용하며, 동작 하나의 실패 때문에 모델·리깅을 다시 생성하지 않는다.
- 유료 제출 전 의도를 저장하고 응답 후 task ID를 저장한다. ID를 받기 전에 연결이 끊기면 `submission_unknown`으로 남긴다.
- 이 복구 규칙은 `Survey/core/model_pipeline.py`와 `tripo_motion_pack.py`에 구현되어 있다.
  오래된 `tripo_trial.py`의 최초 모델 제출은 응답 후 기록하므로, 이를 서비스에 그대로 복사하지 않는다.
- 다른 리깅의 클립을 섞지 않는다. `merge_pack()`의 노드·관절·바인드 포즈 검사를 유지한다.
- 리깅·동작이 실패했는데 정적 모델을 `ready`로 표시하는 동작은 금지한다.
- 완료 기준: worker 재시작, 전달 실패, 특정 동작 재시도에도 이미 성공한 유료 작업을 재요청하지 않는다.

### 단계 D — Unity 연결

웹은 제작·진행 관리, Unity는 결과 검사와 재생을 담당한다.
Unity의 `Tripo_Model_Test` 검사 창에 제작 서버 주소, 작업 목록, 결과 받기 기능을 추가한다.
Tripo API 키는 Unity에 전달하지 않는다. Unity는 제작 서버의 다운로드 API만 사용한다.

결과는 프로젝트의 `tools/_work/tripo_trial_<job_id>/`에 내려받아 기존 검사기로 연다.
파일명은 `generated.glb`, `rigged.glb`, `animated.glb`, `animated_pack.glb`, `motion_catalog.json` 계약을 유지한다.
`.part` 파일과 SHA-256 검증으로 미완성 결과를 완성 모델처럼 열지 않는다.
모델 재생·목록 새로고침·재다운로드가 새 생성 작업을 요청하지 않도록 한다.

- 완료 기준: 서버의 작업 한 개를 선택하면 단계별 모델과 9개 클립을 기존 검사 창에서 확인할 수 있다.
- 서버가 꺼져 있어도 이미 받은 로컬 모델 검사는 가능해야 한다.
- AI 테스트용 URL·토큰·EditorPrefs·씬 설정을 변경하지 않는다.

## 7. 새 제작 API와 산출물 계약 초안

다음은 미구현 독립 제작 기능의 계약 초안이다. 실제 경로를 구현하면 Unity 소비 코드와 이 문서도 함께 갱신한다.

| API 초안 | 역할 |
|---|---|
| `POST /tripo/jobs` | 원본 사진으로 작업 생성. 음성·인물 등록 불필요 |
| `GET /tripo/jobs`, `GET /tripo/jobs/{id}` | 목록·단계·진행·오류·산출물 조회 |
| `POST /tripo/jobs/{id}/tpose` | 설정한 이미지 편집 공급자로 전처리 |
| `POST /tripo/jobs/{id}/tpose-image` | 준비된 T포즈 이미지 업로드 |
| `POST /tripo/jobs/{id}/generate` | 선택한 전처리 결과로 생성·리깅·동작 시작 |
| `POST /tripo/jobs/{id}/retry` | 실패 단계부터 복구. 제출 결과 불명은 자동 재제출하지 않음 |
| `GET /tripo/jobs/{id}/artifacts/{kind}` | 허용된 산출물 종류만 다운로드 |

응답에는 `schema_version`, `job_id`, `stage`, `status`, `progress`, `error`, 입력 해시,
생성 프리셋, 산출물 종류·바이트 수·SHA-256·다운로드 경로를 포함한다.
서버 절대 파일 경로, API 키, 공급자의 서명된 URL을 클라이언트 계약으로 사용하지 않는다.
전처리·생성 작업 상태와 결과를 검수했는지는 별도 필드로 구분한다.

기존 등록 API의 `/internal/personas/...`와 `/session/...` 규격은 보존한다.
신규 `/session/start`에는 ID를 지정하지 않고 응답의 `session`을 사용한다. 기존 ID 지정은 400으로 거부된다.
제작의 `job_id`는 인물 등록과 별도로 발급한다. 기존 인물에 GLB를 붙일 때만 등록 API의 해당 ID를 사용한다.
새 파일·라우터가 생기면 `tools/service_bundle.py`의 platform 배포 목록과 인수인계 범위도 갱신한다.
파일을 추가하고 배포 ZIP에서 빠뜨린 채 서버 적용을 완료했다고 보고하지 않는다.

## 8. 검증과 인수 조건

아래를 통과하고 결과를 문서에 남긴다. 모의 검사와 실제 공급자 검사를 구별한다.

1. `Survey/tests/test_model_worker.py`의 현재 11개 검사와 관련 회귀 검사가 통과한다.
2. 이미지 전용 생성, 잘못된 이미지·작업 ID, 작업 간 파일 격리, 중복 시작, 부분 실패·재시작을 검사한다.
3. 전처리 공급자가 없어도 준비된 T포즈 업로드로 개발·검사가 가능하다.
4. 등록 서버·대화 서버 없이 제작 기능의 모의 검사가 통과한다. 운영 인물/DB가 변하지 않는다.
5. head는 실제 머리 생성·몸체 결합 결과의 얼굴·머리카락·목·본 연결을 사람이 확인한다. 전신 동작 팩 확장 시에는 별도로 최소 두 입력의 리깅·9개 동작을 검수한다.
6. Unity 컴파일과 모델 검사 메뉴, 모델 전환·Play/Stop·씬 재진입을 확인한다.
7. 공통 코드를 바꿨다면 `--area all`과 `AI_Response_Test`의 관련 검사 메뉴를 확인한다. 운영 대화·TTS 설정은 유지한다.
8. 웹/worker만 배포·재시작했음을 확인하고, 바뀐 파일·설정·검사 결과·남은 제약을 인계한다.

API 키나 테스트 사진이 없으면 모의 공급자·수동 T포즈 경로·다운로드 계약·UI를 먼저 완성한다.
사용량이 드는 실제 생성은 준비한 입력·설정·예상 작업 수를 담당자가 검토한 범위에서 실행한다.
실제 공급자 연결이나 시각 검증을 수행하지 않았다면 그 항목은 완료로 표시하지 않는다.
