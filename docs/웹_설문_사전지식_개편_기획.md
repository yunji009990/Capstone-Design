# 웹 설문·사전지식 개편 기획안

작성일: 2026-09-15. 기준 코드: `jw` / `1dae205`.
상태: **범위 확정 후 구현함**. 사용자가 D1은 전체 개편, D2는 설문 원본만 영구 보관으로 확정했다.
이 문서는 결정과 설계 근거를 남기고, 실제 구현·사용 방법은 [설문 v2 사용법](웹_설문_v2_사용법.md)에 있다.
로컬 모의 검사만 마쳤고 실제 서버·브라우저·Gemma 확인은 메인 담당이다.
운영에 아직 적용하기 전의 동작은 [등록 흐름 개선](웹_등록_흐름_개선.md)을 따른다.

## 1. 목표와 범위

사용자가 아는 인물 정보와 경험을 웹에서 입력하고, AI가 그 근거와 실제 말투를 사용해 대화하도록 만든다.
이름·호칭·말투의 기존 문제 해결과 사전지식 확장을 같은 개편으로 다룬다.
완료 단위는 설문 화면 → 확인 → 등록 → 관리자 조회 → 대화 프롬프트 → 실제 답변 검증이다.
개발 중에는 각 단계의 검사를 진행하고, 연결된 기능을 한 번의 개편으로 제공한다.

### 기존 합의와 유지할 동작

- 기본 예시 인물·추억을 실제 입력값으로 채우지 않는다.
- 앞 단계의 설문을 바꾸면 확인 결과를 다시 작성한다. 늦게 도착한 이전 응답은 적용하지 않는다.
- 작성 실패·빈 인물·확인하지 않은 새 버전은 등록을 막는다.
- 신규 등록 ID는 서버 UUID4다. 기존 ID 지정·덮어쓰기나 운영 인물의 자동 교체를 테스트에 사용하지 않는다.
- 대화 AI·웹/등록의 서비스 경계와 기존 음성·끼어들기 계약을 유지한다.

### 범위 확정

| 결정 | 확정 내용 |
|---|---|
| D1. 받을 정보 범위 | **전체 개편.** 이름·말투, 배경·취향, 사람·장소·추억, 근황·언급 조건까지 모두 받는다 |
| D2. 대화 기억의 영구 저장 | **설문 원본만 영구 보관.** 대화 기억은 기존대로 연결 단위이며 등록 DB를 자동으로 고치지 않는다 |

아래 상세 설계는 이 확정을 따른다.

### 테스트 인물 선택 (2026-09-15 추가 요청)

기존의 "시험용 자동 채우기 제거" 지시는 사용자의 새 요청으로 바뀌었다.
화면 상단의 **테스트** 버튼에서 가상 인물 **할머니**·**친구**를 골라 설문을 채울 수 있다.

- 처음 화면은 여전히 빈 설문이다. 명시적으로 고른 경우에만 입력을 채운다.
- 가상 예시임을 화면에 표시한다. 사진·음성 파일은 사람이 직접 고르고 등록 버튼도 사람이 누른다.
- 인물을 바꾸면 이전 인물의 카드·선택·확인 상태를 먼저 비운다.
- 기준 자료는 `Web/static/presets_v2.json` 하나이며 화면과 Python·Node 검사가 함께 쓴다.
T포즈·Tripo 제작 화면, Unity 씬·VR 기능, TTS 모델 교체는 이번 개편의 범위에 넣지 않는다.
등록 완료 후 같은 인물을 편집·재게시하는 기능과 서버 임시 저장도 후속으로 둔다. 이번의 수정 흐름은 등록 전 설문 수정이다.

## 2. 문항 구성

화면의 1~10단계는 유지한다. 아래 번호는 이번 개편에서 표시할 `단계-문항` 번호다.
기존 화면에는 개별 문항 번호가 없었으므로, 기존 4단계·5단계 등의 순서를 기준으로 정했다.
내부 필드 이름은 문항의 표시 순서와 분리하여 문구 변경이 저장 자료를 바꾸지 않게 한다.

| 번호 | 질문·입력 | 방식·조건 | AI 사용처 |
|---|---|---|---|
| 1-1~4 | 사별 기간·기존 동의 3개 | 기존 입력 유지 | 기록·진행 확인. 사별 기간은 프롬프트에 넣지 않음 |
| 2-1~2 | 오디오/영상·화자 수 | 기존 음성 경로 유지 | TTS 참조. 녹음 내용을 인물의 경험으로 변환하지 않음 |
| 3-1 | 사진 | 선택 | 기존 Tripo 경로 |
| 4-1 | 그분과 나는 어떤 관계인가요? | 필수 자유 입력 | 캐릭터와 사용자의 관계 |
| 4-2 | 그분의 성별 | 선택·모름 | 캐릭터 정보. 말투·취향을 성별로 추측하지 않음 |
| 4-3 | 나는 그분을 뭐라고 불렀나요? | 선택 | 사용자 → 캐릭터 호칭 |
| 4-4 | 그분은 나를 뭐라고 불렀나요? | 선택 | 캐릭터 → 사용자 호칭 |
| 4-5 | 내 이름이나 사용할 별명 | 선택 | 사용자 이름 |
| 4-6 | 그분의 성격 | 기존 선택 + 직접 입력 | 인물 성격 |
| 4-7 | 그분이 자주 하셨던 말 | 최대 3개·선택 | 말버릇. 존댓말/반말 설정과 충돌하는지는 확인 화면에서 점검 |
| 4-8 | 그분의 이름이나 별명 | 선택 | 캐릭터 이름. 4-5와 분리 |
| 4-9 | 기억 속 그분의 나이대·시기 | 대략적인 표현 허용·선택 | 어떤 시기의 정보인지 표시. 사별 날짜를 대신 계산하지 않음 |
| 4-10 | 그분이 지내던 지역·하셨던 일 | 배경 카드·선택 | 생활 배경 |
| 5-1 | 함께한 추억 | 사건별 카드 추가 | 실제로 제공된 공유 경험 |
| 5-2 | 좋아하거나 싫어하던 것·생활 습관 | 분류 + 짧은 설명 카드 | 일상 대화 소재 |
| 5-3 | 함께 아는 사람 | 이름/별명 + 양쪽과의 관계 | 누구를 가리키는지 구분 |
| 5-4 | 함께 가던 장소·자주 하던 일 | 장소/활동 카드 | 반복되던 일상 |
| 5-5 | 그분이 알고 있던 나의 모습 | 취향·꿈·당시 생활 카드 | 과거에 알려진 사용자 정보 |
| 6-1 | 가장 그리운 순간 | 기존 선택 입력 | 사용자 감정의 배경 |
| 6-2 | 전하지 못한 말 | 기존 선택 입력 | 사용자가 먼저 꺼낼 때 참고 |
| 6-3 | 다시 듣고 싶은 말 | 기존 선택 입력 | 사용자의 희망. 실제 과거 발언으로 취급하지 않음 |
| 6-4 | 이번에 새로 전하고 싶은 소식 | 근황 카드·선택 | 이번에 알려준 새 정보. 공유했던 과거로 바꾸지 않음 |
| 6-5 | 대화에서 지켜줬으면 하는 점 | 먼저 꺼내지 않을 주제·반응 선호 | 대화 지침 |
| 7-1 | 원하는 대화 톤 | 기존 위로형·평소형·자유형 | 대화 방향 |
| 7-2 | 그분은 나에게 어떤 말투를 쓰셨나요? | 반말·존댓말·혼용·잘 모름 중 선택 | 실제 어미와 예문 선택 |
| 7-3 | 말투가 달라지는 상황 | 혼용 선택 시 설명. 사투리도 선택 입력 | 상황별 말투. 관계·지역만으로 사투리를 만들지 않음 |
| 7-4 | 이런 상황에서 실제로 어떤 말을 하셨나요? | 상황 + 기억나는 대답, 최대 3쌍·선택 | 사용자 제공 말투 예시. 실제 기억인지 대략적인 표현인지 표시 |
| 8 | 사용할 목소리 확인 | 기존 경로 | TTS 참조 선택 |
| 9 | AI가 이렇게 알고 대화합니다 | 항목별 요약·수정·최종 확인 | 실제 등록할 내용 확인 |
| 10 | 등록 | 기존 서버 UUID4 발급 | 확인된 버전으로 등록 |

이름·나이·취향·사건 날짜를 모르면 비워 둘 수 있다. 이름이 없으면 입력된 관계·호칭으로 표현하고 새 이름을 만들지 않는다.
관계와 말투는 독립 입력이다. 존댓말을 쓰는 친구·자녀도 표현할 수 있어야 한다.
7-2의 ‘잘 모름’은 부드러운 해요체를 사용한다고 확인 화면에 명시한다. 선택 전부터 실제 말투가 확인된 것으로 저장하지 않는다.

## 3. 카드 입력과 최종 확인

### 공통 동작

- 선택 영역은 원하는 카드만 추가한다. 빈 카드는 사실로 저장하지 않는다.
- 카드마다 대상(그분/나/함께/선택한 인물), 내용, 시점, 기억 정도, 언급 방식을 구분한다.
- 시점은 ‘초등학생 때’, ‘정확히 기억 안 남’처럼 받을 수 있다. AI가 연도를 보충하지 않는다.
- ‘모름’, ‘답하고 싶지 않음’, ‘실제로 없음’을 서로 다른 상태로 다룬다. 마지막 상태는 사용자가 명시한 경우만 사용한다.
- ‘답하고 싶지 않음’은 답변 내용 없이 항목 상태만 남기고 그 항목을 추가로 캐묻지 않도록 한다.
- 입력 예시는 placeholder/도움말이며 저장 값이 아니다.
- 이전/다음 이동과 작성 실패 때 현재 입력은 유지한다. 브라우저 새로 고침·종료 후 복원은 이번 범위에서 제공하지 않는다.

### 공유 기억 카드 예시

다음은 가상 예시이며 미리 채우는 값이 아니다.

| 필드 | 예시 | 조건 |
|---|---|---|
| 어떤 일이 있었나요? | 할머니와 마루에서 수박을 먹었다 | 카드를 사용할 때 내용 필수 |
| 언제쯤인가요? | 초등학생 때 여름 | 선택 |
| 어디였나요? | 시골집 | 선택 |
| 누가 함께 있었나요? | 나, 할머니 | 선택. 관련 인물 카드와 연결 가능 |
| 실제 기억나는 말 | 씨는 여기다 뱉어라 | 선택. 듣고 싶은 말을 넣는 칸과 구분 |
| 기억의 정도 | 정확히 기억함 / 대략 기억함 / 확실하지 않음 | 사건 전체의 확실성. 정확한 날짜를 별도로 추정하지 않음 |
| 언급 방식 | 관련 대화에서 먼저 언급 가능 / 내가 꺼낼 때만 / AI에 전달하지 않음 | 사실 내용의 사용 범위 |

‘내가 꺼낼 때만’은 언어 모델의 대화 지침이다. 해당 내용이 모델에 전달되지 않는다는 뜻으로 표시하지 않는다.
‘AI에 전달하지 않음’은 사전지식·예문·리액션 입력에서 해당 내용을 제외한다. 저장 여부는 확인 화면에서 별도로 보여준다.

### 9단계 확인과 편집의 기준

일반 화면에는 ‘그분의 정보 / 우리의 기억 / 새로 전할 소식 / 대화 방식’을 보여준다.
각 항목의 수정은 원래 문항을 고치고 다시 작성하는 방식으로 통일한다. 확인 화면에서 입력 완료 전 미확정 내용을 숨기지 않는다.
이전 버전의 원시 persona/knowledge 직접 편집 화면을 새 설문의 일반 편집 방식으로 사용하지 않는 것이 권장안이다.
사용자가 추가 설명을 적고 싶으면 해당 종류의 직접 입력 카드를 사용한다.

수정 → 작성 버전 무효화 → 새 미리보기 → 최종 확인 → 등록 순서다.
요청 중 이탈·실패·시간 초과·늦은 응답·중복 클릭 방지는 현재 구현을 유지한다.
설문 원문과 별개로 편집한 프롬프트가 남는 두 개의 편집 기준을 만들지 않는다.

## 4. 저장 자료와 API 설계

### 원본과 실행용 정보

| 자료 | 저장·생성 방식 | 소비자 |
|---|---|---|
| 설문 원본 | 기존 SQLite `payload_json`에 `survey_schema_version=2`와 구조화된 답변 저장 | Web·관리자 |
| 등록 시 스냅샷 | 확인된 답변 해시, 변환기 버전, 최종 persona/knowledge/rules를 같은 payload에 기록 | 등록 내용 대조·진단 |
| `persona` | 관계·분리된 이름·호칭·성격·말투·예문을 규칙으로 변환 | 대화 인물 설정 |
| `knowledge` | 사용자 제공 사실·사건·근황과 그 출처/시점/확실성을 읽기 쉬운 텍스트로 변환 | 대화 사전지식 |
| `rules` | 언급 조건·반응 선호를 공통 규칙 아래의 추가 지침으로 생성 | 대화 정책 |
| 연결 내 기억 | 기존 사용자 발화 근거·정정·삭제 처리 유지 | 해당 대화 연결 |

원본 설문의 `answers`와 생성한 `compiled_snapshot`을 분리한다. 입력 해시는 answers와 설문 버전으로 계산하고
자기 자신인 compiled_snapshot을 포함하지 않는다. 카드 ID는 설문 안에서만 고유하며 등록 세션 ID와 구분한다.
사용자 입력을 사실 자료·말투 예시로 표현하고, 그 안의 문장을 공통 운영 규칙으로 승격하지 않는다.

카드 공통 필드 초안: `id`, `kind`, `subject`, `content`, `time`, `certainty`, `mention_policy`, `answer_state`.
종류별 세부 필드는 인물의 양방향 관계, 장소, 참석자, 실제 대사 등을 가진다. 알 수 없는 종류·상태·깨진 참조는 검증 오류로 처리한다.
원문에 없던 사실을 요약 과정에서 추가하지 않는다. 최초 구현의 변환은 기존처럼 규칙 기반이며 설문 작성 때 Gemma를 추가 호출하지 않는다.

### 기존 API에 추가할 계약

- `/persona`: v2를 검증하고 `persona`, `knowledge`, `rules`, 사용자용 확인 항목을 반환한다.
- 기존 `survey_revision`은 입력 일치 검사로 유지한다. 변환기 버전과 최종 세 텍스트의 해시를 포함한 `preview_revision`을 추가한다.
- `/publish`·`/publish_direct`: v2 원문을 서버에서 다시 검증·변환한다. 입력 버전과 미리보기 버전이 같을 때만 등록한다.
  변환기 배포 이후 오래 열린 화면도 다시 확인하게 한다. 이 해시들은 인증 토큰이 아니다.
- 등록 API에는 서버가 만든 persona/knowledge/rules와 참조 음성을 전달한다. 기존 서버 발급 UUID4를 사용한다.
- 인물 조회의 `schema_version=1`, `session`, `revision`, `persona`, `knowledge`, `rules`, `voice_sha256` 계약은 유지한다.
- 대화 AI는 등록 API만 읽는다. Survey DB나 Web 모듈을 import하지 않는다.
- 관리자 상세 화면과 JSON 다운로드에서 v1/v2 원문·최종 확인 내용을 구분해 조회한다. 입력 텍스트를 HTML로 실행하지 않는다.

기존 등록 인물과 v1 DB 행은 그대로 읽고 자동 변환하지 않는다. 새 화면과 신규 등록은 v2만 사용한다.
오래 열린 v1 웹의 작성·등록 요청은 새 화면에서 다시 확인하도록 명확한 오류로 거부한다.
거부 응답 때문에 기존 화면의 입력을 비우지는 않는다. 구형 화면 입력의 자동 이전은 제공하지 않으므로
배포 안내에 새로 작성해야 한다는 점을 포함한다. API 경로와 기존 인물 조회 호환성은 유지한다.
기존 데이터 삭제 경로에서도 새 payload와 등록 스냅샷을 함께 제거한다.
현재 두 서비스의 부분 저장 실패 응답은 유지한다. 분산 트랜잭션 도입까지 이 개편에 포함하지 않는다.

## 5. AI 답변과 길이 처리

### 사실 해석 규칙

1. 사용자 이름과 캐릭터 이름을 다른 필드·문장으로 만든다. 사용자 이름을 캐릭터의 자기소개 예문에 사용하지 않는다.
2. 관계만 보고 반말·사투리·취향·경험을 결정하지 않는다. 실제 말투 선택과 제공된 표현을 우선한다.
3. 불확실한 기억은 ‘사용자가 대략 기억하는 내용’으로 표현한다. 빈 항목을 존재하지 않는 사실로 바꾸지 않는다.
4. 희망하는 대사는 과거 발언·약속이 아니다. 새로운 근황은 이번에 알려준 정보로 표현한다.
5. 대화 중 사용자가 정정한 사실은 기존 연결 내 기억 계약에 따라 반영한다. 원본 설문 DB는 자동 수정하지 않는다.
6. 모르는 사실이 답변에 필요하면 한 가지를 자연스럽게 되묻는다. 이미 확인된 내용은 반복해서 묻지 않는지 평가한다.

### 길이와 대기 리액션

현재 대화의 기본 예산은 8,192토큰이고, 사전지식은 시스템 프롬프트에 포함되어 오래된 대화 원문처럼 자동 제거되지 않는다.
따라서 카드 수만 늘려 모든 내용을 무제한으로 붙이는 구현은 피한다.

- 첫 구현은 짧은 카드와 전체 길이 제한을 사용한다. 한 카드의 주 내용은 최대 200자, 전체 지식 카드 최대 20개,
  AI에 전달할 추가 지식의 원문 합계는 2,000자를 초기 상한으로 제안한다. 시점·대사 등 부가 텍스트도 합계에 포함한다.
  → **이 2,000자는 검증 전 초안이다.** 실제 `/tokenize` 검사에서 2,000자는 705토큰, 1,200자는 69토큰을 넘겨
  **확정 상한은 800자**가 되었고 집계 범위도 이름·호칭·성격까지 넓혔다. [설문 v2 사용법](웹_설문_v2_사용법.md) 5장을 따른다.
- 확인 화면에서 길이 초과 항목을 알려 사용자가 줄이거나 AI 사용에서 제외하도록 한다. 조용히 잘라 저장하지 않는다.
- 위 문자 제한을 토큰 수 보장으로 설명하지 않는다. 실제 모델의 `/tokenize`와 현재 기억 최대 입력을 조합해
  일반·추론 모두에서 답변 공간이 남는지 검증하고, 실패하면 출시 전에 상한·표현 길이를 조정한다.
- 답변 전 기존 실제 토큰 검사와 오류 처리는 유지한다. 매 턴 추가 Gemma 선택 호출이나 벡터 DB는 도입하지 않는다.
- 대기 리액션은 성격·말투로 준비한다. 사전지식·새 근황·언급 제한의 구체적인 내용은 준비 입력에서 제외한다.
  현재 리액션 준비가 추가 rules도 사용하므로, 새 언급 조건이 그 경로로 들어가지 않게 대화 코드에서 입력을 분리한다.
- 등록을 새로 해도 이름·말투가 다른 인물의 이전 리액션 캐시를 재사용하지 않는지 확인한다.

이 상한은 권장 설계값이다. 더 많은 자료와 문서 업로드·질문별 검색은 후속 확장으로 둔다.

## 6. 구현 순서와 수정 범위

| 순서 | 작업 | 주된 위치·완료물 |
|---|---|---|
| 1 | 문항·v2 자료 형식·상태·길이 규칙 고정 | 이 문서와 가상 입력 자료 |
| 2 | v2 검증·규칙 기반 변환과 기존 자료 조회 호환 | 전용 변환 모듈 `Web/survey_v2.py` (v1의 `persona.py`·`registration_input.py`를 대체) |
| 3 | 단계별 카드·수정·최종 확인 | `Web/static/index.html`, 전용 JavaScript/CSS 모듈 |
| 4 | 두 등록 경로의 버전 검사·스냅샷 저장·관리자 조회 | `Web/app.py`, `Survey/core/database.py`, `Web/static/admin.html` |
| 5 | 대화의 말투·사실 전달 및 리액션 입력 경계 | `Server/persona_context.py`, `dialogue_server.py` 등 필요한 대화 코드 |
| 6 | 회귀·브라우저·실제 Gemma 검증 | `Web/tests`, 등록/인물 계약 검사, 대화 평가 자료 |
| 7 | 배포·복구·사용법 정리 | 두 영역의 배포 목록·해시·백업·문서·팀원 인계 목록 |

유료 Tripo 호출·모델 생성·Unity 기능 변경은 이 구현의 선행 조건이 아니다.
실제 대화가 새 필드를 읽는 데 필요한 변경만 대화 영역에 적용하고, 다른 기능의 재구성은 섞지 않는다.

## 7. 완료 기준

### 기능·계약 검사

- 어머니·친구·자녀·미분류 관계 각각에서 반말/존댓말/혼용/모름이 지정한 텍스트와 예문으로 만들어진다.
- 캐릭터와 사용자 이름이 다르거나 같거나 비어 있을 때 각각의 역할이 유지된다.
- 카드 추가·삭제·순서 변경·모름·비공개 선택·불확실한 시점이 원문 → 확인 화면 → 등록 → 조회에서 유지된다.
- ‘희망 대사’가 실제 발언으로, ‘새 근황’이 공유했던 기억으로 변환되지 않는다.
- AI 제외 내용이 최종 지식·예문·리액션 입력에서 빠진다. 조건부 언급 지침의 전달과 실제 답변 준수는 별도로 검사한다.
- 수정 후 이전 미리보기 등록, 시간 초과·늦은 응답, 이중 클릭, 직접 ID 지정, 너무 긴 입력, 알 수 없는 상태를 처리한다.
- 두 음성 등록 경로, 기존 v1 인물 읽기, 관리자 표시·다운로드·삭제, 부분 저장 실패를 확인한다.
- `python tools/check.py --area all` 통과. 기존 135개 결과는 변경 후 새 검사를 대신하지 않는다.
- 실제 Edge에서 전체 입력·수정·확인·실패 복구·등록 완료 화면을 확인한다. 가상 API와 실제 운영 API의 범위를 기록한다.

### 실제 AI 검사

- 가상 인물 3종(반말·존댓말·혼용), 각 10턴 이상에서 동일한 인물·상황·이전 발화를 유지한다.
- 이름·호칭·관계, 알고 있는 사실, 모르는 사실, 대략적인 날짜, 인물 간 관계, 새 소식, 정정, 금지/조건부 주제를 평가한다.
- 고정된 입력·토큰 수·모델 설정·응답 원문을 남긴다. 특정 답변의 자연스러움을 자동 기능 통과로 보고하지 않는다.
- 최대 길이 설문과 기존 기억을 함께 넣은 일반/추론 경로의 토큰 예산·응답 지연을 확인한다.
- 운영의 현재 등록 인물을 가상 인물로 바꾸지 않는다. 격리된 등록 자료와 검사 연결로 제공자·소비자 흐름을 확인한다.
- 음성 지연까지 비교할 경우 같은 입력 3종을 각 3회 사용하고 첫 리액션·첫 본답변·실제 청취 결과를 구분한다.

이름 역할 혼동·등록 정보 유실·AI 제외 정보 전달은 출시 전에 해결한다.
조건부 주제와 말투의 실제 준수 결과는 사례별로 기록하고, 반복되는 실패가 있으면 프롬프트를 수정해 재검증한다.

## 8. 배포와 이후 작업

새 모듈과 화면 파일은 platform 배포 목록에 포함한다. 대화 변경은 dialogue 묶음에 포함한다.
관리자가 v1/v2 저장 자료를 모두 읽고, 대화가 기존/새 인물 텍스트를 모두 처리하는 상태를 먼저 만든 뒤 새 화면을 공개한다.
적용 시 대상 파일 백업·배포 해시·health·로그를 확인하고 진행 중인 체험과 현재 인물 자료를 보존한다.
되돌릴 때에는 원본 v2 설문을 삭제하지 않고, v2를 표시하지 못하는 이전 관리자 화면의 제한도 기록한다.

사용자에게 전달할 산출물은 최종 문항표, v2 자료 형식, 사용 방법, 실제/모의 검사 결과, 배포·복구 기록이다.
이 중 문항표·자료 형식·사용 방법은 [설문 v2 사용법](웹_설문_v2_사용법.md)에 정리했다.
D2를 나중에 영구 대화 기억까지 넓히면 해당 저장·확인·삭제·재접속 계약을 먼저 추가한다.
지금 구현은 설문 원본 보관까지이며, 대화에서 나온 내용은 연결 안에서만 유지된다.
