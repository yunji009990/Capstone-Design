# 첫 턴 뒤 무응답과 말끝 감지 보완

기준일: 2026-09-16. WebRTC VAD가 배경음을 계속 말로 판단해 다음 음성 인식으로 넘어가지 못하는 경로를 재현하고 보완했다. UI 받아쓰기 제거·이동 버튼 디자인은 사용자 요청으로 보류했다.

## 원인과 증거

문제가 발생한 실제 체험에서는 첫 답변 이후에도 마이크 PCM과 heartbeat가 계속 들어왔다. 다음 입력 후보는 18~26초 동안 `started` 상태였고 `closed`가 없어 Whisper가 추가로 호출되지 않았다. Unity의 재생 버퍼 고갈과 큰 프레임 지연은 없었다. 마지막 종료 기록은 `on_disable`/`control_disabled`였으며, 답변 완료가 체험을 종료하는 연결은 없었다. 같은 코드로 정상 3턴이 이어진 기록도 있었다.

기존 순서는 **WebRTC의 말끝 → Silero 검증 → Whisper → 대화 판정·답변**이었다. WebRTC가 700ms 연속 비음성을 찾지 못하면 Silero도 시작하지 못했다. 30초를 넘기면 발화를 버리고 다시 무음을 기다리므로 잡음이 계속되는 동안은 복구가 어려웠다.

원음은 저장하지 않았다. 실제 환경음이 웅웅거림인지 스피커 에코인지는 확정하지 않는다. 다만 공개/합성 음성에 낮은 hum(-35dBFS)을 섞어 같은 대기 상태를 재현했다. 실제 운영 API에서도 같은 연결에서 첫 조용한 질문은 답하고 두 번째 잡음 섞인 질문은 15초 검사 제한까지 답하지 않았다.

## 현재 동작

1. WebRTC의 기본 말끝 기준(700ms)과 Silero 채택 기준(0.7, 최소200ms)을 유지한다.
2. 후보가 2초 이상 열리면 최근2초를 400ms 간격으로 같은 CPU Silero 실행기에 보낸다. 30초 상한 이후 폐기 대기도 검사한다.
3. Silero가 마지막 음성 뒤 700ms 이상의 비음성을 확인한 경우 후보를 마감하거나 폐기 대기에서 벗어난다. 길이만으로 문장 중간을 강제 마감하지 않는다.
4. 마감한 입력은 기존 전체 Silero 검증과 Whisper 전사 유효성 검사를 거친다. 그 뒤에만 기존 답변을 보류·중단할 수 있다.
5. 검사 중 새 오디오가 한 프레임이라도 들어오면 과거 결과를 버리고 최신 창으로 재검사한다. reset/close에서는 작업·일정·최근 오디오를 정리한다.

Whisper·Gemma·Qwen 모델, Unity 프로토콜, 등록 정보는 변경하지 않았다. 말끝 보완 자체는 새 GPU 모델이나 Gemma 호출을 추가하지 않는다. 모델 사용법은 설치된 sherpa-onnx API와 [공식 VAD 예제](https://github.com/k2-fsa/sherpa-onnx/blob/master/python-api-examples/vad-microphone.py)를 확인했다.

주요 코드: `Server/realtime_audio.py`, `speech_gate.py`, `realtime_dialogue.py`, `dialogue_diagnostics.py`. 회귀 검사는 `Server/tests/test_endpoint_supplement.py`다.

## 상태와 로그

`/health.input_gate.endpoint.version=silero_tail_v1`이면 보완 코드가 적용돼 있다. 창·최소 후보 길이는2,000ms, 검사 간격은400ms다. `/health.diagnostics.version=dialogue_diag_v3`에는 기존 기록과 함께 다음 항목이 생겼다.

| 항목 | 뜻 |
|---|---|
| `input.endpoint reason=silence_tail` | Silero 비음성 꼬리로 후보 마감 |
| `reason=rearmed` | 길이 상한 폐기 대기에서 복구 |
| `reason=speech` | 아직 말이 이어지거나 꼬리를 재지 못해 계속 기다림 |
| `reason=stale` / `failed` | 오래된 결과/검사 오류. 기존 답변에는 영향 없음 |
| `age_ms`, `voiced_pct`, `max_quiet_ms`, `tail_ms` | 후보 나이, WebRTC 음성 비율, 최장 연속 비음성, Silero 비음성 꼬리 |
| `endpoint_checks/end/rearm/failed/stale` | 연결별 집계 |

변화가 없는 결과는2초 간격으로 제한한다. 사용자 발화·음성·인물·장치명·키를 로그에 넣지 않는다. 양쪽 진단의 시간 대조는 [음성 재생 끊김 진단](음성_재생_끊김_진단.md)을 따른다.

## 후속 실제 모델 검사에서 확인한 별도 실패

말끝 수정 후 같은 연결의 두 번째 발화는 정상 마감되고 Whisper 전사와 추론 답변 생성까지 진행했다. 그러나 Gemma가 숨은 추론만으로 생성 한도를 소진하여 `finish_reason=length`로 끝났다. 서버의 `answer token budget exhausted`가 `turn_failed`로 전달됐고, 대기 리액션 1.36초 뒤 본답변은 나오지 않았다. 이는 말끝 대기와 별개의 실패이며, 실제 사용자 기록의 원인으로 소급해서 단정하지 않는다.

수정 전 결과는 `live-baseline.json`(두 번째 입력 이후 전사 없음), 말끝 수정 직후 결과는 `live-fixed-before-budget.json`(전사 성공 후 추론 한도 오류)에 구분해 보관한다.

이 실패는 `Server/realtime_llm.py`에서 제한적으로 복구한다. **추론 경로가 생성 한도로 끝났고, 아직 본답변의 유효 문자를 하나도 전달하지 않은 경우**에만 원래 메시지를 일반 경로로 한 번 다시 요청한다. 숨은 추론·초안은 넘기지 않는다. 각 요청의 토큰화·문맥 제한과 추론 텍스트 필터를 그대로 적용한다. 이미 본답변을 내보냈거나 일반 경로도 실패하면 오류를 유지하며, 부분 답변을 정상 완료로 바꾸지 않는다. 취소·HTTP 오류·문맥 한도 오류도 이 복구 대상이 아니다.

운영 로그의 `answer.budget_fallback route=reasoning->normal reason=length_before_any_text`로 복구 여부를 확인한다. Unity의 최초 `route`는 원래 선택한 `reasoning`을 유지한다. 이 예외 상황에서만 일반 Gemma 호출이 한 번 추가된다. 추론 대기 시간을 줄이는 수정은 아니며, 해당 턴의 답변 품질은 일반 경로 기준이 된다.

- 새 모의 검사 13개는 리액션 이후 본답변 완료·다음 턴 처리, 중복 답변 방지, 취소·오류 유지, 스트림 정리, 각 경로의 문맥 검사를 포함한다.
- 최종 공식 검사: **297개 통과, 건너뜀 0**(하네스 94개 + 서버 203개). 결과는 `tools/_work/checks/20260916-one-turn-final/report.json`이다.
- 2026-09-16 18:04 KST에 `realtime_llm.py`만 추가 백업·배포했다. 대화 API만 재시작했으며 ready 상태와 모델 준비를 확인했다.
- 실제 Gemma HTTP 스트림에서도 별도 검사 클라이언트에만 추론 한도 16토큰을 주입해 실패를 만들고, 일반 경로 1회 재요청으로 답변이 완료됨을 확인했다. 운영의 2048토큰 설정은 바꾸지 않았다. 추론 텍스트 유출 없이 본답변이 나왔고 복구 로그도 1개 남았다(`budget-live.json`).
- 이 검사로 최초 수정안의 INFO 기록이 운영 기본 로그 수준에서 빠지는 것을 발견했다. WARNING 기록으로 보강하고 18:13 KST에 해당 파일만 배포했다. 로그 보강 후 위 공식 검사와 실제 한도 오류 복구 검사를 통과했다.

## 최종 연속 대화 검사

공개 한국어 음성, 합성 질문, 합성 주제 전환 구절을 각각 3회씩 같은 WebSocket에 보냈다. 첫 입력은 조용한 조건, 나머지 8개는 -35dBFS hum이 계속 있는 조건이다. Unity와 같은 16kHz 모노 PCM을 80ms마다 보내고, 턴 사이 연결 재시작이나 reset은 하지 않았다. 재생 확인은 검사 클라이언트가 대신하므로 실제 Unity·스피커·헤드셋의 청취 검사는 아니다.

| 항목 | 결과 |
|---|---|
| 입력 채택 / Whisper 호출 / 본답변 완료 | 각각 9회 |
| 최초 선택 경로 | 일반 6회, 추론 3회 |
| 의미 없는 음성 후보 기각 | 27회 |
| 말끝 검사 실패 / 오래된 결과 / 30초 상한 폐기 | 각각 0회 |
| 모든 입력 전송 종료 후 잡음만 5초 | 추가 전사·답변 0 |
| 검사 종료 후 연결 / 서버 상태 | 0 / ready |

`live-fixed.json`, `final-diagnostics.json`에 결과가 있다. 가장 오래 걸린 추론 턴은 입력 시작부터 첫 본답변 음성까지 약 35.8초였다. 말끝 보완과 한도 복구는 이 추론 지연 자체를 줄이는 작업이 아니다.

중간 검사 `live-fixed-before-tail-check.json`은 9회 답변 후 추가 답변 때문에 실패 처리했다. 해당 검사의 `switch.wav`에는 약 700ms 전후의 긴 쉼을 사이에 둔 두 발화가 있었고, 첫 답변 완료(입력 시작 후 2.565초) 시점에도 3.84초 파일의 뒷부분을 계속 보내고 있었다. 따라서 그 구간을 '잡음만'으로 보는 것은 잘못된 검사였다. 최종 검사는 입력 전송 완료를 직접 확인하고, 원본을 변경하지 않은 채 이 파일의 두 번째 구절(1.6~3.84초)을 사용했다. 실패 결과를 덮어쓰거나 말끝 기준을 완화하지 않았다.

## 남은 범위와 되돌리기

실제 사용자 마이크 재검사는 별도로 필요하다. AEC·화자 식별을 추가한 것은 아니므로 주변 사람 말과 캐릭터의 스피커 음성을 구별하지 못한다. Silero가 놓치거나200ms보다 짧아 구간으로 보고하지 않는 소리는 비음성 꼬리에 포함될 수 있다. 첫 답변 전 `microphone_stopped`와 오디오 구성 변경이 함께 있었던 별도 사례도 이 변경의 해결 대상으로 확정하지 않는다.

배포 전4개 파일은 서버 `~/capstone-server/backups/one_turn_20260916T085107Z/`에 있다. 되돌릴 때 활성 연결0인지 확인하고 대화 API만 멈춘 뒤 이4개 파일을 복원한다. `dialogue.sh api start` 후 health와 해시를 확인한다. Whisper 설정·TTS·웹·등록 서비스는 변경 대상이 아니다.

추론 한도 복구 전 `realtime_llm.py`는 `~/capstone-server/backups/one_turn_budget_20260916T090431Z/`에 별도로 보관했다. 이 파일만 복원하면 말끝 보완은 유지하면서 추론 복구만 되돌릴 수 있다.
로그 수준 보강 직전 파일은 `~/capstone-server/backups/one_turn_budget_log_20260916T091345Z/`에 있다.
