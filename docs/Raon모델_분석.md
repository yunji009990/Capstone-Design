### 문서에 있는 것 / 없는 것

**있는 것** — 기술 보고서에서 건진 유일한 수치:

> 화자 정체성 제어를 위해 화자 임베딩으로 조건화하며, **목표 음성의 2~8초 무작위 청크**를
> 인코딩하여 LLM 입력 시퀀스에 삽입

즉 `tts()` 의 화자 조건화는 **2~8초로 학습**됐다. 참조가 길다고 좋은 게 아니다.

**없는 것 (중요)** — 모델 카드·GitHub README·기술 보고서·OpenTTS 논문 어디에도 없다:

- `tts_continuation` 의 참조 음성 조건
- **RAS(Repetition Aware Sampling) 설명이 전무하다**
- 생성 파라미터 권장값
- 반복 루프 같은 알려진 실패 사례

**그래서 이 문서의 내용은 대부분 코드를 읽고 실측해서 얻은 것이다.** 문서를 찾아
헤매지 말 것 — `modeling_raon.py` 가 유일한 권위 있는 출처다.

## 2. 두 가지 합성 경로

### `tts()` — 음색만

```python
# modeling_raon.py:10589
speaker_token = str(SPEAKER_EMBEDDING_PLACEHOLDER) if speaker_audio is not None else ""
```

참조를 **화자 임베딩 토큰 하나로 압축**한다. 담기는 건 음색뿐이고 억양·속도·리듬은
전달되지 않는다. 그 자리를 모델의 기본 낭독체가 채운다.

**참조 조건이 사실상 없다.** 조각을 이어붙인 6.3초 참조로도, 잡음이 심한 참조로도 동작한다.

### `tts_continuation()` — 억양까지

```python
# modeling_raon.py:10626
combined_text = f"{ref_text} {target_text}"          # 참조 전사 + 할 말을 한 문장처럼
audio_prefix = AUDIO_START + AUDIO_OUTPUT_PLACEHOLDER * num_ref_frames
output = self.model.generate(audio_output=ref_audio_tensor, ...)
```

참조 오디오를 **"모델이 방금 생성한 출력"으로 문맥에 프리필**하고 그 뒤를 잇게 한다.
이미 그 억양으로 말하던 중이니 계속 그 억양으로 말한다.

**`ref_text` 가 필수다.** 안 주면 매 합성마다 `self.stt(ref_audio)` 를 다시 돈다(1.2초).
서버는 `REF_TEXT` 에 세션당 1회만 캐시한다.

파라미터는 `task_params["tts_continuation"]` → 없으면 `task_params["tts"]` → 없으면
함수 기본값 순으로 읽는다.

| 파라미터 | 기본값 |
|---|---|
| `max_new_tokens` | 512 (= 41초) |
| `temperature` | 1.2 |
| `top_k` / `top_p` | 20 / 0.8 |
| `ras_enabled` | **False** |
| `ras_window_size` / `ras_repetition_threshold` | 50 / 0.5 |
| `continuation_silence_frames` | 2 |

## 3. RAS (Repetition Aware Sampling)

`modeling_raon.py:6206`. **문서 어디에도 설명이 없다.**

```python
def apply_repetition_aware_sampling(sampled_ids, logits, audio_codes,
                                    window_size, repetition_threshold, skip_frames=0):
    first_group_codes = audio_codes[:, skip_frames:, 0]     # 첫 코드 그룹만
    window = codes_seq[max(0, len - window_size):]          # 최근 N 프레임
    repetition_ratio = (window == sampled_token).sum() / window.numel()
    if repetition_ratio > repetition_threshold:
        probs = F.softmax(logits, ...)                      # ← 원본 logits
        result_ids = torch.multinomial(probs, 1)            # top_k/top_p 안 거치고 재추첨
```

**알아둘 것 넷:**

1. **프레임당 코드 그룹 16개 중 첫 번째(의미 토큰)에만 적용**된다.
2. **재추첨이 원본 logits 에서 이뤄진다.** `top_k=20`/`top_p=0.8` 필터를 건너뛰므로
   확률이 아주 낮은 토큰도 나온다. 자주 발동하면 그만큼 이상한 토큰이 섞인다.
3. 하는 일은 **토큰 하나 다시 뽑기**뿐이다. 루프 상태를 구조적으로 깨지는 못하고
   확률만 낮춘다.
4. `window` 는 항상 **최근** N 프레임이라, N 프레임 넘게 생성된 뒤엔 `skip_frames` 가
   무의미하다. continuation 에서 프리필 프레임이 섞이는 건 생성 초반뿐이다.

### 임계값 정하기

같은 파일 안에 기본값이 두 가지다 — `generate()` 는 **50/0.5**(7543), 내부 호출부는
**40/0.1**(7008, 7036).

- **0.5는 너무 느슨하다.** 토큰 하나가 창의 절반을 넘어야 발동해서, 두세 토큰이
  번갈아 도는 패턴을 놓친다.
- **너무 낮추면 무음에서 발동한다.** 쉼도 같은 토큰이 이어지므로, 창 40(3.2초)에서
  1.5초 쉬면 그것만으로 47% 다.
- **창을 넓히는 게 임계값을 낮추는 것보다 낫다.** 창 100(8초)이면 1.5초 쉼은 19% 라
  안 걸리고, 8초를 뒤덮는 루프는 70% 가 넘어 여전히 걸린다. **쉼과 루프를 분리하는
  게 요점이다.**

실측 결론: **창 100 / 임계 0.35** 에서 루프가 사라지고 무음 훼손도 없었다.

## 4. 프레임 단위 스트리밍 훅

`Server/modeling_raon.patch` — `generate()` 루프에 넣은 우리 코드.
`self._frame_callback` 이 없으면 완전히 무해하다.

생성 도중 `audio_codes` 를 잘라 `audio_tokenizer.decode(use_streaming=True, ...)` 로
증분 디코딩하고 캐시를 넘겨받는다. `_frame_chunk`(기본 8 = 0.64초)마다 플러시.

**실측으로 확인한 것:**

- **`generate()` 는 프리필한 참조 프레임을 `audio_codes` 에 남기지 않는다.**
  `_raon_sent = [0]` 으로 처음부터 잘라도 참조가 흘러나오지 않는다.
  12초 참조 + 짧은 답변 → 출력 2.9초. continuation 에 수정 없이 그대로 쓸 수 있다.
- **경계 아티팩트가 없다.** 생성 오디오의 급변 지점이 0.64초 격자와 무관하게 흩어져
  있다(위상 평균거리 0.148초, 무작위 기댓값 0.160초). 지지직의 원인이 아니다.
- 이 모델은 `delays = None` → `max_delay = 0`. 지연 코드 패턴이 없어 선행 대기가 0이다.

## 5. `tts_continuation` 의 반환값은 못 믿는다

```python
# modeling_raon.py:10732
audio_lengths = output["audio_lengths"]
return waveform[:length], self.processor.sampling_rate
```

프리필한 참조 프레임을 빼는 길이 계산이 어긋나 **거의 비어 있다.** 같은 세션·같은
참조·같은 텍스트로:

| 오디오를 어디서 꺼내나 | 결과 |
|---|---|
| 반환 파형 | 0.0 / 0.32 / 0.32초 |
| 프레임 훅 | 2.48 / 7.52 / 4.56초 |

**서버는 `synth()` 도 프레임 훅으로 모으게 바꿔서 우회했다**(`generate()` 함수).
`/talk` 이 0.3초 → 7.4초로 복구됐고 되인식 결과도 답변과 일치한다.

### 미해결 — `/tts` 만 여전히 짧다

같은 `synth()` 를 부르는데 `/talk` 은 정상(7.4초), `/tts` 는 실패(0.2~0.9초).
배제한 것: 텍스트 내용·길이, curl 인코딩(`--form-string`), 선행 호출 상태
(`/stt`·`/talk` 을 먼저 돌려도 동일), 세션·참조 명시.

단서 하나 — 실패한 0.16초를 되인식하면 **"네."** 다. 요청한 문장을 읽은 게 아니라
**대꾸를 만들었다.** 모델이 텍스트를 "읽을 것"이 아니라 "답할 것"으로 해석한 듯한데
밖에서는 못 가렸다.

**`/tts` 를 계측기로 쓰지 말 것.** 이 값을 믿고 참조 품질을 두 번 잘못 판단했다.

> **2026-08-01 재확인 — 통제 조건에서 다시 재현했다.** `/talk` 이 방금 정확히
> 합성한 문장을 그대로 `/tts` 에 넣으면 실패한다(16.0초 잡음 / 0.56초 "네."). 세션·
> 참조·텍스트가 전부 같고 엔드포인트만 다르다. `/stt` 를 먼저 끼워도 안 고쳐진다.
> 남은 차이는 `/talk` 이 `synth()` 전에 `pipe.chat()` 을 돈다는 것 하나뿐이다.
>
> 중간에 "프레임 훅으로 고쳐졌다"고 판단했다가 취소했다 — 200 OK 와 오디오 길이만
> 보고 **내용을 되인식하지 않은 채** 단정했다. 길이가 정상이어도 내용이 딴소리일 수
> 있다. 계측기를 검증할 때는 반드시 `/stt` 로 내용까지 볼 것.

## 6. 참조 음성 조건 — 통제 실험

### 잡음: 용량-반응이 확인된다

같은 화자·같은 내용(`녹음.m4a`)에 **핑크 잡음만** 얹어 SNR 을 낮춘 결과.
화자·내용·쉼이 고정되고 잡음만 변한다.

| 참조 SNR | 출력 길이 | 고역 아티팩트 |
|---|---|---|
| 40dB | 6.8 / 7.4초 | 0.029 |
| 32dB | 6.2 / 6.2초 | 0.055 |
| 26dB | 5.4 / 5.9초 | 0.065 |
| 21dB | **12.9** / 8.9초 | 0.077 |
| 16dB | **16.0**(상한) / 8.6초 | 0.086 |

**루프 절벽은 21~26dB 사이**다. 지지직(고역 아티팩트)은 절벽 없이 연속으로 늘어난다.

### 쉬는 구간은 조건이 아니다

깨끗한 녹음에서 조용한 프레임만 잘라내 **쉼 0%** 로 만든 참조 → 출력 4.1 / 5.3 / 5.0초,
고역 0.047. **정상이다.** "멈추는 패턴을 못 본 참조는 멈출 줄 모른다"는 가설은 틀렸다.

조각을 이어붙이는 것도 문제가 아니다 — 조각 3개짜리 12초 참조가 정상 동작했다.

### 측정 지표 (한 번 갈아엎었다)

처음 쓴 "0.1초 창 RMS 최댓값 / 하위 10퍼센타일" 은 **잡음이 아니라 다이내믹
레인지**를 잰다. 쉼을 잘라낸 깨끗한 녹음이 14.9dB 로 나왔다(실제로는 정상).

지금은 **대역별로 시간축 하위 분위수를 잡음 바닥으로** 본다(`Web/app.py` 의
`_quality()`). 발화 중에도 정상 잡음은 계속 깔리므로 쉼이 없어도 추정된다.
쉼을 잘라낸 녹음이 46dB 로 바로잡혔다.

### 음원 분리(Demucs)는 답이 아니었다 — 시도했고 기각

배경 음악이 비정상 신호라 지표에 안 잡히니, 걷어내고 재면 되겠다고 보고
`demucs 4.1.0` (htdemucs, two-stems=vocals) 로 시험했다. 15초 슬라이스 5개를
분리 전/후로 각각 3회씩 합성해 비교했다.

| 소스 | 루프 전→후 | 고역 전→후 |
|---|---|---|
| A 깨끗한 녹음 | 0 → **2** | 0.087 → 0.068 |
| B 목소리+노래 | 0 → 0 | 0.024 → 0.032 |
| C 유튜브1 | 1 → 1 | 0.093 → 0.059 |
| D 유튜브2 | 0 → 0 | 0.124 → **0.204** |
| E 교육녹음 | 2 → **0** | 0.093 → **0.241** |

**이미 깨끗한 A 가 망가졌다**(루프 0→2). E 는 루프가 사라졌지만 아티팩트가 세 배가
되고 한 번은 0.2초로 잘렸다. **무조건 적용하면 손해다.**

분리 자체는 잘 된다(측정 SNR 30.6 → 59.9dB). 문제는 그게 합성 품질로 이어지지
않는다는 것이다. 분리 산물 특유의 아티팩트를 모델이 그대로 따라 만드는 것으로 보이나
확인하지 못했다.

**주의 — 회차 간 편차가 크다.** 온도 1.2 샘플링이라 같은 참조·같은 질문에도 길이가
크게 흔들린다. 단일 소스 단발 측정에서 "0.121 → 0.037" 을 얻어 효과가 있다고
보고했는데, 다섯 소스로 늘리니 재현되지 않았다(같은 유튜브 소스가 0.093 → 0.059).
**참조 실험은 소스 3개 이상 · 회차 3회 이상으로 할 것.**

### 남은 한계 — 지표가 실제 실패를 다 잡지 못한다

| 참조 | 옛 지표 | 새 지표 | 실제 |
|---|---|---|---|
| 원본 깨끗 | 57.9 | 72.1 | 정상 |
| 쉼 제거(깨끗) | 14.9 | 46.0 | 정상 |
| 잡음 26dB | 26.0 | 24.5 | 정상 |
| 잡음 16dB | 16.0 | 17.5 | 루프 |
| **실제 녹화본(mp4)** | 16.3 | **31.2** | **루프·지지직** |

새 지표로도 mp4 는 31dB 로 통과하면서 실패한다. **대역별 하위 분위수는 정상
잡음을 가정하는데, 배경 음악과 다른 목소리는 비정상 신호**라서 바닥 추정에
안 잡힌다. 실제 가정용 영상·방송 녹화가 정확히 이 경우다.

**그래서 현재 경고는 "확실히 나쁜 것"만 거른다(25dB 미만).** 통과했다고 안전하지
않다.

### 6.5 지지직 — 여덟 가지를 시험해 하나만 남았다 (2026-08-01)

정답표는 **사용자 청취**다. 조건마다 5회씩 생성해 들었고, 6개 조건은 블라인드로도
확인했다(6/6 일치). `good` 계열 10/10 지지직 없음, `bad`(유튜버 녹음) 계열 40/40 있음.

| 대상 | 시도 | 결과 |
|---|---|---|
| 참조 | 저역통과 6k / 7k | **실패** — 지지직 그대로 + 먹먹함·음량저하 |
| 참조 | 잡음 제거(스펙트럼 게이팅) 35→59dB | **악화** |
| 참조 | 저레벨 16bit + MP3 128k 열화 | **재현 안 됨** — 깨끗한 참조는 그래도 깨끗 |
| 참조 | 문장 끝에서 자르기 | **실패** |
| 참조 | **장기 평균 스펙트럼 교환** | **부분 성공 — 유일하게 효과** |
| 생성 | RAS 끄기 | 변화 없음 |
| 생성 | `temperature` 1.2 → 0.8 | 변화 없음 |
| 생성 | `top_k` 20 → 5 | 변화 없음 |

**대역 분포는 양방향으로 확인됐다.**

| 방향 | 참조 | 결과 |
|---|---|---|
| bad → good 스펙트럼 | 지저분함 | 지지직 **크게 좋아짐** |
| good → bad 스펙트럼 | **깨끗함**(청취 확인) | 지지직 **생김** |

만드는 쪽에서 재료가 깨끗했다는 게 핵심이다 — 가공이 만든 잡음이 아니라 모델이
그 스펙트럼을 받고 망가진 것이다. 두 참조의 차이는 **0~300Hz 가 70.3% 대 5.8%** 다.

용량-반응(bad 를 good 쪽으로 부분 보정):

| 보정 | 참조 0~300Hz | 출력 지지직 지표 |
|---|---|---|
| 0% | 5.8% | 2.34 |
| 25% | 12.1% | 1.80 |
| 50% | 21.5% | 0.56 |
| 75% | 33.3% | 0.21 |
| 100% | 47.2% | 0.16 |

**그래도 완치는 아니다.** 75% 보정본을 들으면 지지직이 남아 있고 **목소리 떨림**이
새로 생긴다. 스펙트럼을 건드린 세 시도(저역통과·잡음제거·대역보정)는 전부 새 결함을
만들었고, 스펙트럼을 안 건드린 열화(코덱·레벨)만 멀쩡했다. **모델은 가공된 참조에
민감하다.**

#### 목소리도 마이크 거리도 아니다 — 같은 화자로 교란을 풀었다

"유튜버 녹음이라서"인지 "그 목소리라서"인지 갈리지 않아서, **같은 사람이 같은
장비로** 조건만 바꿔 네 번 녹음했다. 대사도 기존 `good.wav` 와 같은 문장으로 고정했다.

| 참조 | 0~300Hz | 1~4k | 지지직 지표 | 청취 |
|---|---|---|---|---|
| 평소 목소리, 가까이 | 82.9% | 1.4% | 0.08~0.20 | 없음 |
| 방송톤, 가까이 | 58.6% | 7.7% | 0.14~0.57 | 없음 |
| 평소 목소리, 40~50cm | 74.7% | 3.9% | 0.02~0.06 | 없음 |
| 높은 목소리, 가까이 | 61.8% | 5.3% | 0.27~0.78 | 없음 |
| **유튜버 녹음** | **5.8%** | **46.1%** | 1.94~3.88 | **심함** |

**네 조건 모두 깨끗하다.** 그리고 더 중요한 것 — **사람이 목소리와 마이크 거리로
만들 수 있는 저역 범위는 58.6% 까지**다. 유튜버 녹음의 5.8% 는 그 열 배 밖이다.
방송용 후처리(하이패스 + 프레즌스 부스트)로만 나오는 값이다.

그래서 결론은 이렇게 좁혀진다 — **모델이 감당 못 하는 것은 "가공된 스펙트럼"이지
사람 목소리의 다양성이 아니다.** 음높이·톤·마이크 거리는 안전하다.

**원인 성질은 여전히 미특정이다.** 대역 분포가 관여하는 것은 양방향으로 확실하지만,
되돌려도 완치가 안 되고 떨림이 따라온다. 실용적 답은 **"직접 녹음을 받을 것"** 이다.

#### 지지직 측정 지표 — 쓸 수 있는 조건이 있다

출력의 **6kHz 이상 에너지 비율(%)**. 청취와 잘 맞는다: good 0.07~0.25 / bad
1.94~3.88 / 잡음제거 2.44~7.24 / good을bad스펙트럼으로 6.21~10.06. 심각도 순서까지
맞는다.

**단, 참조를 스펙트럼 가공한 조건에는 무효다.** 저역통과(0.23)와 대역보정 75%(0.21)가
good 수준으로 나왔지만 실제로는 지지직이 들렸다. 출력의 그 대역은 참조의 그 대역을
따라 움직이므로, **측정 대상을 손댄 셈**이 된다. 원본 참조끼리 비교할 때만 쓸 것.

탈락한 후보: 거칠기(30~300Hz 진폭 변조 — 순서가 반대로 나옴), 대역 4~6k/1~4k 비,
고역 평탄도, 바닥 흔들림(잡음이 아니라 **쉼**을 재고 있었다).

#### RAS 재추첨은 필터를 건너뛴다 (별개의 실제 결함)

지지직의 원인은 아니지만 코드상 분명한 문제라 적어둔다. `make_audio_code_sampler`
안에서 정상 경로는 `processed_logits`(temperature·top_k·top_p 적용)로 뽑는데,
RAS 가 발동하면 **원본 `logits`** 를 넘긴다:

```python
sampled_ids = apply_repetition_aware_sampling(..., logits=logits, ...)
#   내부:  probs = F.softmax(logits[b], ...);  multinomial(probs, 1)
```

`top_k=20` 이 사라져 코드북 전체에서 뽑고, **첫 번째 코드 그룹만** 바뀌므로 나머지
15개 그룹과 어긋난다. 고치려면 `logits=processed_logits` 한 단어. 다만 RAS 를 꺼도
지지직은 그대로였으므로 **이건 지지직과 별개의 개선 항목**이다.

### 6.6 "늘어진다"의 절반은 반복이 아니라 무음이다 (2026-08-01)

깨끗한 참조(`good`)로 `/talk` 5회를 재고 사용자 청취와 대조한 결과.

| 회차 | 총 길이 | 말 끝 | 꼬리 | 판정 |
|---|---|---|---|---|
| 1 | 16.0초(상한) | 7.6초 | **8.4초 무음** | 꼬리김 |
| 2 | 16.0초(상한) | — | 6.3초 쉬었다 **재시작** | 반복 |
| 3 | 13.0초 | 9.8초 | 3.2초 무음 | 꼬리김 |
| 4 | 11.8초 | 11.3초 | 0.5초 | **내부 쉼 5개 2.9초** |
| 5 | 16.0초(상한) | 9.1초 | 6.9초 무음 | 꼬리김 |

**5회 중 정상이 없다.** 그런데 **말하는 속도 자체는 0.103~0.128초/글자로 매우
일정**하다. 모델이 느리게 말하는 게 아니라 **쉼이 아무 데나 들어간다.** "속도·말투가
AI 틱하다"는 체감의 정체가 이것이다.

문장을 다 말하고도 생성이 안 멈추고 상한(200프레임=16초)까지 무음을 만든다.
**상한이 피해를 막고 있는 것**이고, 반이중 구조라 그 무음이 다 재생될 때까지
사용자는 말을 못 한다. 꼬리를 잘라내기만 해도 체감이 크게 달라진다.

`task_params` 에 **`continuation_silence_frames: 2`** 가 있다. 이름으로 보아 관련이
있어 보이나 아직 안 건드렸다.

#### 원인은 참조의 쉼 비율이다 — 코드를 안 고치고 해결된다

같은 화자가 같은 장비로 녹음한 참조 네 개로 확인했다. **참조가 얼마나 쉬느냐가
출력의 꼬리를 결정한다.**

| 참조 | 참조 쉼 비율 | 출력 꼬리 무음 | 쉼 판정 |
|---|---|---|---|
| `good.wav` (기존) | **27.6%** | **0.0~8.4초** | **0/5** |
| 새 녹음 — 평소, 가까이 | 19% | 0.2~0.6초 | 5/5 |
| 새 녹음 — 방송톤 | 15% | 0.4~0.5초 | 5/5 |
| 새 녹음 — 높은 목소리 | 12% | 0.5~1.0초 | 5/5 |
| 새 녹음 — 평소, 멀리 | 7% | 0.1~0.6초 | 4/5 |

**20회 중 19회 정상.** 기존 `good.wav` 는 5회 중 0회였다. 유튜버 녹음(쉼 9%)도
꼬리는 0.3~1.6초로 좋았다 — 지지직과 꼬리는 서로 다른 축이다.

**등록 도구 안내 문구로 해결된다:**

> 10~15초 동안 **끊지 말고 이어서** 말해 주세요. 문장 사이에 뜸을 들이면
> 합성된 목소리도 중간에 멈춥니다.

이전에 "쉬는 구간은 조건이 아니다"(§6 위쪽)라고 적은 것과 모순되지 않는다. 그건
**쉼이 0% 여도 정상 동작한다**는 반증이었다. 이번 것은 **쉼이 많으면 출력도 많이
쉰다**는 것으로, 방향이 반대인 별개의 발견이다.

#### 쉼 계측기 — 청취와 5/5 일치, 블라인드에서도 재현

전대역 RMS 로 재면 **두 번 틀린다.** ① 출력이 50~150Hz 에 몰려 있어 말이 끝난 뒤에도
RMS 가 절반 남는다 → 무음을 "소리 있음"으로 본다. ② 끝에 말이 다시 시작하면
"소리끝=총길이"가 되어 중간 6초 공백이 지워진다.

**300~4000Hz 로 걸러서 0.1초 창으로** 재면 청취와 맞는다. 재는 것:
말 끝 · 꼬리 무음 · 내부 쉼 개수/합 · 무음 후 재시작 · **발화속도**(쉼 뺀 것) ·
**체감속도**(쉼 포함).

사람이 "느리다"고 느끼는 것은 **체감속도** 쪽이다. 발화속도가 같은데도(0.118 대
0.119) 체감이 갈린 사례가 있었고(0.145 대 0.176), 블라인드에서 사용자가 그 파일만
"단어 사이 쉼이 있다"고 짚었다.

구현은 `실험결과.md` 옆 `analyze.py`(바탕화면 작업 폴더). 제품에 넣을 때 옮길 것.

## 8. 출력 품질 실측

| 설정 | 고역/음성대역 | 분량 |
|---|---|---|

**지지직의 출처는 참조 음성이다.** 같은 세션·같은 참조에서 `CONT=0` 으로 껐는데도
고역 비율이 0.120 / 0.095 로 그대로였다. 모드를 바꾸면 출력은 달라지지만 잡음은 남는다.

위 표의 `CONT=0` 행(0.014~0.040)은 **다른 세션·다른 참조**에서 잰 값이라 위 행들과
비교할 수 없다. 이걸로 "continuation 특유의 문제"라고 판단했던 것은 틀렸다.
비교 실험은 반드시 같은 참조에서 할 것.

RAS 도, 스트리밍 패치도 원인이 아니다(각각 끄고·격자 검정으로 확인).

### 대역별 에너지 분포

```

mp4 033421          93.7%   5.6%   0.5%   0.1%   0.1%
mp4 033757          52.9%  42.9%   3.5%   0.3%   0.5%
```

12.5Hz 프레임 코덱의 한계로 추정하나 확인하지 못했다. **파볼 지점이다.**

## 10. 틀렸던 판단 (다시 밟지 말 것)

오늘 시간을 가장 많이 쓴 건 코드가 아니라 **원인을 잘못 짚은 것**이었다.

| 판단 | 실제 |
|---|---|
| "참조가 6.3초라 짧아서 깨진다" | 음량 문제였다. `tts()` 기준 2~8초는 오히려 적정 |
| "참조 소재가 나쁘다(배경음)" | 노래 틀고 녹음한 것도 통과했다. SNR·쉼이 기준 |
| "전사가 `피카츄 라이` 로 나오니 소재가 엉망" | 10배 증폭하니 완벽히 알아들었다 |
| "연속 구간이 조각보다 낫다" | 쉼이 긴 13.7초 연속 구간이 더 나빴다 |
| "스트리밍 패치가 지지직 원인" | 격자와 무관. 무죄 |
| "RAS 가 지지직 원인" | 끄니 오히려 늘었다 |
| "저역 편중이 먹먹함의 원인" | 잘 된 참조가 가장 저역 편중이었다 |
| "지지직은 continuation 특유" | 참조 탓. CONT=0 으로 꺼도 그대로였다 |
| "Demucs 로 지지직이 해결된다" | 단발 측정이었다. 5개 소스로 늘리니 재현 안 됨 |
| "조각을 이어붙이면 안 된다" | 조각 3개짜리 12초 참조도 정상 동작했다. 문제는 **틈 없이** 붙인 것 |

**계측기를 먼저 검증할 것.** `/tts` 값을 믿고 두 번 잘못 판단했다.

**비교 실험은 한 번에 하나만 바꿀 것.** `CONT` 를 비교하면서 세션(참조)까지 바뀌어
있었다. 참조가 지배적 변수인 상황에서 모드 차이를 읽으려 한 셈이라 결론이 뒤집혔다.

## 11. 측정 방법 (재현용)

```python
# 음량: 0.1초 창 RMS 의 최댓값
w = 2400; n = len(y)//w
r = np.sqrt((y[:n*w].reshape(n, w)**2).mean(axis=1))
level = r.max()

# SNR: 최대 / 하위 10퍼센타일
snr_db = 20*np.log10(r.max() / np.percentile(r, 10))

# 쉬는 구간 비율
quiet = (r < r.max()*0.05).mean()

# 고역 아티팩트: 6kHz 이상 / 음성대역(200~3000Hz)
S = np.abs(np.fft.rfft(y[:sr*5])); f = np.fft.rfftfreq(sr*5, 1/sr)
ratio = S[f>6000].mean() / S[(f>200)&(f<3000)].mean()

# 프레임 경계 아티팩트 검정: 급변 지점이 (chunk/12.5)초 격자에 몰리는지
d = np.abs(np.diff(y)); idx = np.where(d > d.mean()+6*d.std())[0]
per = 8/12.5
ph = (idx/sr) % per
# 무작위면 평균거리 ≈ per/4
```

전사는 서버 `/stt` 로 확인하는 게 가장 정확하다 — 실제로 모델이 무엇을 듣는지가 중요하다.

## 12. 학습 가능성 — 결론: 지원된다

공개된 게 "가중치뿐"이라는 전제는 **틀렸다.** `modeling_raon.py` 에 학습 경로가
살아 있다. 확인한 근거:

```
8918:  ) -> RaonModelOutput:
8919:      """Run training forward pass: embed inputs, run text model,
           compute text and audio loss."""          ← 독스트링이 명시
5652:  # ── from utils/loss.py ──                    ← 학습 손실 모듈을 인라인
5666:  Mixin providing loss computation methods for RaonModel
5670:  audio_loss_weight, text_loss_weight, epad_loss_weight, code_predictor_grad_scale
5680:  def unreduced_causal_lm_loss(logits, labels)
5696:  def _compute_audio_loss(...)                   ← 코드 그룹별 교차 엔트로피
2373:  self.gradient_checkpointing
 397:  손실 가중치를 환경변수로 조절 가능
5872:  "keeps DDP from hanging"                       ← 분산 학습 인지 코드
```

`code_predictor_grad_scale` 이 있다는 건 RCP 로 흘러드는 그래디언트까지 설계에
넣었다는 뜻이고, 손실 가중치를 환경변수로 뺀 건 **남이 튜닝할 것을 상정**한 것이다.

### `forward()` 시그니처에서 중요한 인자

| 인자 | 왜 중요한가 |
|---|---|
| `labels` | 학습 라벨. 손실이 여기서 나온다 |
| **`use_speaker_embedding` / `speaker_embeds`** | **미리 계산한 화자 임베딩을 직접 주입**한다. ECAPA 를 우회하는 문 |
| `audio_output_codes` / `_mask` | 코덱 타깃을 미리 계산해 넘긴다. 학습 중 코덱 forward 불필요 |
| `speaker_encoder_audio` | 화자 참조가 `audio_output`(프리필)과 **별도 인자**다 |
| `audio_output_segments` | 다중 구간 학습 지원 |

**`speaker_embeds` 가 Prosody Encoder 의 진입점이다.** 모델을 개조해 인코더를 넣는
게 아니라, **이 슬롯에 들어갈 벡터를 만드는 모듈**을 학습하면 된다. 구조 수술이
필요 없다. 추가로 `is_pretrained_speaker_encoder` 플래그(5673, 5877)가 있어
"화자 인코더가 동결이냐 학습 대상이냐"가 이미 매개변수화돼 있다.

### 화자 인코더의 실체

```
1157:  a frozen SpeechBrain ECAPA model, and projects the pretrained embedding to ...
1255:  Extract frozen ECAPA embeddings from 16kHz audio.
```

**동결 ECAPA-TDNN, 임베딩 하나를 투영**해 `SPEAKER_EMBEDDING_PLACEHOLDER` 자리에
넣는다. 시간 축이 없으므로 **프로소디는 실릴 자리가 없다.** 억양을 얻으려면
continuation 이 필요한 이유가 이것이다.

기술 보고서의 "2~8초 무작위 청크"는 ECAPA 에 먹일 구간을 고르는 이야기이지
시퀀스로 삽입한다는 뜻이 아니다.

### 없는 것

데이터셋·콜레이터, 옵티마이저·스케줄러, 분산 실행기, 체크포인트 저장.
**전부 표준 부품이다.** 다중 코드북 손실을 역설계하는 것에 비하면 사소하다.

### 제약

- **VRAM** — 추론이 `RAON_MEM_FRACTION=0.60` 으로 40GB 를 쓰니 카드는 약 67GB 이상,
  80GB 급으로 보인다. LoRA + gradient checkpointing 에 짧은 시퀀스면 한 장으로
  가능한 범위지만 여유가 크지 않다.
- **MoE** — 21B 중 활성 3.5B. 학습 시 라우팅·부하 균형이 얽히고 일부 전문가만
  갱신되며 불안정해질 수 있다. 밀집 모델 LoRA보다 까다롭다.
- **라이선스** — CC BY-NC 4.0. 파생 모델도 비상업 제약을 받는다.

### 권장 순서

**1단계 — 강건성 LoRA.** 깨끗한 녹음을 열화시켜(잡음 추가·무음 제거·대역 제한)
입력으로 쓰고 정상 출력을 정답으로 둔다. 페어를 무한히 합성할 수 있고, 성공 판정
지표가 이미 있다(§11 측정 코드, "0.13~0.20초/글자" 정상 범위, 고역 비율 0.04).
목표가 명확하고 실패해도 원인이 보인다.

**2단계 — Prosody Encoder.** 1단계로 학습 파이프라인을 검증한 뒤에 간다.
첫 시도에 구조 변경까지 겹치면 실패했을 때 학습 문제인지 설계 문제인지 못 가린다.

## 13. 다음에 파볼 것

**먹먹함의 정체.** 모든 출력이 6kHz 위로 비어 있다. Mimi 코덱의 대역폭 한계인지,
디코딩 설정 문제인지, RVQ 코드 그룹 수(16)와 관련 있는지 확인할 것.
`audio_tokenizer.decode` 주변과 코덱 설정이 출발점.

**`/tts` 이상.** 같은 `synth()` 인데 `/talk` 과 결과가 다르다. `generate()` 에 들어가는
입력을 양쪽에서 덤프해 비교하면 갈릴 것이다.

**`continuation_silence_frames`.** 현재 2. 생성 초반 프레임을 무음으로 강제하는 값인데,
쉼이 없는 참조 문제와 관련 있을 수 있다. 값을 키우면 참조 조건이 완화되는지 볼 만하다.

**참조 품질에 따른 자동 전환.** 등록 시점에 SNR·쉼을 이미 재고 있다. 기준을 넘으면
CONT=1, 미달이면 CONT=0 으로 세션마다 다르게 잡으면, 좋은 음성은 억양까지 얻고
나쁜 음성도 지지직 없이 나온다. 지금은 전부 아니면 전무라 나쁜 참조 하나 때문에
전체를 포기하거나 감수해야 한다.

**답변 길이·되묻기.** `BASE_RULES` 가 "한 문장 40자", "직전과 같은 문장 반복 금지",
"되묻기만 하지 말 것"을 지시하는데 지켜지지 않는다. 실제로 "아, 그렇구나"로 네 번
연속 시작한 적이 있다. `RAON_ANSWER_TOKENS`(현재 200) 조정이 가장 확실하나 문장이
잘릴 수 있다. 오디오보다 대화 품질에 더 크게 작용한다.
