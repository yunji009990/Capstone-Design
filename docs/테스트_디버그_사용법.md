# 테스트 디버그 사용법

기준일: 2026-09-16. 대상은 `AI_Response_Test`·`Scene_2` 음성 대화 테스트다.

체험 중 **어디서 멈췄는지, 어디서 소리가 끊겼는지**를 로그로 가리기 위한 흐름을 적는다.
말끝 음절 문제의 원인 확정이나 오디오 품질 개선은 이 문서의 범위가 아니다.

## 1. 한눈에 보는 흐름

**사용자가 반드시 할 일은 "평소대로 테스트하고 알려주기" 하나뿐이다.**
진단 로그는 체험을 시작하면 자동으로 쌓이고, Codex 가 그 자동 로그를 직접 열어 분석한다.
로그 파일을 열어 볼 필요도, 어디에 올릴 필요도 없다.

| 순서 | 누가 | 무엇을 |
|---|---|---|
| 1 | 사용자 | 평소대로 테스트한다. 진단 로그는 자동으로 쌓인다. |
| 2 | 사용자 | 끝나고 "언제 어떤 게 이상했다"고 알려준다. |
| 3 | Codex | 자동 로그를 분석하고, 필요하면 `--ssh raon` 으로 서버 쪽 같은 trace 를 합친다. |

아래 두 메뉴는 **선택 편의 기능**이다. 안 써도 분석은 된다.

| 메뉴 | 언제 쓰면 좋은가 |
|---|---|
| `Tools/Dialogue/Diagnostics/Mark issue` | 이상한 순간에 눌러 두면 그 지점을 찾기 쉽다. |
| `Tools/Dialogue/Diagnostics/Create local report` | 사용자가 직접 요약을 먼저 보고 싶을 때. |

## 2. 사용자 쪽 (Unity)

### 2.1 자동 기록

체험을 시작하면 `<프로젝트>/.dialogue-work/logs/dialogue-<시각>-<trace>.jsonl` 이 생긴다.
`trace` 는 이번 실행에만 쓰는 가명 ID다. 실제 세션 ID 가 아니다.
파일에는 사건 이름·정해진 원인 코드·숫자만 들어간다.
발화 원문, 답변 원문, 인물 정보, 경로, 토큰, PCM 은 들어가지 않는다.

기록에 실패해도 대화는 끊기지 않는다. 대신 그 구간은 "관측 없음"이 되므로
보고서에서 0 이 아니라 `—` 로 나온다.

### 2.2 Mark issue (선택)

소리가 끊기거나 멈춘 것 같은 순간에 누른다. 지금 진행 중인 응답의 관측값과 순번만 남긴다.
응답을 멈추거나 마이크를 끄지 않으므로 체험을 이어서 하면 된다.
여러 번 눌러도 된다. 보고서에 순번과 시각이 모두 나온다.

안 눌러도 된다. 다만 "3분쯤에 끊겼다"보다 마커 순번이 지점을 훨씬 빨리 좁힌다.
누르지 않았으면 말로 알려준 시점 주변을 Codex 가 로그에서 찾는다.

### 2.3 Create local report (선택)

체험을 **끝낸 뒤** 누른다. 가장 최근 로그 한 개로 로컬 보고서를 만든다.
Codex 가 같은 분석을 자동 로그로 직접 할 수 있으므로, 사용자가 먼저 요약을 보고 싶을 때만 쓴다.
이 메뉴는 SSH 를 쓰지 않는다. 그래서 서버 쪽 칸은 "서버 미확인"으로 비어 있다.

서버 로그가 없어도 Unity 로그만으로 알 수 있는 것이 있다. 턴별 **모드**(`response.started` 의
경로), 응답 수명(`started → paused → resumed → done/cancelled`), 재생 **중단 사유**,
그리고 파일로 주입한 오디오인지(`주입` 칸)다. 서버가 보고한 초 단위 값도 Unity 가 중계해
받아 둔 것이 있으면 나온다.
창이 뜨지 않고 백그라운드로 돌며, 끝나면 Console 에 결과 경로 한 줄이 남는다.
실패하면 실패했다는 사실만 알린다. 로그 원문을 Console 에 쏟지 않는다.

체험이 아직 끝나지 않은 상태로 만들면 보고서에 `experience_ongoing` 신호가 붙는다.
그 보고서를 "정상 완료"로 읽지 않는다.

### 2.4 Open log folder (선택)

로그 폴더를 연다. 파일을 직접 읽거나 어딘가에 올릴 일은 없다. 경로를 확인할 때만 쓴다.

## 3. Codex 쪽 (명령줄)

```
python tools/analyze_dialogue_trace.py                                  # 최신 Unity 로그만
python tools/analyze_dialogue_trace.py --ssh raon                       # 서버 로그까지 합쳐서
python tools/analyze_dialogue_trace.py --unity-log <경로> --server-log <경로>
```

| 옵션 | 뜻 |
|---|---|
| `--latest` | 가장 최근 Unity 진단 로그를 쓴다. 기본값이라 보통 적지 않는다. |
| `--unity-log <경로>` | 특정 JSONL 을 지정한다. `--latest` 와 같이 쓸 수 없다. |
| `--server-log <경로>` | 이미 받아 둔 서버 진단 로그를 쓴다. `--ssh` 와 같이 쓸 수 없다. |
| `--ssh <별칭>` | **이 옵션을 적었을 때만** SSH 로 접속한다. 별칭은 `raon` 같은 이름만 받는다. |
| `--output <디렉터리>` | 결과 위치. 이미 있는 디렉터리는 거부한다. |

기본 결과 위치는 저장소 기준 `.dialogue-work/reports/<UTC 시각>-<trace>/` 이고
그 안에 `report.md` 와 `report.json` 이 생긴다. 기존 결과는 덮어쓰지 않는다.

성공하면 stdout 마지막 줄이 `report.md` 절대 경로 한 줄이다. Unity 메뉴가 이 줄을 읽는다.
실패하면 stderr 에 아래 코드 하나만 나온다. 로그 내용이나 원격 오류 문구는 나오지 않는다.

| 코드 | 뜻 |
|---|---|
| `no_unity_log` | Unity 진단 로그를 찾지 못했다. |
| `unity_log_unreadable` | 파일은 있으나 읽지 못했다. |
| `invalid_trace` | 로그에서 유효한 trace(12 또는 32자리 16진수)를 찾지 못했다. |
| `output_exists` | 결과 디렉터리가 이미 있다. 다른 `--output` 을 준다. |
| `output_unwritable` | 결과를 쓰지 못했다. |
| `ssh_alias_rejected` | 별칭 형식이 아니다. 옵션처럼 보이는 값은 접속 전에 막는다. |
| `bad_arguments` | 같이 쓸 수 없는 옵션을 함께 줬다. |

### 3.1 `--ssh` 가 실제로 하는 일

`ssh -T -o BatchMode=yes … <별칭> python3 - <trace>` 한 번이다.
고정된 파이썬 스크립트를 stdin 으로 넣고, 원격에서
`~/capstone-server/logs/dialogue-diagnostics.log` 와 회전본 5개까지 훑어
**선택한 trace 가 들어 있는 줄만** 되돌려 받는다. 크기·시간 상한이 있다.

- 다른 세션 줄이나 원문 로그 파일은 가져오지 않는다.
- 키·비밀번호를 조회하지 않고, 비밀번호를 묻지도 않는다(BatchMode).
- 서버 프로세스를 건드리지 않는다. 읽기만 한다.
- 접속에 실패하면 보고서는 그대로 만들되 서버 칸이 "미확인"이 된다.
  원격 stderr 본문은 보고서에도 화면에도 옮기지 않고 종료 코드만 남긴다.

## 4. 보고서 읽는 법

### 4.1 `—` 와 0 은 다르다

`—` 또는 `null` 은 **기록이 없다**는 뜻이다. 0 이나 정상이 아니다.
서버 로그를 확인하지 않은 보고서에서 서버 칸이 비어 있는 것은 당연하다.

### 4.2 턴 상태

| 표시 | 뜻 |
|---|---|
| 완료 | Unity `playback.completed`(complete=1) 와 서버 `turn.done` 이 **둘 다** 있다. |
| 서버완료·재생미확인 | 서버는 응답을 끝냈는데 재생 완료 기록이 없다. `turn.done` 만으로 재생 완료라고 읽지 않는다. |
| 재생완료·서버미확인 | 재생은 끝났는데 서버 기록이 없다. 보통 서버 로그를 안 봤을 때다. |
| 취소 | 사용자 끼어들기나 새 발화로 끊긴 정상 경로일 수 있다. |
| 재생 중단 | 완료가 아니라 중단으로 끝났다. 사유 코드를 같이 본다. |
| 미완료 또는 관측 부족 | 오류 확정이 아니다. 기록이 모자라다는 뜻이다. |

### 4.3 시간 값

- Unity `ms` 는 체험 시작 후, 서버 `uptime_s` 는 연결 시작 후 단조시간이다.
- 두 값은 **다른 기기의 시계**다. 빼서 네트워크 지연이라고 말하지 않는다.
- 서버가 보고한 `first_audio_sec`·`total_sec` 은 **생성 시각**이지 실제로 들린 시간이 아니다.
- 첫 리액션 시간과 본답변 첫 PCM 시간은 별도 칸이다. 섞어 보지 않는다.
- `첫텍스트ms(respond)`(`first_text_ms`)는 **respond 시작 기준**이다. 일반 마이크 경로는
  후보 검증 STT 가 respond 전에 끝나므로 STT 는 따로 잰다. 다만 예외적으로 respond 안에서
  전사하는 경우에는 그 시간이 이 값에 포함될 수 있다.
- `LLM호출ms`(`llm_first_ms`)는 **LLM 호출 기준**이다. 위 값과 기준점이 다르다.
- 본답변 TTS 와 리액션 TTS 는 칸이 따로다. 리액션이 먼저 나왔다고 본답변이 빨랐던 게 아니다.
  `tts_total_ms`·`tts_max_gap_ms` 에는 **보류 대기와 전송 대기가 포함될 수 있다**. 합성만의 시간이 아니다.
- `input.started` 는 Unity 가 서버의 `speech.started` 를 받은 시점이다.
  마이크 raw VAD 가 말을 감지한 시점이 아니므로, 이 값으로 VAD 반응 속도를 재지 않는다.

### 4.3.1 STT 칸이 "미확인" 일 때

STT 시간은 서버의 `input.assigned` 로 **채택된 후보와 응답 턴이 이어졌을 때만** 그 턴에 붙는다.
거절된 잡음 후보와 채택 후보가 한 턴 앞에 여러 개 섞이기 때문이다.
그 줄이 없는 구버전(v3) 로그에서는 턴별 STT 가 `미확인` 으로 나오고,
잰 값들은 `## 3. 입력 판정` 의 "턴에 붙이지 못한 STT" 에만 모인다. 0 이라는 뜻이 아니다.

### 4.4 샘플 수

서버 송신 샘플과 Unity 수신 샘플 대조는 **정상 `playback.completed` 와 서버 `turn.done` 이
둘 다 있을 때만** 한다. 그 밖에는 "대조 불가(관측 부족)"이고, 이를 손실로 읽지 않는다.

언더런은 `playback.completed`·`playback.stopped` 가 남긴 **응답별 델타**만 그 턴의 값이다.
주기 표본만 있는 구버전 로그에서는 `(체험누적)` 이 붙는다. 이 값은 체험 내내 쌓인 수라
해당 턴의 문제로 읽지 않는다. (`received`·`consumed` 는 렌더러가 응답마다 0 으로 되돌리므로
주기 표본에서도 응답 단위 값이다.)

### 4.4.1 구버전(v1) 로그에서 빈 칸

v1 로그에는 `audio.first_received`·`playback.first_render` 사건 자체가 없다.
그래서 "첫PCM수신" 칸이 비는데, 이것은 **PCM 을 못 받았다는 뜻이 아니라 그 종류의 사건을
관측하지 못했다는 뜻**이다. 주기 표본의 수신 샘플이 0 보다 크면 보고서가
`first_audio_not_recorded` 신호로 그 사실을 적는다. `no_audio_received` 와 구별해서 읽는다.

### 4.4.2 부분 기록

머리말의 `부분 기록: 예` 는 **빠진 기록이 있다**는 뜻이다. 다음 중 하나라도 있으면 붙는다.

- `trace.limit`: Unity 로거가 파일 상한에 닿아 그 뒤를 남기지 못했다.
- `reader_limit`: 이 도구의 파일 상한(16MB)에 닿아 뒤를 읽지 않았다.
- 해석 실패 줄, 한 줄 상한(64KB)을 넘어 건너뛴 줄, 모르는 버전 줄.

한 줄이 64KB 를 넘으면 **자르지 않고 통째로 건너뛰고** 그 사실만 센다. 잘린 조각을 정상 줄처럼
읽는 일이 없게 하기 위해서다. 같은 이유로 SSH 수집기도 긴 줄을 자르지 않는다. 서버 v4 줄은
600자를 넘을 수 있고 뒤쪽에 timing 이 붙기 때문이다.

이 표시는 "그 뒤에 사건이 없었다"는 뜻이 아니다. 로그는 읽은 시점의 스냅샷이라,
체험이 진행 중이면 파일에 뒤가 더 붙는다. 마지막 줄에 개행이 없는 것도 쓰는 중이라는
표시일 뿐 그 자체로 결함이 아니다.

### 4.4.3 모르는 버전·모르는 코드

허용 목록에 없는 사건은 버리고, 없는 원인 코드는 `other` 로 접고, 모르는 `v` 값은
**보고서에 옮기지 않고** 건수만 센다(`미지 버전` 칸). 그 숫자가 0 이 아니면
로그가 다른 버전에서 왔거나 producer 목록과 이 도구의 목록이 어긋난 것이다.

### 4.4.4 report.json 의 `events`

`report.md` 는 요약이다. 표에 넣지 않은 수치는 `report.json` 의 `events` 배열에 그대로 있다.
말끝(`tail_rms`·`tail_peak`·`tail_silence_ms`), 출력 장치(`output.state` 의 볼륨·음소거·포커스),
입력(`input.sample` 의 마이크 계수·레벨), 경계 누계(`expected_samples`·`received`) 따위다.
말끝 음절이나 장치·입력 원인을 나중에 좁힐 때 이 배열을 쓴다.

담기는 것은 파서를 통과한 허용 사건·코드·유한한 숫자뿐이다. 원문·미지 필드는 이미 버려진 뒤라
이 배열에도 없다. `periodic` 이 `true` 인 항목은 주기 표본이다. Unity 표본은 2초, 서버 heartbeat는 5초 간격이다.

`injected` 는 `1` 일 때만 파일 주입이다. `-1` 은 "해당 없음"이라 보고서에서 `—` 로 남는다.

### 4.5 신호

`## 5. 관측 신호` 는 **관측된 사실과 확인해 볼 영역**이다. 원인 확정이 아니다.
예를 들어 `underrun_observed` 는 "재생 중 언더런이 있었다"까지만 말하고,
수신 간격·재생 버퍼·메인 스레드 멈춤 중 무엇인지는 사람이 좁혀야 한다.

## 5. 이 도구가 하지 않는 것

- 제품 동작을 바꾸지 않는다. 읽기 전용이고 프로토콜·재생·VAD·취소 계약을 건드리지 않는다.
- `--ssh` 를 적지 않으면 네트워크에 나가지 않는다.
- 로그 원문·사용자 발화·모델 답변·세션 ID·키·경로를 보고서에 옮기지 않는다.
  허용 목록에 없는 사건은 버리고, 없는 원인 코드는 `other` 로 접은 뒤 건수만 적는다.
- 근본 원인을 자동으로 정하지 않는다.

## 6. 검사

```
python -m unittest discover -s tools/tests -p test_dialogue_trace_report.py
```

합성 로그로만 검사한다. 실제 체험 로그나 서버 파일은 읽지 않고 SSH 는 가짜 실행기로 대신한다.
검사 초점은 구현 재현이 아니라 **보고서를 잘못 읽게 만드는 경우**를 막는 것이다.
기록 없음을 0 으로 읽기, 서버 응답 종료를 재생 완료로 읽기, 체험 누적 카운터를 이번 턴 값으로 읽기,
거절된 후보의 STT 를 다음 턴에 떠넘기기, 관측이 모자란데 샘플 손실이라고 말하기 따위다.

`ProducerContractTests` 는 이 도구의 허용 목록이 실제 producer 의 목록을 모두 담는지 본다.
`DialogueTraceLog.cs` 의 `Events`/`Reasons`/`Names` 나 `dialogue_diagnostics.py` 의
`EVENTS`/`REASONS`/`NUMBERS` 가 늘어나면 이 검사와 도구의 목록도 함께 늘린다.
빠뜨리면 정상 기록이 `other` 로 접히거나 통째로 버려진다.

전체 영역 검사는 `python tools/check.py --area dialogue` 를 따른다.

이 단위 검사와 별개로, 실제 v1·v2 로그와 실제 서버 로그(`--ssh`)로 대조한 기록은
「현재 검증 상태」 표의 `unity-validation-report/`·`legacy-correlated-report/` 에 있다.

보고서를 읽을 때는 `## 1. 자료` 의 `미지 사건`·`미지 코드`·`미지 버전` 칸이 0 인지 먼저 본다.
0 이 아니면 producer 목록과 이 도구의 목록이 어긋난 것이므로, 숫자를 믿기 전에 목록부터 맞춘다.
