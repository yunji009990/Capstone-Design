# Qwen3-TTS 합성 도구

참조 음성 하나로 **아무 문장이나 그 목소리로 만든다.** 화자 분리도 LLM 도 대화도 없다.

제품 코드가 아니라 **모델을 직접 만져보는 도구**다. 제품(`Web/`)이 쓰는 것은 Raon 이고,
여기는 Qwen3-TTS 를 단독으로 확인하는 자리다.

## 실행

```bash
python TTSWeb/app.py
```

브라우저에서 `http://localhost:5002`. 스튜디오(5001)와 동시에 띄워도 된다.

## 모델에는 아무것도 하지 않았다

가중치·파인튜닝·`qwen_tts` 패키지·어댑터 코드 전부 그대로다. 이 폴더가 하는 일은
**이미 있는 엔진을 호출하는 것**뿐이고, 실제 추론은 `voice_clone_studio` 의 것을 탄다.

| 쓰는 것 | 어디 |
|---|---|
| 모델 | `Qwen/Qwen3-TTS-12Hz-1.7B-Base` (bfloat16, cuda:0) |
| 어댑터 | `engine/tts/adapters/qwen3tts/infer.py` + 그 전용 venv |
| 상주 워커 | `backend/workers/tts_worker.py`, `backend/warm.py` |
| 받아쓰기 | `backend/workers/stt_worker.py` (faster-whisper large-v3) |
| 글 정규화 | `engine/tts/pipeline/normalize_ko.py` |

경로는 환경변수로 바꾼다. `Web/app.py` 와 같은 이름을 본다.

```bash
set VCS_DIR=C:\...\voice_clone_studio
```

## 왜 Qwen3-TTS 인가

zero-shot 한국어 TTS 5종 벤치마크에서 종합 2위였는데 **메인으로 뽑혔다.**
근거는 `voice_clone_studio/docs/제거된_기능.md` (저장소 밖, `VCS_DIR` 아래).

| 순위 | 모델 | Score | SECS | CER | 실패율 |
|---|---|---|---|---|---|
| 1 | cosyvoice2 | 0.971 | 0.771 | 0.049 | 3.7% |
| 2 | **qwen3tts** | 0.912 | 0.723 | **0.044** | **0.0%** |
| 3 | chatterbox | 0.834 | 0.737 | 0.040 | 0.0% |
| 4 | f5tts_ko | 0.753 | 0.716 | 0.054 | 0.4% |
| 5 | gptsovits | 0.000 | 0.528 | 0.220 | 0.0% |

1위 cosyvoice2 는 참조의 **녹음 환경까지 복제**해 지지직이 낀다. 종합 1위인 것도
유사도 가중치(0.4) 때문이다. Qwen3-TTS 는 LLM 기반이라 목소리 정체성만 뽑아
참조가 지저분해도 출력이 깨끗하고, 발음 정확도 1위 · 실패율 0% 였다.

## 호출 규격

```python
model.generate_voice_clone(text=..., language="Korean", ref_audio=..., ref_text=...)
```

**`ref_text` 가 필수 입력이다.** 참조 음성에서 실제로 말한 문장을 넣어야 한다.
사람이 매번 받아적을 수 없으므로, 비워두면 whisper 웜 워커로 받아쓴다.
직접 적으면 whisper 는 아예 뜨지 않는다.

**참조는 24kHz 모노 16bit** 로 맞춘다(`preprocess_refs.py` 와 같은 규격). 무엇을 올리든
ffmpeg 로 변환한다. 벤치마크가 쓴 길이는 6~12초다.

### 모델 안에서 벌어지는 일

참조를 버리고 시작하지 않는다. **참조 코드를 앞에 이어붙여 함께 디코딩한 뒤 앞을 잘라낸다**
(`qwen3_tts_model.py:612-633`).

```
[참조 코드][생성 코드] → 통째로 디코딩 → cut = ref_len/total_len × 길이 → wav[cut:]
```

앞을 자르는 계산이므로 **끝과는 무관하다.** `max_new_tokens` 기본값은 2048 —
12Hz 기준 약 170초라 짧은 문장에서는 걸리지 않는다.

## 구조

```
브라우저 ─ POST /api/ref ─→ ffmpeg 24k 변환 → (ref_text 비었으면) whisper → refs/<id>/
        └ POST /api/synth ─→ normalize_ko → TTS 워커(소켓) → out/<id>.wav
```

무거운 일은 스레드로 돌리고 화면은 `/api/job/<id>` 를 폴링한다.

**웜 워커** — 모델을 1회 로드한 뒤 localhost 소켓으로 상주한다. 서버가 뜰 때 TTS 를
백그라운드로 예열하고, STT 는 필요할 때만 올린다. GPU 는 `GPU_LOCK` 으로 직렬화해
두 모델이 동시에 상주해도 연산이 겹치지 않는다. 앱이 내려갈 때 `atexit` 로 워커도 내린다 —
스튜디오처럼 이름으로 훑어 죽이지는 않는다(5001 이 띄운 워커까지 죽는다).

## 실측 (RTX 5060 Ti)

| | 시간 |
|---|---|
| TTS 워커 예열 (서버 시작 시 자동) | 8초 |
| STT 워커 예열 (참조 문장을 비웠을 때만) | 10초 |
| 참조 등록 — 12초 오디오, 변환 + 받아쓰기 | 약 14초 |
| 합성 — 24자 → 3초대 wav | 약 11초 |

생성 속도는 **0.113~0.153초/자**(24자 문장 6회). 참조는 디스크에 남아 서버를 껐다 켜도
재사용된다. 진행 목록(JOBS)은 메모리라 재시작하면 비지만 파일은 `workspace/out/` 에 남는다.

## API

| | |
|---|---|
| `POST /api/ref` | multipart `audio`, 선택 `ref_text` → `{job}` |
| `POST /api/synth` | json `{ref_id, text, ref_text}` → `{job}` |
| `GET /api/job/<id>` | `{state, stage, error, result}` |
| `GET /files/<path>` | 참조·결과 wav |

## 알려진 문제 — 끝의 여운이 짧다

**말은 다 들어 있는데 마지막 음절이 급히 멈춘다.** 조사한 것과 아직 모르는 것을 갈라 적는다.

확인된 것:

- **모델이 끊긴 채로 준다.** 워커는 모델이 준 배열을 그대로 쓰고 길이도 배열에서 직접
  계산하는데(`tts_worker.py:66-69`), 그 값과 디스크 wav 길이가 일치한다. 우리 코드에
  자르는 곳은 없다
- **단어는 하나도 안 없어진다.** 생성물 6개를 whisper 로 받아쓰니 전부 요청 문장과
  글자까지 일치했다. 사라진 것은 말이 아니라 **여운**이다 — 끝 여백이 0.02~0.04초뿐이다
- **길이 상한이 아니다.** `max_new_tokens` 2048 ≈ 170초
- **딸깍(불연속)이 아니다.** 끝 20ms 진폭이 0.000~0.014 로 0 에 내려앉는다
- **참조 끝맺음이 원인의 전부가 아니다.** 참조를 말 도중(11.96초에서 뚝)에서 문장 끝
  ("…없어졌어요.")으로 바꾸니 길이는 늘었지만(2.72~3.28초 → 3.44~3.68초) 3회 중 2회는
  여전히 짧게 끝났다

모르는 것: **왜 여운 없이 멈추는지.** 그리고 판정에 쓴 지표(마지막 100ms 에너지 / 전체
에너지)는 **마지막 음절이 유성음이냐에 흔들려서** 도구로 약하다 — 같은 조건 3회에서
1~2회만 "잘림"으로 나오는 것이 그 탓일 수 있다. 소리 판정은 귀로 해야 한다.

갈라볼 것 — 끝에 무음 0.25초만 붙인 것이 괜찮게 들리면 **여백 문제**이고(앱에서
페이드 + 무음으로 마무리하면 된다), 그것도 잘려 들리면 **마지막 음절 자체가 잘리는 것**이라
생성 쪽을 파야 한다. 표본은 `들어볼것/qwen3tts_끝잘림/`.
