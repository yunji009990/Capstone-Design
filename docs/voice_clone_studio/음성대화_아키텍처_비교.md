# 음성 대화 시스템 아키텍처 비교: 캐스케이드 vs S2S

> 오디오 입력 → (이해) → 답변 생성 → 오디오 출력 파이프라인을 만들 때의 두 갈래 접근과 장단점 정리.
> 대상 프로젝트 요건: **완전 로컬/오프라인**, **추출한 화자 목소리로 클로닝**, **한국어**, Unity 연동, 실시간 지향.
> 하드웨어 기준: RTX 5060 Ti 1장. TTS 기본 모델: Qwen3-TTS.

---

## 1. 두 가지 방법 개요

| | 방법 1 — 캐스케이드 | 방법 2 — S2S(통짜) |
|---|---|---|
| 구조 | `오디오 → STT → 텍스트 → LLM → 텍스트 → TTS → 오디오` | `오디오 → [하나의 신경망] → 오디오` |
| 중간 텍스트 | 있음 (핵심 훅 지점) | 없음/약함 |
| 예시 | whisper + 로컬 LLM + Qwen3-TTS | GPT-4o realtime, Moshi, Qwen2.5-Omni |
| 성격 | 모듈 조립형, 제어 쉬움 | 통합형, 지연 최소 |

---

## 2. 방법 1 — 캐스케이드 (STT → LLM → TTS)

STT로 음성을 텍스트로, LLM이 답변 텍스트를 생성, TTS가 다시 음성으로. **중간에 항상 텍스트를 거친다.**

### 장점
- **제어성이 높다** — 중간 텍스트가 손댈 수 있는 지점:
  - **RAG**(문서 검색 후 프롬프트에 주입), **툴/함수 호출**, **금칙어·정책 필터**, **정확한 로깅/감사**
  - 프롬프트 수정·LLM 교체·출력 형식 강제
- **목소리 클론 자유** — TTS 단계에서 원하는 레퍼런스 화자 목소리 지정 가능
- **말투/사투리 주입이 쉬움** — LLM 프롬프트+few-shot로 문체·사투리 어휘, TTS 레퍼런스로 사투리 억양
- **완전 로컬 실행 가능** — 오픈 STT/LLM/TTS 조합으로 오프라인 구성
- **모듈 교체·디버깅 용이** — 각 단계 독립적으로 개선/측정

### 단점
- **지연이 쌓이기 쉽다** — 3단계 핸드오프. 순차로 하면 느림 (스트리밍·파이프라이닝 필수)
- **구성요소 관리 부담** — 3개 모델 각각 로드·버전·환경 관리
- **오차 전파** — STT 오전사가 LLM·TTS로 번짐
- **감정·억양 손실** — 텍스트로 변환되며 원음의 감정/톤 정보 일부 소실

---

## 3. 방법 2 — S2S (Speech-to-Speech, 통짜 모델)

음성을 텍스트로 바꾸는 중간 단계 없이 하나의 모델이 **오디오를 직접 듣고 직접 말한다.**

### 장점
- **지연 최소** — 단계 핸드오프 없음, 사람과 대화하는 느낌
- **자연스러운 상호작용** — 억양·감정·끼어들기(full-duplex, 듣기·말하기 동시) 처리에 유리
- **오차 전파 없음** — 텍스트 병목 없음

### 단점
- **로컬 실행이 어렵다**
  - 최상급(GPT-4o realtime)은 **클라우드 전용 → 오프라인 불가**
  - 오픈 모델(Moshi 등)은 무겁고, 실시간 양방향 인프라 복잡, **한국어 품질·지원 약함**
- **목소리 클론이 사실상 막힘** — 프리셋 목소리만, 임의 화자 클로닝은 정책/설계상 불가
- **제어성이 떨어짐** — 중간 텍스트 훅이 없어 RAG·툴·필터·로깅이 어렵거나 덜 투명
  - 단, 텍스트 컨텍스트+툴을 지원하는 모델(GPT-4o realtime)이면 RAG는 조건부 가능
- **성숙도 낮음** — 오픈 생태계·도구 아직 미성숙

## 4. 축별 비교 요약

| 축 | 캐스케이드 | S2S |
|---|---|---|
| 지연(첫 소리) | 최적화 필요 (스트리밍 시 수초) | 최소 (수백 ms급 가능) |
| 로컬/오프라인 | ⭕ 가능 | ❌ 좋은 건 클라우드 전용 |
| 임의 목소리 클론 | ⭕ 자유 | ❌ 프리셋만 |
| 제어(RAG/툴/필터/로깅) | ⭕ 강함 | △ 약함/조건부 |
| 말투·사투리 주입 | ⭕ 프롬프트+레퍼런스 | △ 어려움 |
| 한국어 품질 | ⭕ 모델 선택 가능 | △ 약한 경우 많음 |
| 개발·디버깅 | ⭕ 모듈별 | △ 통짜라 손대기 어려움 |
| 자연스러움(감정/끼어들기) | △ 텍스트에서 일부 손실 | ⭕ 강함 |

## 5. 이 프로젝트 요건 대입 → **캐스케이드 권장**

| 요건 | 캐스케이드 | S2S |
|---|---|---|
| 완전 로컬/오프라인 | ⭕ | ❌ |
| 추출 화자 목소리 클론 | ⭕ | ❌ |
| 배경지식·제어 필요 | ⭕ | △ |
| 저지연 | △ (최적화로 커버) | ⭕ |

→ **로컬 + 목소리 클론**이라는 두 핵심 요건에서 S2S가 막히므로, **캐스케이드가 맞는 선택.**
S2S는 "지연은 최고지만 로컬·제어·클론이 발목 잡는" 트레이드오프.

---

## 6. 캐스케이드를 택한 뒤의 로드맵

### 6-1. 지연 최적화 (가장 중요)
캐스케이드의 유일한 약점인 지연은 아래로 잡는다. 목표 지표는 **"첫 소리까지의 시간(time-to-first-audio)"**.

- **모든 단계 스트리밍 + 파이프라이닝(겹치기)** — 순차로 쌓지 않고 동시 실행
- **문장 버퍼(sentence chunking)** — LLM 토큰을 문장 경계에서 끊어 즉시 TTS 투입 → 첫 문장부터 재생
- **엔드포인팅/턴 감지 튜닝** — "말 끝났는지" 판단 시간이 숨은 병목. semantic VAD 등
- **웜 모델 유지 + 전사 캐시** — 재로드·재전사 제거
- **작고 빠른 모델** — LLM은 TTFT 짧은 소형(3~8B), STT는 whisper turbo/distil

> 참고: 업계 클라우드 최적 사례는 첫 소리 600~900ms. 우리는 로컬 + Qwen3-TTS(조각 스트리밍 불가, RTF 1.93)라 **첫 소리 ~1.5~3초가 현실적 목표.**

### 6-2. 말투·사투리·배경지식 (프롬프트 우선, 파인튜닝은 fallback)
| 대상 | 1순위(학습 없음) | 부족할 때 |
|---|---|---|
| 배경지식(사실) | **RAG**(검색→프롬프트 주입) | — (파인튜닝 비권장) |
| 말투/문체 | 프롬프트 + few-shot | 거의 불필요 |
| 사투리 어휘·문법 | 프롬프트 + few-shot | LLM QLoRA |
| 사투리 억양·발음 | **TTS 레퍼런스 화자 선택** | TTS 화자 파인튜닝 |

- 말투/사투리 주입은 **캐스케이드가 텍스트 훅(LLM)과 레퍼런스 훅(TTS)을 공짜로 주기 때문에** 가능한 것.
- **파인튜닝은 "프롬프트/레퍼런스로 안 될 때만" 꺼내는 카드.**

### 6-3. 파인튜닝 소요(선택 시, RTX 5060 Ti 기준)
| 작업 | 순수 GPU 시간 | 현실 벽시계(데이터·반복 포함) |
|---|---|---|
| 목소리 클론(화자별, GPT-SoVITS류) | 화자당 <1시간 | ~1주 이내 |
| 배경지식(RAG, 학습 아님) | 0 | 며칠(구축) |
| 사투리/말투(LLM QLoRA) | 수 시간 | 1~2주(데이터 확보가 좌우) |

> 핵심: GPU 학습은 짧다. 진짜 시간은 **데이터 준비·품질 반복**에서 나간다.

---

## 7. 예상 지연 (캐스케이드, 웜 모델 기준)
사용자 ~5초 발화, ~5초 답변 가정.

| 단계 | 웜 상태 |
|---|---|
| STT (whisper large-v3, 5초) | 0.5~1.5초 |
| LLM (로컬 7~8B, ~80토큰) | 2~5초 |
| TTS (Qwen3, 답변 5초, RTF 1.93) | ~8~13초 (병목) |
| **완주 합계** | **~11~20초** |
| **문장 스트리밍 시 첫 소리** | **~6~8초** |

> 콜드(첫 실행)는 모델 로드로 ~45~95초 → 서버 뜰 때 3모델 미리 웜업 필수.

---

## 8. 결론
- **아키텍처: 캐스케이드 확정** (로컬 + 목소리 클론 + 제어 요건).
- **기본값: 프롬프트(말투·사투리 어휘) + zero-shot 레퍼런스(억양) + RAG(배경지식).** 학습 없이 여기까지.
- **최적화: 스트리밍·문장청킹·웜모델·엔드포인팅**으로 지연을 잡는다.
- **파인튜닝: 기본으로 부족할 때만** (목소리 고품질 → TTS 화자 파인튜닝, 사투리 일관성 → LLM QLoRA).
