# 판정기 텍스트 검사

2026-09-11. TTS를 비활성화하고 **기존 Gemma의 실제 추론 API**에 텍스트를 넣어 검사했다.
가짜 판정 결과를 반환하는 단위 검사와 구분한다. 첫 검사에서 문제 세 가지를 찾아 수정했고,
수정 후 사전에 정한 68개 입력에서 기대한 방향·경로와 일치했다.

## 현재 실행 상태

- `DIALOGUE_TTS_URL=`로 음성 합성을 끄고 Qwen3-TTS 프로세스를 종료했다. TTS 코드·가중치는 재연결할 수 있다.
- 8002는 `mode=streaming_text`, `tts=false`, `interruption_policy=semantic_v1`이다.
- 마이크 → SenseVoice → 판정·LLM → **텍스트 답변**을 사용할 수 있다. 참조 음성을 준비하지 않는다.
- 판정은 TTS와 독립적이다. 새 클라이언트가 `start.interruption_policy=semantic_v1`을 보내면
  텍스트 생성 도중에도 보류·의도 판정·재개가 가능하다. 이미 생성이 끝난 답변은 대화 기록이 된다.
- 판정기는 기존 일반 Gemma를 재사용한다. 추론 경로는 현재 같은 Gemma의 thinking 설정 차이다.

## 검사 방법과 결과

입력·기대값은 [turn_judge_cases.json](../tools/turn_judge_cases.json)에 먼저 작성했다.
[eval_turn_judge.py](../tools/eval_turn_judge.py)가 실제 `Dialogue.messages()`로 STT 이후 입력을 구성한 다음
운영 코드의 `LLMClient.route()` 또는 `decide_interruption()`을 호출한다.
이 분류 검사에서는 STT·TTS·후속 답변 생성을 호출하지 않는다. 관찰 정보는 모두 명시적으로 만든 입력이다.

**아래 68개 결과는 2026-09-11 당시의 사례 파일로 잰 값이다.** 그 파일에는 지금은 없는 음성 감정
항목이 들어 있었다. 2026-09-16에 그 기능을 제거하면서 사례에서도 해당 항목을 지웠고,
**수정한 사례로는 아직 다시 측정하지 않았다.** 아래 수치를 현재 사례의 결과로 읽으면 안 된다.

| 검사 | 결과 |
|---|---|
| 수정 전 기본 사례 | 45/48 일치: 일반/추론 16/16, 끼어들기 29/32 |
| 수정 후 같은 기본 사례 | 48/48 일치 |
| 수정에 사용하지 않은 추가 사례, 첫 실행 | 20/20 일치 |
| 수정 후 합계 | 일반 발화 경로 24/24, 끼어들기 방향·경로 44/44 |
| 분류 요청 지연 68건 | 중앙값 0.465초, p95 0.600초, 최대 0.630초 |

같은 “네”의 맞장구/질문 응답 구분, 아직 전달하지 않은 질문, 미완성 정정, 같은 주제의 조건 변경,
새 주제, 중단·대기, 대기 중 맞장구, 명시적 재개, 부정·인용 표현, STT 띄어쓰기 오류,
Unity 물건 정보, 계산·조건 비교·일상 설명을 포함했다.

이 수치는 **프로젝트 정책에 맞춰 만든 소수 기능 사례의 기대값 일치율**이다.
실사용 정확도나 모든 표현에서의 동작을 보장하는 수치가 아니다. 판정 지연에는 사용자 발화·VAD·STT·
후속 답변 생성·TTS 시간이 포함되지 않는다. 기본 사례 결과로 수정한 뒤 추가 20개를 처음 실행했으며,
검사 결과에 맞춰 기대값을 바꾸지 않았다.

## 발견하고 수정한 문제

| 입력 상황 | 이전 판정 | 수정 후 |
|---|---|---|
| “아니, 내가 말하려던 건...”처럼 정정 내용이 아직 없음 | 수정할 내용을 모르는 채 `revise` | `clarify`로 의도 확인 |
| 아직 전송하지 않은 초안에 질문이 있고 사용자는 “네”라고 맞장구 | 그 질문을 이미 들었다고 보고 `revise` | `resume` |
| 산책 준비 설명 중 같은 산책의 길·시간 조건 비교 요청 | 별개 주제로 보고 `switch` | `revise` + `reasoning` |

미전달 초안을 판정기 입력에서 **제외**했다. 판정기는 원래 요청·전달 확인된 답변·대화 기록만 본다.
초안은 `revise`가 결정된 뒤 답변을 고치는 모델에 참고 자료로만 전달한다.
또한 구체적인 정정 내용이 없는 경우, 같은 활동의 세부 조건을 바꾸는 경우의 분류 기준을 명확히 했다.

TTS 의존성도 분리했다. 텍스트 모드에서는 이미 전송한 글자를 전달된 내용으로 처리한다.
보류 중 LLM의 스트림이 끝나더라도 답변을 임의로 완료 처리하지 않고 재개 결정을 기다린다.
기존 음성 모드에서는 재생 확인된 문장 경계를 계속 사용한다.

## 실제 연결 검사

TTS가 꺼진 실제 8002 WebSocket에서 첫 답변을 생성하는 도중 새 텍스트를 보내 네 경로를 검사했다.

| 새 입력 | 확인한 동작 |
|---|---|
| “계속 말해 줘.” | 같은 응답 ID로 글자 스트림을 이어서 완료 |
| “비가 오는 날 기준으로 바꿔 줘.” | 새 응답에서 우산·방수 신발 등으로 수정 |
| “그건 됐고 고양이에 대해서 설명해 줘.” | 새 응답에서 고양이 설명 |
| “잠깐 기다려 줘.” → “이제 계속 말해 줘.” | 대기 중 출력 없음, 요청 뒤 같은 응답 재개 |

네 경우 모두 음성 패킷과 참조 준비 호출이 없었다. 별도로 Unity Editor에서 텍스트를 전송해
Unity의 “가족 사진을 집어 들었다” 행동 정보가 답변에 반영되는지 확인했다.
질문 “내가 지금 들고 있는 게 뭐야?”에 “가족 사진을 들고 계시네요.”라고 답했고,
`ttsEnabled=false`, `audioSamples=0`, `audioEvent=text`였다.
서버/로컬의 회귀 검사 53개도 통과했다.

## 다시 실행하기

서버의 `~/capstone-server/tools/`에 실행기와 JSON 사례를 배포했다.
서버 로그인 후 비밀 값을 출력하지 않고 환경을 불러와 실행한다.

```bash
cd ~/capstone-server
set -a
source dialogue.env
set +a
~/venv/dialogue/bin/python tools/eval_turn_judge.py --split all --output .text-judge-all.json
```

`--split core`는 기본 48개, `--split holdout`은 추가 20개다.
`--ids i_unheard_question,i_compare_conditions`처럼 일부만 실행할 수 있다.
새 입력은 JSON의 `contexts`와 `cases`에 대화 상황·사용자 텍스트·기대 판정을 작성한다.
실패한 사례, 실제 판정 이유, 요청 시간이 출력되며 JSON에도 남는다. 실패가 있으면 종료 코드는 1이다.

Unity에서는 AI 테스트 씬을 Play한 뒤 `Tools > Dialogue > Run text response check`를 실행하면
마이크·STT·TTS 없이 텍스트 질문과 Unity 상황 전달을 검사한다.
`Run AI test scene check`는 공개 WAV를 입력해 STT와 텍스트 답변 경로를 검사한다.
실제 재생 위치 검사인 `Run voice interruption check`는 TTS를 다시 켠 상태에서 사용한다.

원본 결과는 로컬 `.dialogue-work/`에 있다.

- `text-judge-core-before.json`, `text-judge-core-after.json`, `text-judge-holdout.json`: 입력별 기대값·판정·지연·소스 해시
- `text-judge-socket-check.json`: 실제 텍스트 생성 중 끼어들기 결과
- `ai-text-scene-smoke.json`, `ai-text-scene-tested.png`: Unity 텍스트 입력 검사

TTS를 재연결할 때는 `dialogue.env`의 `DIALOGUE_TTS_URL`을 `http://127.0.0.1:8003`으로 설정하고
TTS 서비스를 시작한 뒤 대화 서비스를 재시작한다. 토큰은 기존 TTS 설정과 일치해야 한다.
음성 품질·VAD·STT 오류가 섞인 실사용 평가는 이 텍스트 검사와 별도로 진행한다.
