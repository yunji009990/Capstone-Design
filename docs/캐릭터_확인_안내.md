# 캐릭터 확인·기억 삭제 안내

기준일: 2026-09-17. 대상은 대화 AI 서버의 **서버가 정해진 자리에서 읽는 안내 문장**이다.
공통 지침은 [AGENTS.md](../AGENTS.md), 대화 구조는 [서버 음성 대화 구조](서버_음성대화_구조.md)를 따른다.

## 1. 왜 바꿨나

실제 사용자 체험에서 캐릭터 말투 중간에 시스템 안내 말투가 끼었다. 원인은 코드에 박혀 있던
`Server/realtime_dialogue.py`의 고정 clarify 문장(예전: "기존 설명을 계속할까요, 아니면 내용을
바꿔서 이야기할까요?")이다. 이 문장은 **일반 Gemma 생성을 거치지 않고 그대로 TTS로** 나갔다.
같은 함수의 기억 삭제 성공·확인 실패 안내 두 줄도 같은 경로의 고정 존댓말이었다.

2026-09-17 사용자 지적으로 `clarify`를 **준비 대상에서 뺐다**. 말투만 캐릭터로 맞춰도 내용은
"계속할지 / 바꿀지"라는 진행 방식 안내라서 사용자가 방금 한 말과 무관했고 몰입을 깼다. 되묻기는
이제 인물의 보통 답변 생성 경로(`realtime_dialogue.CLARIFY_GUIDANCE`)로 만든다. 판정 호출은
늘지 않고 생성 호출은 다른 턴과 같이 1회다. 아래 내용은 기억 삭제 안내 두 종류에만 해당한다.

## 2. 무엇을 준비하나

두 종류(`memory_forgotten`, `memory_clarify`)의 문장을 캐릭터 말투로 미리 만든다.

- `memory_forgotten`: 요청받은 기억을 **이번 대화의 기억에서** 지웠다고 알린다.
- `memory_clarify`: 아직 지우지 않았고 무엇을 지울지 되묻는다.

## 3. 준비 시점과 설정

- 설정은 `DIALOGUE_SYSTEM_LINES_ENABLED`(기본 1)다. 0이면 아래 폴백 문장을 쓴다.
- **연결 준비(접속) 때만** 한 번 생성한다. 실제 턴에서는 이 문구를 만드는 모델 호출이 없다.
  기존 끼어들기 판정과 기억 삭제 판정 호출은 그대로다.
- 캐시는 서버 프로세스 RAM 전용이며 최대 16개다. 키는 버전 `persona_system_line_v2` +
  인물 프로필 + 생성 모델 설정이라 다른 캐릭터의 문장이 섞이지 않는다. 디스크에 쓰지 않으므로
  **서버 재시작 시 비워진다**. 실패·취소는 저장하지 않고 다음 연결에서 다시 시도한다.
- 준비는 순차 잠금이라 같은 자료의 동시 접속에도 모델을 한 번만 부른다. 상한은 준비 20초,
  실제 생성 호출(`memory_json`)은 HTTP 10초다.
- 오디오는 미리 만들지 않는다. 대기 리액션과 달리 사전 합성 캐시가 없고, 실제 턴에서
  기존 TTS 경로로 합성해 내보낸다.
- 생성 입력은 성격·말투(persona)뿐이다. 등록 `knowledge`와 인물별 추가 `rules`는 넣지 않는다.

## 4. 준비 실패와 폴백

준비가 실패해도 체험 시작을 막지 않는다. 그 연결은 짧은 폴백 문장을 쓴다. 폴백의 존대/반말은
**raw persona의 `[말투]` 구간 선언만** 보고 고른다. 공통 규칙과 다른 문항의 예시·사실에도
존댓말·반말이라는 낱말이 있어 전체 글에서 찾으면 뒤집히기 때문이다. 선언이 없거나 존대와
반말이 함께 적혀 있으면 해요체가 기본이다. 이름·관계·사실은 만들지 않는다.

## 5. 검증 범위

생성 문장은 형식·금지어·모순 표식만 본다. 완전한 의미 검증이나 자연스러움 판정이 아니다.
`memory_forgotten`은 완료 표현이 있어야 하고 부정이 섞이면 거절하며, 삭제 범위를 밝히는
**'이번 대화'** 글자가 필수다. `memory_clarify`는 아직 지우지 않았음을 밝혀야 하고, 부정된
완료 표현을 지운 나머지에 완료 주장이 남으면 거절한다. 어긋나면 폴백으로 돌아간다.

## 6. 관측

- 진단 로그에 `event=answer.fixed`와 `reason=memory_forgotten|memory_clarify`가 남는다.
  되묻기 턴은 일반 생성이므로 `llm.first_text`로만 남는다. 문장 원문은 남기지 않는다.
- `ready.system_lines`에 `version`·`ready`·`source`·`cache_hit`(실패 시 `reason`)가 있고,
  `/health`의 `system_lines`에 `enabled`·`version`이 있다.
- 현재 버전 값은 `persona_system_line_v2`이며 준비 대상은 기억 삭제 안내 두 종류뿐이다.
  되묻기 문장은 이 경로에 없다.

## 7. 검사 현황

### 7.1 2026-09-17 되묻기 변경 뒤

- 실제 Gemma가 CLARIFY로 판정한 불완전 발화 6건에서 **진행 방식 선택지 없이** 짧은 캐릭터 반응을 생성했다.
  강제 CLARIFY 스트레스 사례와 실제 판정 사례는 구별한다.
- 변경 뒤 전체 하네스 492개, 연결된 Unity의 경계 정지 28개·리샘플러 38개 통과.
- 운영 API는 `persona_system_line_v2`로 적용했다. 실제 모델/WS 검사 결과와 산출물은
  [서버 음성 대화 구조](서버_음성대화_구조.md)의 2026-09-17 기록을 따른다.
- **VR에서의 사람 청취는 미실행**이다. 자동 검사 통과로 자연스러움까지 단정하지 않는다.

### 7.2 v1(고정 clarify) 시점 기록

아래는 `clarify`가 준비 대상이던 v1 시점의 기록이다. 되묻기 관련 수치는 현재 구현의 근거가 아니다.

- 자동 검사 472/472 통과(하네스 160, 서버 263, worker 5, web 44), skip 0. 이후 부정문 검사
  자료를 보강해 신규 16개를 `targeted-final.log`에 재실행해 통과했다. 실행 코드는 바꾸지 않았다.
- 실제 Gemma로 합성 역할 3종(할머니·친구·존댓말) × 3회 준비 9/9 통과. 캐시 재호출 0회,
  준비 0.967~1.323초(평균 1.05초)다. **접속 때의 값이며 매 턴 지연이 아니다.** 각 3회는
  temperature 0이라 같은 대사가 나온다. 자연스러움·다양성 평가가 아니다.
- 처음 9건은 형식·캐시만 통과했고, 메인 품질 검토에서 완료 안내가 삭제 범위를 생략하는 문제를
  발견해 지침·검증기를 보완했다. 형식 검사 통과가 문장 품질의 근거가 아니라는 사례다.
- 운영 8002에 실제 WebSocket으로 접속해 Gemma 끼어들기 판정 → 준비된 문구 → Qwen TTS까지
  확인했다(합성 text 입력). 확인 질문 9, 이후 일반 대화 3, 기억 삭제 완료 3, 삭제 대상 확인 3으로
  18/18 성공이다. 기본 설명 9턴은 별도 집계다. 24k 모노 PCM 수신과 `response_id` 정합을 확인했고
  재생 완료는 가상 `playback.done`이며, 참조 테스트 자료는 해제했다.
  STT·VAD와 Unity 실제 마이크·스피커 청취는 검사하지 않았다.
- `live-diagnostics`: 세 연결 모두 `clarify` 3, `memory_forgotten` 1, `memory_clarify` 1이고

- 배포는 실행 파일 5개만 백업 후 대화 API를 재시작했다. 백업은
