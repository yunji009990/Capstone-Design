## 후속: 끝음절이 다른 문장으로 확인

사용자가 처음에는 A·B의 마지막이 잘린다고 보고했지만, 압축을 푼 뒤에는 둘 다 끝까지 나온다고 정정했다.
다만 기존 문장의 마지막 `어`가 잘림을 구분하기 어렵다는 요청에 따라 새 청취 자료를 만들었다.
압축 여부가 실제 원인이었다고 확정하거나 모든 문장의 음질이 통과했다고 판정한 것은 아니다.

[새 끝음절 청취 페이지](../tools/_work/tts_replacement_20260917/ending-listening/들어보기.html)는 이미 압축을 푼 폴더에 있다.
`고맙습니다`, `만납시다`, `사랑`, `약속`, `책`으로 끝나는 짧은 문장 5개와, `만납시다`로 끝나는 세 문장짜리 대사를 A·B로 생성했다.
각 문장 아래 A·B·기존 Qwen3-TTS 재생 버튼이 있고, 참조 3종과 회차 3개를 선택할 수 있다. 마지막 항목은 세 문장을 한 번에 생성한 결과다.

이후 사용자는 Qwen 음원도 `밥은 꼭 챙겨 먹고, 내일 다시 만납시다.`를 제외하면 끝까지 잘 나온다고
보고했다. 어느 참조·회차를 들었는지는 기록되지 않아 Qwen 54개 전체가 청취 통과했다고 세지는 않는다.
이 정상 청취 사례는 새 웹 합성에서 보고된 말끝 잘림과 함께 비교해야 한다.

| **B: CosyVoice3** | 54/54 · 20/20 | 약 486ms | 0.263 | 우선 후보. 취소 후 복구는 A보다 느림 |
| VoxCPM2 ultimate | 54/54 · 20/20 | 약 41ms | 0.257 | 같은 모델의 다른 복제 모드. 추가 비교용 |
| MOSS-TTS-Realtime | 54/54 · 20/20 | 약 332ms | 0.554 | 이번 참조·설정에서 전사 불일치와 긴 공백이 많아 후순위 |
| Fish S2 Pro | 짧은 3건만 완료 | 약 117ms | 0.503 | 공유 GPU에서 전체 시험을 완주하지 못해 최종 후보 제외 |
| 기존 Qwen3-TTS | 54/54 · 20/20 | 약 120ms | 0.231 | 사용자가 말끝 잘림을 보고한 기존 방식의 비교 기준 |

후보 4개 모델과 기존 Qwen을 실제 실행했다. VoxCPM2의 두 모드는 별개 모델로 세지 않는다.
위 표는 후보별 네이티브 실행기 기준이며 Qwen과 Fish는 로컬 HTTP 경로를 포함한다. 기존 서버 계약에 붙인 HTTP 측정은 아래와 별도로 구분한다.

## 공통 조건과 판정 한계

- 참조 3종: 시험 당시 등록 음성, 공개 한국어 음성, 공개 영어 음성. 영어 참조로 한국어를 생성하는 경우도 포함했다.
- 참조마다 고정 문장 6종 × 3회 = 후보 설정당 54건, 예열 3건, 연속 요청 20건, 취소 후 재요청을 검사했다. Fish는 부분 시험만 완료했다.
- 문장은 짧은 문장 3개, 이를 합친 문단, 존댓말, 짧은 리액션이다. 시드 41/42/43을 사용했으나 Qwen API에는 시드 지정이 없어 3회 반복으로만 비교한다.
- 출력은 24kHz 모노 PCM16LE, 패킷 최대 9,600바이트다. 리샘플러 마지막 잔여 샘플까지 배출해 샘플 수를 대조했다.
- 실제 생성 도중 청크를 받았다. 완성된 WAV를 뒤에서 나누어 보내는 방식으로 스트리밍을 대신하지 않았다.
- 첫 PCM 측정에는 모델 적재·참조 준비·VAD·STT·LLM·외부 네트워크·Unity·재생 버퍼·음성 앞부분의 무음은 포함하지 않는다.
- RTX PRO 6000 Blackwell 96GB 공유 서버에서 순차 실행했다. Qwen을 잠시 내린 뒤 남은 약 15.8GB 안에서 시험했다. 다른 사용자 GPU 프로세스와 LLM·STT는 중단하지 않았다.
- 자동 전사는 Whisper large-v3 CPU int8로 검사했다. **전사 정확도는 음색·자연스러움·끝음절 완결성의 증명이 아니다.** Qwen도 54건 중 53건의 전사가 정확해 기존 청취 문제를 자동 전사만으로 잡지 못했다.

## A: VoxCPM2 검증

- reference-only 모드를 기본 청취 후보로 삼았다. 전체 평균 문자 오류율(CER)은 2.37%, 전사 완전 일치는 49/54였다.
- 네이티브 48kHz를 24kHz로 변환한 결과에서 마지막 샘플 누락은 발견하지 못했다.
- 동일 참조 3종 × 시드 3회의 스트리밍·일괄 생성 9쌍도 비교했다. 9/9의 총 샘플 수가 같고 평균 절대 차이는 약 0.000008~0.000018이었다. 청크 조립의 꼬리 누락은 관찰되지 않았으나, 모델의 발음 자체가 완전한지는 청취해야 한다.
- 기존 `tts_server.create_app`에 실험 어댑터를 주입하고 기존 `TTSClient`로 연결했다. HTTP 검사 10개, 연속 20건, 첫 PCM 전 취소 3건, 두 청크 후 취소 3건과 후속 요청이 통과했다.
- HTTP 연속 20건의 평균 첫 PCM은 약 **53ms**였다. 취소 후 유휴 복귀는 100ms 간격 폴링에서 약 **102~104ms**로 관찰했다. 정확한 GPU 취소 지연을 뜻하지 않는다.
- 네이티브 생성기 `close()` 자체는 0.149ms였으나 이를 HTTP 전체 취소 시간으로 해석하면 안 된다.
- PyTorch 최대 예약 메모리는 6,512MiB였다. 연속 20건 전후의 예약 메모리 바닥값은 5,432MiB로 같았다. 이 값은 CUDA 컨텍스트 등을 포함한 프로세스 전체 VRAM은 아니다.
- ultimate는 같은 모델의 다른 모드다. 등록 음성의 CER은 reference-only 3.09%, ultimate 10.06%여서 기본 후보에서 제외하고 추가 청취 항목으로 남겼다.

## B: CosyVoice3 검증

- 모델은 `FunAudioLLM/Fun-CosyVoice3-0.5B-2512`다. 초기 transformers 4.57.3 조합은 발화가 깨졌으며 fp32 전환만으로 해결되지 않았다. 격리 환경에서 공식 고정 버전인 **transformers 4.51.3 / tokenizers 0.21.4**로 정상 출력을 확인했다.
- fp16, TRT/vLLM 미사용, `text_frontend=False`로 시험했다. 공식 접두 `You are a helpful assistant.<|endofprompt|>`는 참조 전사에만 붙였다.
- 상류 코드가 요청 중 `token_hop_len`을 25에서 100으로 바꾸므로 요청마다 25로 초기화했다. 이전 조합의 첫 PCM 약 892ms를 약 486ms까지 줄였다.
- 협조형 토큰 생성 취소를 실험 어댑터에 추가했다. 정상 생성 54개 WAV는 취소 기능 추가 전 같은 설정 결과와 **54/54 바이트 동일**했다.
- 평균 CER은 4.55%였다. 등록 음성 12.72%, 공개 한국어 0%, 공개 영어 0.94%였다. 일부 자동 전사는 환각 가능성이 있어 실제로 엉뚱한 단어를 발화했다고 단정하지 않는다.
- 기존 서버·클라이언트 계약의 HTTP 검사 10개와 연속 20건을 통과했다. HTTP 첫 PCM 평균은 약 **498ms**였다.
- 첫 PCM 전 취소 3건은 유휴 복귀 **609~813ms**, 두 청크 후 취소 3건은 **307~710ms**였다. 후속 합성은 모두 복구됐다. A보다 느린 취소가 적용 시 고려할 제약이다.
- 네이티브 취소는 약 258ms였다. 토큰 루프 정지 뒤에도 남은 오디오 처리와 자원 정리를 기다려야 했다. 검사 종료 후 작업 사전과 참조는 비어 있었다.

## 후순위 후보

**MOSS-TTS-Realtime:** 공식 예시처럼 비어 있지 않은 user 텍스트(`Hello!`)를 사용한 결과를 최종 비교에 썼다.
54건 중 전사 완전 일치 21건, CER 20% 초과 18건이었다. 21개 클립에서 긴 공백 31개를 측정했다.
전사 환각으로 평균 CER이 크게 부풀 수 있어 이를 음질 점수로 제시하지 않는다. 이 환경·참조·설정에서 후순위이며, 모델 전체의 한국어 능력을 단정하는 결과는 아니다.

**Fish S2 Pro:** vLLM-Omni 0.26의 실제 코덱 오디오 스트림으로 시험했다. BF16 적재는 메모리 부족으로 실패했다.
FP8 설정을 요청한 실행에서 짧은 한국어 3건을 생성했고 그 전사는 정확했다. 실제 가중치 정밀도가 FP8인지 별도 검증하지는 않았다.
HTTP 검사 클라이언트의 불필요한 CUDA 컨텍스트까지 없앴지만 전체 비교의 참조 준비 STT에서 GPU 메모리 부족이 발생했다.
현재 서버 자원에서 STT와 안정적으로 병행하는 조건을 충족하지 못했으므로 짧은 3건만으로 최종 후보에 올리지 않았다.

## 공식 근거와 후속 작업

한국어 지원, 목소리 복제, 스트리밍 API는 각 공식 저장소·모델 설명을 기준으로 후보를 골랐다.
[VoxCPM](https://github.com/OpenBMB/VoxCPM), [CosyVoice](https://github.com/QwenAudio/CosyVoice), [CosyVoice3 모델](https://huggingface.co/FunAudioLLM/Fun-CosyVoice3-0.5B-2512), [MOSS-TTS](https://github.com/OpenMOSS/MOSS-TTS), [MOSS 실시간 모델](https://huggingface.co/OpenMOSS-Team/MOSS-TTS-Realtime).
이 세 계열은 Apache-2.0이다. Fish는 [Fish Audio 연구 라이선스](https://github.com/fishaudio/fish-speech/blob/main/LICENSE)이므로 같은 이용 조건으로 취급하지 않는다.
시험에 고정한 코드는 [커밋 기록](../tools/_work/tts_replacement_20260917/review-data/repos.json), 가중치는 [모델 리비전 기록](../tools/_work/tts_replacement_20260917/review-data/models.json)에 남겼다.

사용자가 말끝·음색·잡음을 듣고 후보를 고르면 해당 어댑터를 운영 구조에 통합하고 대화 중 취소·재개와 Unity 재생을 확인한다.
현재 완료 범위는 실제 모델 비교와 서버 HTTP 계약 검사다. **대체 모델의 Unity 체험 및 운영 배포는 아직 하지 않았다.**
