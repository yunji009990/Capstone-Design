공식 저장소에도 복제 음성의 마지막 음절이 짧게 끝난다는
[사용자 보고](https://github.com/QwenLM/Qwen3-TTS/discussions/161)가 있다.
언어·입력이 다른 미해결 보고이므로 이번 문제의 원인이나 해결책으로 확정하지 않는다.

따라서 이번 청취에서는 **문장부호 자체보다 생성 요청의 최종 끝**과 증상이 일치한다.
문장별 TTS 요청에서는 모든 문장이 요청의 끝이라 잘렸고, 한 요청에서는 마지막만 잘렸다.
이 사실만으로 조기 EOS와 디코더의 마지막 파형 처리를 구분하지는 못한다.
종료 단계의 추가 비교도 준비했다(`tts_tail_followup_20260917/eos/`).

- 기준 음성을 계측 래퍼로 다시 생성한 WAV는 C의 문장별 WAV와 **3/3 해시가 같다**.
- E `eos_delay.wav`: 기준 실행이 EOS를 선택했던 단계와 다음 단계에서만 EOS를 막았다.
  기존 음성 코드의 접두부는 세 문장 모두 완전히 같고, 이후 각각 17·20·4프레임을 더 생성했다.
  두 단계만 막아도 실제 추가 길이는 160 ms로 고정되지 않았다. 그대로 운영에 적용할 수 있는
  종료 정책이라고 판단하지 않는다. 사용자 청취는 **앞쪽 문장 끝 잘림 지속·중간 숨소리 추가,
  마지막 문장 끝은 잘리지 않음**이다. 전체 해결책으로 실패했다.
- F `decoder_extension.wav`: 기준 실행의 음성 코드는 바꾸지 않고 마지막 코드를 두 번
  복제해 디코딩했다. 문장마다 3,840샘플(160 ms)이 늘었다. 기준 디코딩 재현 오차는 0이지만,
  확장 디코딩의 기존 구간 최대 차이는 문장별 0 / 0.00390625 / 0.02905273이었다.
  원래 PCM 뒤에 단순 무음을 붙인 파일이나 손실된 샘플을 복구한 파일로 설명하지 않는다.
  사용자 청취는 **끝 음절이 비정상적으로 반복됨**이다. 해결책으로 실패했다.
- 위 검사 코드는 Claude Code 제안을 메인이 실제 설치된 공식 API와 대조해 수정·실행했다.
  `VoiceClonePromptItem` 리스트와 `speech_tokenizer.decode` 계약을 확인한 뒤 적용했다.
  운영 패키지·서비스·설정은 변경하지 않았고 검사 모델은 CPU에서만 실행 후 종료했다.

### 2026-09-17 마감 전 마지막 개선 비교

사용자는 오늘 마감이며 **등록한 목소리 복제가 필수**라고 확인했고, Qwen 개선은 마지막으로
시도하기로 했다. 고정 목소리 대체나 모델 교체는 적용하지 않았다.

- Claude Code가 기존 검사 코드의 수정안을 작성했고, 메인은 PCM 표본 수와 codec 프레임 수를
  구분하도록 고치고 임시 참조·HTTP 연결의 오류 시 정리를 보완한 뒤 실행했다.
- 현재 등록 참조 하나와 같은 세 문장을 사용했다. seed 0·1·2마다 기준 / G / H를 비교한
  **27회 실제 생성**이다. 모델·샘플링·참조는 고정하고 입력 접미사만 바꿨다.
- G는 원문 뒤 ` ^.`, H는 원문 뒤 ` ... 네.`를 추가했다. H의 더미 발화는 아직 제거하지 않은
  원음이다. 세 문장을 합친 청취 파일은 문장 사이에만 기존과 같은 150 ms 무음을 넣었다.
- 검사 자료는 `tools/_work/tts_tail_followup_20260917/deadline/`에 있다. 다운로드한 청취 WAV

### 같은 답변 다시 듣기 (비교 재생)

증상이 난 **그 회차에 실제로 받은 PCM** 을 두 재생 경로로 다시 듣는 개발용 메뉴다.
같은 문장을 다시 합성한 음성은 결과가 달라질 수 있어 원본 대조를 대신하지 못한다.

1. 체험에서 문제가 난 답변을 **끝까지** 듣는다.
2. **체험 종료**를 누른다. **Play 는 켜 둔 채**로 두고, **`대화 초기화`는 누르지 않는다**

   메뉴가 "체험·답변이 진행 중"이라며 거절하면 몇 초 기다렸다가 다시 고른다.
3. `Tools/Dialogue/Compare last reply/Stream renderer` 를 고른다(실제 대화와 같은 재생 경로).
4. 이어서 `Tools/Dialogue/Compare last reply/AudioClip` 을 고른다(비교용 경로).
5. 두 번 다 Console 첫 줄의 `turn=` 과 `gen=` 이 **같은지 확인**한다. 다르면 서로 다른 답변을

   `Tools/Dialogue/Compare last reply/Stop replay`.

읽는 법. **어느 경우도 원인 확정이 아니다.**

| 들은 결과 | 다음에 볼 곳 |
|---|---|
| 두 경로 모두 잘려 들린다 | 수신 PCM 자체, 두 경로가 공유하는 Unity 출력 단, 출력 장치 |

  비활성·Play 종료에서도 지운다.

   `Tools/Dialogue/Compare last reply/Stream renderer`로 같은 답변을 다시 듣는다.
5. 기존 방식으로 돌아갈 때는 Play를 끄고 `Tools/Dialogue/Playback mode/Stream as received`를 고른다.

선택은 이 PC의 프로젝트별 EditorPrefs에 저장되고 다음 Play부터 적용된다.
다른 clone의 기본값과 플레이어 빌드는 기존 스트리밍이다. APK 단독 실행에는 적용되지 않는다.
Scene_2, 서버, 등록 인물 데이터는 이 옵션으로 수정되지 않는다.

구현과 판정의 한계:

- 수신 중에는 재생하지 않는다. 마지막 짧은 패킷까지 포함한 PCM 전체를 24 kHz AudioClip에 넣는다.
  최대 45초이며 초과하면 기존 버퍼 오류 경로로 명시적으로 종료한다.
- 소비량은 AudioSource의 실제 재생 위치로 계산한다. 수신 완료만으로 `playback.done`을 보내지 않는다.
  취소·초기화 시 아직 재생하지 않은 데이터와 클립도 버린다.
- 두 채널에 같은 mono 샘플을 넣는다. 이 PC에서 native mono AudioClip 출력이 기존 렌더러보다
  약 0.707배로 측정되어 음량 차이를 줄이기 위한 처리다. 예전 `Compare last reply/AudioClip` 메뉴는
  mono이므로 그 메뉴를 쓸 때는 음량 차이를 감안해야 한다.
- 비교 모드의 끼어들기는 기존 유예 시간 뒤 짧은 감쇠로 멈춘다. 렌더러의 정확한 샘플 경계 정지는
  지원하지 않으므로 끼어들기 품질 비교에는 쓰지 않는다.
- `output.state.playback_mode`는 0=스트리밍, 1=전체 수신이다. native DSP 출력량을 계측하지 않으므로
  이 모드의 `rendered`, `callbacks`는 **-1(미측정)**이다. `OutputPeak=0`도 무음이라는 증거가 아니다.
- 수신 원음, 음성 생성 시점의 문장 분할, 공통 출력 장치는 두 방식에서 여전히 영향을 줄 수 있다.

## 10. 웹 생성 방식별 사용자 청취 결과

사용자가 웹 조각 수신 테스트에서도 다음을 확인했다.

| 생성 방식 | 사용자 청취 |
|---|---|
| 문장별 생성 | 각 문장 끝에서 잘림 |
| 전체 문장 한 번에 생성 | 마지막 문장 끝에서 잘림 |

잘리는 위치가 각 TTS 요청의 마지막에 대응한다. 앞선 D 실험과 같은 패턴이며,
Unity만의 실시간 재생 버퍼 문제라는 가설을 더 약화한다. 전체 문장 생성은 중간 문장 문제를
피했지만 마지막 문장까지 해결한 것은 아니다.

읽기 전용으로 현재 서버의 전송 코드를 재확인했다. `tts_omni.py`, `tts_server.py`,
`realtime_tts.py`는 로컬 검토본과 서버 파일 해시가 모두 일치한다. 설치된 엔진의
`serving_speech.py`는 PCM 청크를 전부 `speech.audio.delta`로 내보낸 다음
`speech.audio.done`을 내보낸다. done에는 사용량 정보가 있고 별도의 마지막 음성은 없다.
따라서 done에 든 음성을 클라이언트가 무시하는 문제는 해당 코드에서 발견하지 못했다.
API 중계와 브라우저 수집 코드에도 의도적으로 마지막 PCM을 절단하는 처리는 없다.

현재 가장 유력한 범위는 Qwen의 요청 종료 시 음성 생성·디코딩 및 참조 조건이다.
정확한 내부 원인이나 물리적 출력 장치까지 확정·배제한 것은 아니다.
앞서 실패한 EOS 억제·코덱 프레임 복제·더미 발화 보정을 해결책으로 다시 적용하지 않는다.
이번에는 추가 합성·운영 설정 변경·Unity 재생 코드 수정 없이 결과를 기록했다.

## 13. 생성 회차를 공유하는 웹 A/B 비교

사용자는 난수로 원인을 설명하는 대신 실제 웹 테스트의 차이를 하나씩 줄이기로 했다.
첫 단계로 같은 한 번의 생성 PCM을 공유하는 두 플레이어를 추가했다.

- A: 원격 Python `wave`로 완성한 WAV를 로컬 HTTP 파일로 재생한다.
- B: 기존 브라우저 조각 수집기로 같은 PCM을 모아 Blob WAV로 재생한다.
- 원격 정상 종료, 서버 WAV의 형식·길이·PCM 해시와 브라우저 WAV의 전체 바이트 일치를
  확인한 다음 두 플레이어를 준비한다. 두 플레이어는 자동 재생하지 않고 preload도 같다.
- 기본 대사를 기존 비교의 첫 문장으로 맞추고, 생성 방식은 전체 한 번으로 시작한다.
  모델·샘플링·참조 준비·문장 간격 설정은 변경하지 않았다.

실제 Qwen에서 전체 생성(한 문장) 1회와 문장별 생성(두 문장) 1회를 검사했고 각각의 A/B는
전체 WAV 바이트가 같았다. 두 플레이어의 끝까지 재생, 취소, 캐시 정리도 통과했다.
이는 수신·재생 기능 검사다. 이후 사용자는 **둘 다 완전히 똑같이 잘린다**고 청취 결과를 전달했다.
이번 전달에서 정확한 대사·생성 모드는 확인되지 않았으므로 별도로 추정해 적지 않는다.

동일 음원의 양쪽에서 동일하게 잘리면 브라우저 조립이 WAV를 훼손한다는 가설을 지지하지 않는다.
그 결과만으로 Qwen 자체가 원인이라고 확정하지 않고 생성 조건과 공통 재생 경로를 계속 구분한다.
두 경로 모두 원래 PCM 스트리밍 합성을 사용하므로 엔진 스트리밍/비스트리밍 비교는 아니다.

사용법과 검사 결과: [웹 TTS 조각 수신 테스트](웹_TTS_조각수신_테스트.md).

다음 단계로 이전 비교 페이지의 등록 음성·회차 1·첫 문장 WAV를 C 플레이어로 추가했다.
2.40초 원본을 새 합성 없이 현재 페이지의 동일한 HTML 오디오 설정으로 재생한다.
실제 HTTP 응답이 원본 전체 바이트와 같고 재생 완료·정리가 동작함을 검사했다.
이후 사용자는 **C는 확실히 안 잘린다**고 확인했다.
이번 C는 예전 파일을 현재 페이지에서도 정상으로 들을 수 있는지 확인하기 위한 대조다.
같은 페이지에서 C는 정상이고 새 합성 A/B는 동일하게 잘리므로, 다음 진단은 과거와 현재의
생성 조건·실제 결과 차이를 중심으로 진행한다. 전송·WAV 조립 위치가 원인이라는 근거는 없다.

사용자에게 생성과 수신을 구분해 설명했다. A/B는 서버/브라우저 중 어디서 조각을 합치는지의
비교였고, 엔진의 완성 후 반환 경로와 현재 스트리밍 생성 경로를 비교한 것은 아니다.
프로젝트의 공식 Qwen `generate_voice_clone` 경로는 완성 파형을 반환하지만, 과거 실험의

## 16. 실제 파형 생성 단계 비교와 운영 복구

`async_chunk`를 제외한 엔진 설정을 유지하고 **조각 파형 생성(true) / 전체 코드가 나온 뒤
파형 생성(false)**를 비교했다. 둘 다 같은 Qwen3-TTS Base·참조 복제·대사·seed이며 HTTP는 SSE다.
앞의 `stream=false` 반환 비교나 `non_streaming_mode` 입력 조건 비교와 구분한다.

GPU 여유가 약 5GiB여서 두 엔진을 동시에 올리지 않았다. 대화 연결 0·TTS 유휴·참조 0을 확인하고
현재 방식 샘플을 만든 뒤, 프로젝트가 관리하는 TTS만 정상 종료했다. 운영 설정 파일을 편집하지 않고
별도 설정 파일·loopback 8014의 임시 엔진으로 전체 파형 샘플을 생성했다. 종료 후 기존 명령으로
TTS 8003·엔진 8004를 복구했다. LLM·대화 API·웹·등록 서비스는 재시작하지 않았다.

- 참조 3종 × 대사 2종 × seed 3개, 두 방식 합계 **36개 WAV**. 참조는 한 번 준비해 두 방식에서 공유했다.

- 18쌍 모두 생성 토큰 수와 최종 샘플 수가 같았다. 18쌍 모두 PCM 값에는 차이가 있었다.
  토큰 개수가 같다는 것만으로 모든 코드북 토큰이 동일하다고 주장하지 않는다.
- 복구 후 참조 3종 × 대사 2종의 seed 41을 대조한 **6/6건이 복구 전 현재 방식과 바이트 동일**였다.
- 운영 `tts.env`, 활성 엔진 설정, `tts_omni.py`, `tts_server.py`의 변경 없음과 임시 포트 종료를 확인했다.
  복구 후 TTS `ready`, `busy=false`, `references=0`, 대화 `ready`, `tts_ready=true`, `connections=0`이다.
- 36개 WAV는 샘플 수·PCM 해시를 검증하고 가공 없이 청취 페이지에 복사했다.
  파형 차이는 청취 개선의 증거가 아니다. 이후 사용자 청취에서도 **두 방식 모두 말끝 잘림이
  지속**됐다. 확인한 네 플레이어의 결과는 아래 17장에 기록하며 모든 참조·회차의 판정으로 확대하지 않는다.

페이지: <http://127.0.0.1:8774/decoder/>. 표시 이름은 **현재: 조각 디코딩 / 비교: 전체 디코딩**이다.
앞의 C/D 음원이나 과거 다른 실험의 E/F 이름과 혼동하지 않는다.

## 17. 진단 중단 시점 정리

사용자의 마지막 보고: "1, 2 똑같이 끊김 3, 4는 맨 끝만 끊김. 이제 실험은 더 하지 말고, 정리좀 하자".
번호는 마지막 파형 생성 비교 페이지의 위에서 아래로 네 플레이어에 대응한다.
사용자가 선택한 참조·회차는 이번 보고에서 명시하지 않았으므로 임의로 확정하지 않는다.

| 번호 | 대사와 생성 방식 | 사용자 청취 |
|---|---|---|
| 1 | 한 문장 · 조각 디코딩 | 끝 잘림 |
| 2 | 같은 한 문장 · 전체 디코딩 | 1번과 동일하게 잘림 |
| 3 | 세 문장을 한 요청으로 · 조각 디코딩 | 중간 문장은 괜찮고 맨 끝만 잘림 |
| 4 | 같은 세 문장을 한 요청으로 · 전체 디코딩 | 맨 끝만 잘림 |

확인된 범위:

- Unity 없이 저장 WAV·브라우저에서도 증상이 있으므로 Unity 재생 버퍼 하나로 설명할 수 없다.
- 같은 PCM의 서버 WAV/브라우저 조립 WAV는 바이트가 같고 청취도 같았다. 엔진 SSE/완성 반환도
  18쌍 모두 PCM이 같았다. 검사한 전달·조립 경로에서는 샘플 손실을 찾지 못했다.
- 실제 파형 생성을 조각/전체로 바꿔도 마지막 청취 증상이 지속됐다. 전체 디코딩은 해결책이 아니다.
- 문장별 요청이면 문장마다, 여러 문장을 한 요청으로 만들면 마지막에서 증상이 나타난다.
  따라서 현재 가장 유력한 문제 범위는 **TTS 생성 요청이 끝날 때의 음성 생성·마무리와 참조 조건**이다.
- 이전 C 저장본의 첫 문장은 사용자가 정상이라고 확인했다. 같은 보관 코드를 재실행한 D는
  잘림이 보고됐다. 정상 파일이 존재하므로 Qwen이 항상 잘린다거나 모델 자체가 확정 원인이라고 단정하지 않는다.

미확정 범위:

- 모델이 발음을 충분히 생성하기 전에 종료하는지, 마지막 음성 코드의 파형 처리 문제인지,
  참조 음성·전사 조건이 영향을 주는지 아직 구분하지 못했다.
- 과거 정상 생성과 현재 실패를 가르는 정확한 조건은 찾지 못했다. 난수·참조·재생 장치를
  증거 없이 확정 원인으로 채택하지 않는다. 샘플 수·해시 일치는 청취 품질 통과가 아니다.

운영·자료 상태:

- 직전 비교 종료 때 기존 Qwen3-TTS Base 스트리밍 설정으로 복구했고 TTS·대화 API의 ready를 확인했다.
  이 정리 작업에서는 서비스를 다시 호출하거나 재시작하지 않았다.
- 전체 디코딩·끝 기호·더미 발화·코덱 복제·EOS 억제를 해결 패치로 적용하지 않았다.
- Unity의 전체 수신 AudioClip 비교 모드와 웹 진단 도구는 남아 있다. 마지막 Unity 실사용 확인은
  전체 수신 모드였고, 이번에는 현재 Editor 선택값을 새로 조회하거나 바꾸지 않았다.
  "TTS 복구"를 Unity의 기존 실험 코드까지 모두 되돌렸다는 뜻으로 설명하지 않는다.
- 마지막 청취 결과는 `tools/_work/browser_pcm_20260917/decoder-listening-feedback.json`과
  청취 묶음의 `manifest.json`에도 남긴다. 기존 생성·검사 보고서는 당시 기록으로 보존한다.

추가 합성·모델 변경·설정 변경·새 청취 비교를 중단한다. 문제 상태는 **미해결**이며,
사용자가 다시 작업 범위를 정하기 전까지 새 실험을 진행하지 않는다.

## 18. 사용자 요청: 200ms 고정 패킷과 스트리밍 재생 복귀

사용자는 진단 중단 자체가 아니라 효율적인 진행을 원한다고 정정한 뒤, 짧은 마지막 조각도
200ms로 맞추고 예전처럼 조각을 받는 대로 재생하도록 변경을 요청했다. 이 변경만 구현했다.

- `tts_server.py`에서 정상 전송 PCM은 매번 4,800샘플·9,600바이트다.
  중간 잔여는 다음 조각과 합쳐 원음 사이에 무음이 들어가지 않도록 한다.
- 각 TTS 요청의 정상 종료 때 마지막 잔여에만 0 이상 200ms 미만의 무음을 붙인다.
  정확한 배수이면 추가 패킷·무음이 없다. 오류·취소 시 남은 PCM을 패딩해 내보내지 않는다.
- 기존 모델·참조·샘플링·문장 분할·150ms 문장 사이 간격은 유지한다. 엔진은 계속 `async_chunk=true`,
  TTS는 `generation_pcm`이다. 전체 답변을 기다리는 서버 모드를 추가하지 않았다.
- Unity의 기존 메뉴 `Tools/Dialogue/Playback mode/Stream as received`를 실행했다.
  Console의 수신 즉시 스트리밍 선택 메시지와 이 프로젝트의 EditorPrefs 값 false를 확인했다.
  Scene_2는 편집 모드였으며 씬·소스 파일 저장 없이 다음 Play의 재생 설정만 바꿨다.
- Unity MCP의 임시 코드 실행은 Mono 명령 길이 오류로 실패해 사용하지 못했다.
  기존 메뉴 실행과 설정 확인은 성공했다. 이를 새 Unity 코드의 컴파일 오류로 보고하지 않는다.

Claude Code가 서버 한 파일의 구현안을 작성하고 메인이 검토·적용했다. 빈 스트림의 거짓 성공을
거부하는 처리와 송신 전에 버퍼를 비우는 순서를 보완했다. 메인은 원음 보존·패딩·정확한 배수·
첫 패킷 조기 전송·오류·취소·legacy 경로를 검증했다.

- `python tools/check.py --area dialogue`: 하네스 195 + 서버 291 = **486개 통과**, 건너뜀 0.
  결과: `tools/_work/checks/20260917T045723Z-dialogue-e0dbf2ca/report.json`.
- 명시된 서비스 번들에서 `tts_server.py`만 적용했다. 백업:
  `~/capstone-server/backups/tts_packet_200ms_20260917T045941Z/`.
- 배포 전후 파일 해시, TTS ready·고정 패킷 health 표시, 대화 API ready·tts_ready를 확인했다.
  엔진 코드·설정·환경 파일은 그대로이며 대화 API PID도 유지됐다.
- 결과 묶음: `tools/_work/tts_packet_200ms_20260917/`의 `deployment.json`,
  `unity-playback.json`, `live-check.json`. 실제 합성은 한 문장 한 번으로 제한했다.
- 실제 합성 결과: 12개 패킷 모두 9,600바이트·200ms. 원음 53,760샘플 뒤에
  무음 3,840샘플·160ms가 붙었으며 총 57,600샘플이었다. 첫 PCM은 TTS 요청 후
  0.187초, 생성 완료는 0.609초로 완료 전 전송도 확인했다. 전체 대화 응답 시간 측정은 아니다.
  참조 해제 후 TTS는 ready·busy=false·references=0이었다. 이 검사는 청취를 포함하지 않는다.

이번 변경의 청취 판정은 아직 없다. 원래 생성 음절이 불완전하면 무음만으로 복원되지 않으며,
기능 검사를 말끝 잘림 해결로 보고하지 않는다.

### 200ms 적용 후 Scene_2 확인과 사용자 청취

Scene_2의 실제 3턴 로그를 같은 trace의 서버 로그와 대조했다. 각 턴의 TTS 패킷은 20·14·11개,
총 45개였으며 별도 문장 사이 무음 150ms 패킷은 턴마다 1개씩이었다.
서버 송신·Unity 수신·재생 소비는 각각 99,600·70,800·56,400샘플로 일치했고 언더런은 0이었다.
구절별 송신 개수·샘플 합계가 패킷 상한 4,800샘플에 정확히 도달해 TTS 패킷이 모두 200ms임을
검증했다. 개별 PCM 패킷 덤프를 저장한 검사는 아니다.
결과: `tools/_work/tts_packet_200ms_20260917/scene2-received/packet-verification.json`.

각각 몇 ms였는지는 기존 대화 로그에 없어 복원할 수 없다. TTS API가 응답하는
`source_samples`·`padding_samples`는 현재 대화 클라이언트가 별도로 저장하지 않는다.
이후 사용자는 **여전히 끊긴다**고 보고했다. 위 수량 검사를 청취 개선으로 해석하지 않는다.

## 19. 사용자 요청: 전송 패킷을 50ms로 축소

동일한 생성·재생 경로에서 TTS API 출력 크기만 200ms에서 50ms로 줄이는 변경이다.
24kHz mono PCM16 기준 패킷마다 1,200샘플·2,400바이트이며, 정상 종료 마지막 잔여에만
0 이상 50ms 미만의 무음을 붙인다. 엔진 입력 조각의 상한은 기존 9,600바이트를 유지한다.
문장 사이 150ms 무음·캐시 대기 리액션·모델·참조·엔진 설정·Unity 소스는 변경 대상이 아니다.

검사·배포 자료는 `tools/_work/tts_packet_50ms_20260917/`에 기록한다.
청취 개선은 별도 사용자 확인 대상이다.

- Claude Code의 구현안을 메인이 검토·적용했다. `tts_server.py`와 관련 기존 검사 두 파일만
  수정했으며 엔진 입력 9,600바이트 수용·원음 보존·최종 패딩·조기 전송·오류·취소를 확인했다.
- `python tools/check.py --area dialogue`: 하네스 195 + 서버 291 = **486개 통과**, 건너뜀 0.
  결과: 위 자료 폴더의 `checks/report.json`.
- 서비스 번들에서 `tts_server.py`만 반영했다. 백업:
  `~/capstone-server/backups/tts_packet_50ms_20260917T051656Z/`.
  파일 해시 일치, TTS ready·`audio_packet_ms=50`·`audio_tail_padding=true`, 대화 API의
  ready·tts_ready를 확인했다. 엔진 코드·환경·설정과 대화 API PID는 유지됐다.
- 실제 Qwen 합성 한 번에서 **45개 패킷 모두 2,400바이트·50ms**였다.
  원음 53,760샘플 + 최종 무음 240샘플 = 총 54,000샘플이다. 이 합성의 마지막 패킷은
  원음 40ms + 추가 무음 10ms이며, 위 Scene_2의 과거 3턴에서 측정한 값은 아니다.
  TTS 요청 후 첫 PCM 0.197초, 완료 0.638초로 완료 전 전송을 확인했다.
  참조 해제 후 ready·busy=false·references=0이었다. 결과: `live-check.json`.
- Unity MCP로 Scene_2 편집 모드와 기존 수신 즉시 스트리밍 재생 로그를 확인했다.
  Unity 소스 변경이나 새 Play 실행은 하지 않았다. Scene_2에서의 50ms 실제 청취는 아직 미확인이다.

## 20. 사용자 청취: 문장 끝 음절의 받침 유무

50ms 변경 후 사용자는 같은 끊김이 지속된다고 보고했다. 이어 `http://127.0.0.1:8773/`에서
받침 없는 마지막 음절은 잘리고 받침을 추가하면 정상이라는 차이를 보고했다.

| 사용자가 제시한 입력 | 마지막 음절 | 사용자 청취 |
|---|---|---|
| 고맙다 | 다: 받침 없음 | 잘림 |
| 고맙지 | 지: 받침 없음 | 잘림 |
| 고맙직 | 직: 받침 있음 | 정상 |
| 고맙닥 | 닥: 받침 있음 | 정상 |
| 고맙닷 | 닷: 받침 있음 | 정상 |

위 표는 사용자의 보고이며 새 합성·독립 청취로 재검증한 자료가 아니다. 참조·반복 횟수·A/B
플레이어 선택·각 항목의 정확한 문장부호는 별도 기록되지 않았다. 모든 한국어 모음·받침에서
항상 재현된다는 검증으로 확대하지 않는다.

읽기 전용으로 확인한 경로:

- 실제 8773 리스너는 `tools/tts_browser_check.py`이며 A(서버 WAV)·B(브라우저 조립 WAV)·
  C(보관 Qwen 음원) 페이지다. 새 입력 합성은 A/B용이고 C는 과거 정적 파일이다.
- 원격 worker는 등록 참조를 대화 API에서 준비한 뒤 `TTSClient`로 현재 TTS API를 호출한다.
  입력 문장을 Gemma 답변 생성이나 Unity 재생에 통과시키지 않는다.
- `tts_browser_worker.py`의 `emit_audio`·`build_wav`, 브라우저의 `StreamCollector`·`pcmToWav`는
  PCM 길이·순서·해시를 검사해 그대로 모은다. 출력 끝부분 무음 제거·VAD·페이드 처리는 없다.
- `tts_omni.py`는 엔진 PCM을 순서대로 나눠 전달한다. `tts_server.py`는 현재 50ms로 재분할하고
  최종 잔여에 무음만 추가한다. 애플리케이션 코드에서 받침 없는 마지막 글자를 지우는 처리는 없다.

이 관찰은 **마지막 음절의 발음 특성과 합성 종료 처리의 연관성**을 우선 조사할 근거다.
받침 추가는 텍스트 토큰화와 생성되는 음성·길이도 바꾸므로, 이것만으로 음성 코드의 조기 종료,
최종 파형 복원, 참조와 발음 조건 중 하나를 확정할 수 없다. 받침을 임의로 덧붙여 발음을 바꾸는
우회 처리는 적용하지 않았다. 이번 확인에서는 합성·재시작·운영 코드 변경을 하지 않았다.

## 21. 같은 음성 코드를 사용한 조각·전체 복원 비교

사용자 요청으로, 동일 문장을 두 번 합성하던 비교 대신 **한 번 생성된 실제 디코더 입력 코드**를
관찰하여 조각 복원 A와 전체 복원 B를 만드는 검사를 준비했다. 자료:
`tools/_work/tts_samecodes_20260917/`.

- 입력은 `고맙다.`, `고맙닥.`, `고맙지.`, `고맙직.`이다. 등록 음성·공개 한국어·공개 영어 참조,
  3회차(seed 41·42·43)의 36쌍을 준비한다. 참조 원음·전사는 원격 메모리에 유지하며 보고서에 싣지 않는다.
- A는 현재 엔진의 조각 복원 결과다. B는 겹치는 과거 코드 문맥을 제거하고 모은 동일 생성 코드와
  동일 참조 문맥을 **같이 로드된 디코더 인스턴스**로 한 번에 복원한다. 합계 300프레임 미만으로
  제한하여 B가 내부에서 다시 조각으로 나뉘지 않게 한다.
- PCM 변환은 실제 엔진의 `soundfile.write(..., format='RAW', subtype='PCM_16')`와 같다.
  별도 무음 추가·페이드·정규화·끝부분 자르기·보조 대사·EOS 보정은 하지 않는다.
- 관찰 A와 실제 엔진 SSE PCM의 바이트 일치, 각 조각과 전체의 샘플 수, 문맥 코드 중복 일치,
  완료 응답의 출력 토큰 수에서 EOS를 뺀 값과 수집한 생성 프레임 수의 일치를 요구한다.
  마지막 비어 있지 않은 조각에 종료 표시가 없을 수도 있으므로 조각마다 복원 기록을 갱신하며,
  **API 완료와 위 수량 검사를 모두 통과한 마지막 기록만** 청취 파일로 인정한다.
- 이 검사에서 추가 전체 복원은 관측용 계산이다. 생성·복원 시간은 운영 지연 측정값으로 쓰지 않는다.
- 설치된 라이브러리를 수정하지 않고 실험 프로세스에만 임시 관찰 코드를 연결한다. GPU 여유 확보를 위해
  자체 TTS만 일시 교체하며, 끝나면 운영 TTS ready·50ms·파일 해시·대화 PID 보존을 확인한다.

B만 정상이라면 조각 복원 경로가 원인 후보가 된다. 둘 다 잘린다면 공통 디코더의 끝 처리와
생성 코드 자체의 끝부분 문제는 이 비교만으로 구별할 수 없다. 코드·샘플 보존을 청취 정상으로
판정하지 않는다. 검사 준비 당시 청취는 보류였으며, 이후 등록 음성의 사용자 판정은 23장에 기록했다.

실행 결과:

- 첫 실행은 내부 관찰 기록이 없어 유효 비교로 인정하지 않았고, 즉시 운영 TTS를 복구했다.
  종료 표시가 없는 경우에도 조각별 기록을 유지하도록 보완한 뒤 재실행했다.

- 실제 **36쌍·72 WAV**를 생성했다. 모든 쌍에서 생성 코드 수(`output_tokens - 1`), 조각별·전체
  샘플 수, 참조 캐시 보존, A와 실제 SSE PCM의 바이트 일치가 확인됐다. 생성 코드 7~22프레임,
  참조를 포함한 전체 디코더 입력 65~94프레임으로 B의 내부 재분할은 없었다.

  전체 PCM까지 완전히 같은 경우는 3쌍이다. 나머지 앞부분 차이도 int16 기준 최대 15이며,

- 짧은 입력은 생성 코드 전체가 기존 과거 문맥 길이 이내에 들어간다. 따라서 마지막 조각 복원에서도
  전체 생성 코드를 함께 보게 되는 조건이다. 이 자료는 이 조건에서 **조각 복원과 전체 복원의 차이로
  마지막 음성이 달라진다는 가설을 지지하지 않는다.** 모든 길이의 문장이나 공통 디코더 자체의

  결과: `data/report.json`. 운영 코드 변경은 없다.
- 청취: `http://127.0.0.1:8774/same-codes/`. 참조 3종×회차 3종의 9개 선택 조합과
  72개 WAV 형식·해시·브라우저 로딩을 확인했다. `browser-validation.json`에 기록했다.

## 22. 청취 보류 후 종료 경계 분석

사용자는 당시 들을 수 없으므로 21장의 직접 평가는 **보류**하고 다음 분석으로 진행하도록 지시했다.
36쌍의 청취 결과를 정상·잘림으로 임의 등록하지 않는다. 이 단계에서는 새 TTS 합성·서비스 재시작 없이
이미 생성한 WAV와 실제 설치된 코드·토크나이저를 검사했다.

- `고맙다/고맙닥/고맙지/고맙직/고맙닷`에 마침표를 붙인 경우와 없는 경우, 총 10개를 실제
  `build_assistant_text`와 모델 토크나이저의 `input_ids[3:-5]`로 왕복 확인했다. **10/10개에서
  마지막 글자와 문장부호가 그대로 보존**됐다. 결과: `data/text-boundary-report.json`.
- 길이 정렬용 `CausalTransConvNet.forward`의 AST는 설치된 공식 Qwen 구현과 동일하다.
  오른쪽 정렬 영역을 자르는 코드가 있다는 사실만으로 버그라고 판단하지 않는다. 커널 길이 K,
  stride S일 때 전치 합성곱 출력 `N*S+(K-S)`를 `N*S`로 맞추는 처리는 모델의 원래 구조다.
  공유 디코더가 특정 종료 코드에서 발음을 충분히 복원하는지까지 검증한 것은 아니다.
- 현재 준비된 참조의 토큰 수와 WAV 길이·코덱 설정으로 계산한 프레임 수를 대조했다.
  네 대사의 전체 텍스트가 세 참조 모두 초기 입력에 포함될 길이였으며, 후속 생성 단계로 남는
  텍스트는 0단계다. 초기 입력 여유는 110·34·67단계다. 참조 코드 수는 실제 인코더 실행값이 아닌
  준비 WAV 길이에서 계산한 값이며, 원음·전사는 보고서에 저장하지 않았다.
  결과: `data/reference-text-fit.json`.
- 기존 36개 WAV에서 문장당 9회 결과의 생성 프레임 수 중앙값은 다 8·닥 10·지 13·직 10이다.
  받침 유무만으로 생성 길이를 단순 분류할 수 없으므로 **짧으면 조기 EOS, 길이가 같으면 디코더 문제**라는
  판정은 채택하지 않았다. 말끝 RMS도 발음 완성 여부를 증명하지 않는다. `tail-analysis.json`에 기록했다.
- `고맙다`와 `고맙지`의 생성 코드·전체 PCM 해시는 같은 참조/seed의 9쌍 모두 달랐다.
  두 입력을 통째로 같은 음성으로 처리했다는 가설 역시 이 자료가 지지하지 않는다.
  결과: `cross_text_comparison.json`.
- Claude Code의 읽기 전용 분석은 확보했지만, 샘플 수·받침별 길이·의도된 정렬 크롭만으로
  원인을 단정하는 제안은 채택하지 않았다. 과거 EOS 억제·마지막 코드 복제 실험 자료도 대조했으며
  이를 새 해결책으로 반복하거나 운영에 적용하지 않았다.

후속 우선순위는 **생성 종료 시점의 발음 완성 여부**다. 입력 마지막 글자 누락·수신 조각 손실보다
조사 범위를 이쪽으로 좁혔으며, 공통 디코더의 종료 경계는 대안 가설로 남긴다. 다음 원인 분리는
완성된 원음을 코덱 인코딩→복원에만 통과시켜, 텍스트 음성 생성 없이도 말끝이 손상되는지를 보는
방식이 적절하다. 이 시점에는 코덱 왕복 검사를 실행하지 않았으며, 후속 실행 결과는 23장에 기록했다.

## 23. 등록 음성의 3회차 청취 결과와 디코더 분리 검사

사용자가 `http://127.0.0.1:8774/same-codes/`에서 **등록 음성·1~3회차**를 직접 청취했다.
회차마다 말투는 조금 달랐지만 아래 결과는 같았으며, A(조각 복원)와 B(같은 코드 전체 복원)는
동일한 오디오로 들렸다고 보고했다.

| 항목 | 입력 | A/B 사용자 판정, 등록 음성 1~3회차 |
|---|---|---|
| 1 | 고맙다. | 모두 말끝 잘림 |
| 2 | 고맙닥. | 모두 부드럽게 끝남 |
| 3 | 고맙지. | 모두 말끝 잘림 |
| 4 | 고맙직. | 모두 부드럽게 끝남 |

기록: `tools/_work/tts_samecodes_20260917/user-listening.json`.
이는 등록 음성의 12쌍에 대한 사용자 판정이다. 공개 한국어·영어 참조의 판정으로 확대하지 않는다.
이 조건에서는 조각/전체 복원의 차이가 잘림을 설명하지 못하지만, 공통 디코더와 생성 코드 중
어느 쪽 문제인지는 아직 구별되지 않는다.

사용자 지시에 따라 후속으로 다음 세 검사를 순서대로 실행했다. 작업 폴더는
`tools/_work/tts_decoder_checks_20260917/`이다.

1. 디코더가 반환한 원시 파형과 문맥·길이 처리 후 실제 엔진 PCM을 비교한다.
2. 동일한 생성·참조 코드를 현재 구현과 설치된 공식 Qwen 디코더로 복원한다.
3. 과거 끝음절 비교에서 사용한 생성 음원을 인코딩→복원하여 텍스트 음성 생성 없이 비교한다.

2번은 CPU·float32·eager·가중치·코드를 맞춘다. 공식 소스를 현재 Transformers에 직접 불러오는
준비 검사에서 API 호환 오류가 났으므로, 실제 비교는 **각각의 기존 설치 환경**에서 수행한다.
공식 환경은 Torch 2.8.0/Transformers 4.57.3, 현재 환경은 Torch 2.11.0/Transformers 5.17.0이다.
공식 디코더 계산식이나 설치 파일은 수정하지 않는다. 결과가 다르면 구현과 의존성 차이를 분리할
수 없다는 제한을 유지한다. 원래 공식 환경의 로드·합성 코드 입력 호환 검사는 통과했다.

관찰 코드의 정상·종료 표시 없음·의도적인 오른쪽 여분·샘플 누락 대조 검사 4개를 통과했다.
오른쪽 여분을 발견하고 누락을 오류로 잡으며, 실제 반환 파형과 임시 메서드 복구를 보존하는지 확인했다.
참조 코드가 포함된 입력은 권한 0700의 서버 tmpfs에만 임시 저장하고 비교 종료 시 삭제한다.
새 산출물의 청취 판정은 기존 21장 자료의 사용자 판정과 별개다.

실행 결과:

| 검사 | 실측 결과 | 판단 범위 |
|---|---|---|
| 1. 원시 파형 → 길이 처리 → 엔진 PCM | 36개·86조각 모두 생성 구간의 원시 파형과 반환 파형 일치. 오른쪽에서 제거한 샘플 0개. 전체 복원 경로도 0개 | 파형 반환 **이후** 문맥·길이 처리에서 말끝을 버린다는 가설을 지지하지 않는다. 디코더 내부 합성곱의 의도된 정렬 처리까지 검증했다는 뜻은 아니다 |

- 1번을 위해 다시 얻은 36개 코드 해시와 생성 PCM은 **이전 same-codes의 36개와 전부 동일**했다.
  따라서 등록 음성 12쌍의 기존 청취 결과를 이번 동일 파일에 연결할 수 있다.
  자료: `data/prior-listening-equivalence.json`.
- 2번 CPU 비교는 각 환경의 설치된 디코더를 수정 없이 실행했다. 앞서 시도한 호환 어댑터는
  실제 결과에 사용하지 않았다. 가중치를 같은 캐시에서 엄격하게 로드하고, 모든 학습 파라미터를
  float32로 비교했다. GPU 대조의 마지막 250ms RMS 비율은 등록 음성에서 CPU/GPU 기준
  약 0.994~1.006이다. 이 에너지 수치를 음절이 완성됐다는 증거로 사용하지 않는다.
- 3번 원본은 과거 끝음절 비교 페이지의 합성 결과이며 참조 원음이 아니다. 9개 모두 24kHz여서
  재표본화도 없었다. 무음 추가·정규화·결과 길이 자르기를 하지 않고 복원 전체를 저장했다.
  과거 비교 세트에 대한 정상 보고와 이번 9개 개별 원본·왕복의 청취 판정은 구별한다.
- 청취 페이지: `http://127.0.0.1:8774/decoder-checks/`.
  1단계는 처리 전/후, 2단계는 현재 GPU/현재 CPU/공식 CPU, 3단계는 원본/왕복 결과다.
  27개 선택 조합·198개 WAV의 브라우저 순차 로딩, 파일 길이, 스크립트 오류 없음과 실제 재생 진행을
  확인했다. 초기 재생 검사에서 350ms 안에 시간이 진행되지 않았지만, 초기화 대기를 둔 재검사에서는
  약 1.16초에 재생이 진행됐다. 이 브라우저 검사 시간을 TTS 응답 지연으로 해석하지 않는다.
- 핵심 결과: `data/verification-summary.json`, `data/stage1/report.json`,
  `data/stage2/report.json`, `data/stage3/report.json`, `browser-validation.json`.
  생성·관찰 코드는 Claude Code의 편집안을 메인에서 검토·수정·실행했다.
- 운영 TTS ready·50ms, 대화 API ready/tts_ready·연결 0개, 자체 임시 엔진 종료,
  운영 파일 해시·대화 PID 보존을 확인했다. 참조 코드의 tmpfs 작업 폴더는 삭제했고,
  설치 파일·운영 코드·Unity는 변경하지 않았다. `data/final-health.json`, `data/overall.json` 참조.

검사 실행 직후 결론은 **복원 후 뒤쪽 샘플을 버리는 처리와 현재/공식 CPU 구현 차이에서는 원인이
드러나지 않았다**는 것이었다. 당시 GPU/CPU와 코덱 왕복의 직접 청취는 보류했으며,
이후 사용자가 전달한 결과와 다음 조사 범위는 24장을 따른다.

## 24. 디코더 분리 검사의 사용자 청취 판정

사용자가 `http://127.0.0.1:8774/decoder-checks/`를 청취한 뒤 다음 결과를 보고했다.

| 단계 | 사용자 청취 결과 | 해석 |
|---|---|---|
| 1. 잘라내기 전/현재 방식 | 완전히 동일. `고맙다.`, `고맙지.`는 잘리고 `고맙닥.`, `고맙직.`은 안 잘림 | 뒤쪽 길이 처리에서 새로 생긴 잘림이 아님 |
| 2. GPU/CPU·구현 비교 | GPU나 CPU 차이에 따른 차이점 없이 모두 동일 | 이 청취 조건에서는 연산 환경이나 복원 구현 교체가 말끝을 복구하지 못함 |
| 3. 입력 원본/왕복 결과 | 양쪽 모두 끝부분 잘림 없음 | 정상 음성을 코드화→복원한 경우 말끝을 보존할 수 있음 |

원문 기준 구조화 기록: `tools/_work/tts_decoder_checks_20260917/user-listening.json`.
이번 보고에는 페이지의 참조·회차·3단계 모델 선택 범위가 명시되지 않았다. 따라서 사용자가
청취한 항목의 결과로 기록하며, 자동 검사 36개 및 왕복 9개 전체를 청취 합격으로 바꾸지 않는다.
앞선 `same-codes` 등록 음성 1~3회차의 명시적 판정은 별도로 그대로 유지한다.

이제 원인 조사의 우선순위는 **텍스트에서 음성 코드를 생성하는 단계**로 옮긴다.
이번 결과는 정상 코드를 복원할 수 있는데도 문제 입력으로 생성한 코드는 여러 복원 경로에서
같은 잘림을 보인다는 근거다. 복원·전송·재생 방식 변경을 반복할 근거는 약해졌다.
다만 정상 원음을 인코딩한 코드와 TTS가 직접 생성한 코드는 같지 않으므로, 디코더가 모든 입력에서
정상이라고 수학적으로 증명된 것은 아니다. **생성 단계가 유력하다는 결론**과 **조기 EOS 확정**을 구별한다.

다음 조사에서는 마지막 음절이 불완전한 코드를 생성하는 경우와, 충분히 발음하기 전에 종료 토큰을
선택하는 경우를 구별한다. 종료 토큰은 `codec_eos_token_id=2150`이며 공식 생성기는 이 토큰 이전의
음성 코드를 사용한다. 기존 공식 생성 실험에서는 180단계 상한보다 짧은 16·18·45단계에서 EOS가
1개씩 관측됐으므로, 그 사례를 단순 생성 길이 상한 문제로 처리할 근거는 없다.

기존 보정 실험도 다시 대조했다. EOS를 두 단계 막은 E는 실제 생성이 4~20프레임 더 이어졌고
사용자는 말끝 잘림·숨소리를 보고했다. 마지막 코드를 복제한 F는 발음 반복을 만들었다.
이 두 방법이나 더미 대사 추가를 새 해결책으로 반복 적용하지 않는다. 이번 후속은 청취 기록과
기존 코드·실험의 읽기 전용 분석이며, 새 합성·서버 재시작·운영 코드 변경은 하지 않았다.

## 25. 복원기의 끝 경계를 더 확실하게 구분하는 방법

사용자는 복원 단계가 원인일 가능성이 낮은지와 더 확실한 확인 방법을 물었다.
정상 원음의 인코딩 코드와 실패한 TTS 생성 코드는 다르므로, 정상 음원의 왕복 성공만으로
특정 생성 코드에서 생기는 문제까지 완전히 배제하지는 않는다.

새 합성에 앞서 기존 E/F WAV의 파일 해시를 검증하고, **원래 음성 길이에 해당하는 공통 구간**을
수치로 비교했다. E에서 원래 코드 접두부가 같았다는 것은 당시 캡처 보고서를 근거로 한다.
참조 코드가 포함된 원본 배열은 이미 폐기했으므로 이번에 배열을 다시 검사한 것은 아니다.

| 기존 입력 | E에서 늘어난 구간 | 원래 구간 비교 | 마지막 250ms RMS 비율(E/기준) |
|---|---:|---|---:|
| 잘 지내고 있지. | 1,360ms | PCM 완전 일치 | 1.000000 |
| 뭐하고 있었어? | 1,600ms | RMS 차이 0.000421, SNR 52.49dB | 0.999796 |
| 오늘은 날씨가 좋아서 같이 산책하고 싶어. | 320ms | RMS 차이 0.001004, SNR 41.36dB | 1.002304 |

F의 기존 구간도 첫 문장은 완전 일치, 나머지는 차이가 있었다. E/F는 공식 CPU/bfloat16/SDPA
검사였으므로 길이 변화에 따른 수치 차이와 실제 끝 경계 영향을 이 결과만으로 분리하지 않는다.
이 수치로 음절 완성도를 판정하지 않으며, **공통 구간이 같다는 것과 추가 시간에 말끝이 나오는지**도
구별한다. 결과: `tools/_work/tts_decoder_checks_20260917/data/old-eos-prefix-review.json`.

추가 실험 후보는 원래 생성 코드를 고정하고, 실제 무음을 인코딩해 얻은 짧은 코드만 뒤에 붙여
복원하는 종료 경계 검사다. PCM에 무음을 덧붙이는 것이 아니라 디코더에 후속 입력을 주는 검사이며,
마지막 음성 코드를 복제하거나 TTS의 EOS를 억제하는 방법과 구별한다. 이 제안은 이후 사용자 승인으로
실행했으며 결과는 26장에 기록한다.

- 원래 코드·참조 문맥의 해시와 CPU float32 조건을 고정한다. 추가 코드만 단독 복원해 음성 성분이
  없는지 먼저 대조하고, 정상 입력에도 같은 추가를 적용한다.
- 공통 시간 구간의 파형과 추가 시간 구간을 따로 검사한다. 원래 마지막 발음에 해당하는 잔여 음성이
  추가 구간에서 드러난다면 디코더 종료 경계·잔여 출력의 영향을 더 조사할 근거가 된다.
- 단순 무음만 늘고 잘림이 같다면 생성 코드 자체의 부족을 더 지지한다. 추가 코드는 입력 조건을
  바꾸므로, 개선이 있더라도 이를 곧바로 디코더 버그나 운영 해결책으로 확정하지 않는다.
- 필요하다면 이 한 가지 변수를 먼저 검사한다. 동일 조건의 조각/전체·GPU/CPU 비교를 다시
  반복하거나 무음 패딩을 해결된 것으로 운영에 적용하지 않는다.

## 26. 무음 코드 추가 진단 완료와 생성 단계의 초기 분석

사용자 지시: “그럼 일단 진단해보자. 확실하게 짚고 생성단계쪽으로 넘어가보자”.
Claude Code의 진단·실행·청취 페이지 편집안을 메인에서 검토·수정한 뒤 실제 모델로 실행했다.
위치: `tools/_work/tts_silence_boundary_20260917/`.

바꾼 변수는 **원래 음성 코드 뒤에 실제 무음의 코드 4프레임(320ms)을 추가하는 것** 하나다.
2초의 디지털 무음을 같은 인코더로 코드화하고 중앙의 8~11번 프레임을 사용했다.
원래 코드·참조 문맥은 그대로 유지했다. CPU/float32/eager·동일 가중치로 A/B를 복원하며,
PCM 뒤에 무음을 붙이거나 마지막 코드를 복제하거나 EOS를 억제하지 않았다.

문제 비교는 `고맙다.`, `고맙닥.`, `고맙지.`, `고맙직.` × 참조 3개 × 회차 3개로 36쌍,
정상 대조는 기존 VoxCPM2·CosyVoice3·Qwen 음원 각 3개로 9쌍이다.
이 표본 수를 사용자가 모두 청취했다는 뜻으로 사용하지 않는다.

| 확인 항목 | 실제 결과 |
|---|---|
| 추가 코드 단독 복원 | RMS -88.93dBFS, 최대 진폭 -65.17dBFS. 사전 진폭 관문 통과 |
| 원래 코드·기준 음원 재현 | 36/36 입력 코드 해시와 이전 CPU 기준 PCM 완전 일치 |
| A/B의 원래 길이 안 공통 구간 | 문제 36쌍·정상 9쌍 모두 PCM16 차이 최대 1. 문제 구간 float 최대 차이 0.000001967, 최소 SNR 117.15dB |
| 문제 음성 뒤의 추가 320ms | 모든 경우 RMS -90.00dBFS 이하, 최대 순간 진폭 -63.59dBFS 이하. 거의 무음 |
| 정상 대조 뒤의 추가 320ms | RMS -81.40dBFS 이하. 공통 구간 PCM16 차이 최대 1 |
| 길이·파일 | 45쌍 모두 정확히 7,680샘플(320ms) 증가. WAV 101개 해시·24kHz·mono·PCM16 확인 |

**판단:** 무음 코드를 더 줘도 원래 파형에 발음 크기의 변화가 없고, 추가 구간에서도 발음에 해당하는
크기의 출력이 나타나지 않았다. “끝에서 디코더의 잔여 음성을 더 내보내면 복구된다”는 가설을
지지하지 않는다. 이전 처리 전/후·현재/공식·GPU/CPU·정상 음원 왕복 결과와 함께 보면,
조사 중심을 **생성기의 마지막 음성 코드와 종료 결정**으로 옮길 근거가 충분하다.
다만 임의 후속 코드를 붙인 한 가지 조건이며, 모든 코드열에 대한 디코더의 완전성을 증명한 것은 아니다.

생성 직후 새 A/B의 직접 청취는 보류였으며, 이후 전달된 사용자 판정은 28장에 기록한다.
위 수치 자체는 음절 완성도의 청취 합격 판정이 아니다.
기존에 명시적으로 들은 등록 음성 1~3회차의 판정은 기준 코드·PCM 일치로 연결된다.
새 페이지: `http://127.0.0.1:8774/silence-boundary/`.
19개 선택 조합·101개 파일의 브라우저 순차 로딩·재생 길이·스크립트 오류 없음,
음소거 상태에서 실제 재생 시간이 진행되는 것까지 확인했다.

생성 단계는 설치된 코드·설정과 이미 수집한 생성 기록을 먼저 읽어 분석했다.

- 요청의 생성 상한은 600이고, 실제 출력 토큰은 8~23개, 유효 음성 코드는 7~22프레임이다.
  36개 모두 `generated_frames = output_tokens - 1`이므로 길이 상한을 늘릴 근거가 없다.
- 현재 설정의 최소 생성 2개·temperature 0.9·top_k 50·repetition_penalty 1.05는 공식 생성 코드의
  해당 기본값과 같다. 공식 코드의 로컬 보관본과 서버 설치본 해시도 일치했다.
- EOS는 2150이고 유효 코드 인덱스는 0~2047이다. 현재 구현은 EOS 등 무효 첫 코드북 행을
  음성 프레임에서 제외하고, 공식 구현도 EOS 이전 프레임을 사용한다.
- **개별 요청의 실제 종료 사유·마지막 EOS 확률은 이번 캡처에 없다.** 프레임 수와 설정만으로
  조기 EOS를 확정하지 않는다. 다음 관찰 대상은 마지막 단계의 실제 종료 사유·선택 토큰,
  샘플링 보정 전후 EOS 확률, 마지막 유효 프레임의 전달 순서다. 기존 E의 EOS 강제 연장이나
  F의 코드 복제를 다시 실행하지 않았다.

운영 복구: TTS ready·50ms, 대화 ready/tts_ready·연결 0개. 운영 파일 해시와 대화 PID 보존,
임시 8014 엔진 종료, 참조 코드가 있던 tmpfs 삭제·잔여 0개, 운영 TTS의 진단 환경변수 없음 확인.
운영 코드·설치 모델·Unity 변경 없음. 생성 관찰 훅의 추가 복원 연산이 있었으므로 이번 실행 시간을
운영 응답 지연으로 사용하지 않는다. 전체 회귀 검사는 운영 코드 변경이 없어 반복하지 않았다.

주요 증거: `data/verification-summary.json`, `data/result/report.json`,
`data/result/overall.json`, `data/result/final-health.json`, `generation-audit/audit.json`,
`browser-validation.json`, `playback-validation.json`. 검사 도구의 입력 변조·길이 불일치 등
합성 대조 4개도 통과했으며, 이 결과는 실제 모델·청취 판정과 구별한다.

## 27. 고정 길이 전송·무음 패딩 되돌리기

사용자는 200ms 길이를 맞추려고 무음을 추가했던 처리가 원인과 관련 없어 보이므로 되돌리기를 요청했다.
실제 직전 운영값은 후속 변경을 거친 50ms 고정 전송이었다. 200ms·50ms 실험의 누적 버퍼와
마지막 조각 패딩을 모두 제거하고, 엔진 어댑터의 원래 가변 길이 조각 전달로 복구했다.

- `tts_server.py`는 수신한 조각을 같은 바이트·같은 길이로 즉시 보낸다. 조각당 상한은
  9,600 bytes(200ms)이며 고정 길이나 송신 주기를 뜻하지 않는다. 짧은 중간·마지막 조각도 그대로 보낸다.
- 완성 PCM 호환 경로는 최대 9,600 bytes씩 나누며 마지막 잔여를 채우지 않는다.
  정상 종료의 `source_samples`는 송신 원음 수, `padding_samples`는 0이고 `audio_sec`에도 추가 무음이 없다.
- health는 `audio_packet_mode=passthrough`, `audio_packet_max_ms=200`, `audio_tail_padding=false`다.
  고정 길이 의미였던 `audio_packet_ms`는 제거했다. 이를 읽는 현재 운영 소비자는 없고 관련 검사를 갱신했다.
- 이미 승인된 문장 사이 150ms 쉼, 음성 복제·생성·디코더 설정, Unity 재생 방식은 유지했다.
  이 변경은 전송 실험을 정리한 것이며 말끝 잘림을 해결했다고 판정한 변경은 아니다.

Claude Code 편집안을 메인에서 검토·적용했다. 7개 패킷 검사를 가변 길이 계약으로 갱신하고
기존 스트리밍 오류 검사 한 곳의 패킷 수 가정도 복구했다. 짧은 조각의 즉시 전달, 마지막 1샘플,
바이트·조각 경계 보존, 추가 무음 없음, 중간 오류, 취소 뒤 자원 해제와 다음 요청을 확인했다.
