# 웹 설문 v2 — 자료 형식과 사용 방법

작성일: 2026-09-15. 기준 코드: `jw` / `1dae205` 위의 설문 v2 구현.
결정 배경과 문항 설계는 [설문·사전지식 개편 기획](웹_설문_사전지식_개편_기획.md)에 있다.
여기서는 **실제로 구현된 것과 쓰는 방법, 남은 한계**만 적는다.
모의 검사에 더해 실제 브라우저·등록 API·Gemma·Unity Scene_2 확인과 **운영 배포까지 마쳤다**
(→ [9장](#9-실제-검증-결과-2026-09-15)).
Scene_2에서 등록 인물과 대화하는 순서는 [Scene_2 웹설문 테스트](Scene_2_웹설문_테스트.md)에 따로 있다.

## 1. 한눈에 보는 흐름

가상 인물로 한 바퀴 돌려보는 순서다. 실제 참여자 등록도 2단계부터는 같다.

1. 등록 화면(`http://<웹 주소>:8500`)을 연다. 처음 화면은 **빈 설문**이다.
2. 상단 **테스트** → **할머니** 또는 **친구**를 고른다. 설문 입력만 채워지고
   "가상 예시 인물" 표시가 남는다. **사진·음성 파일과 등록 버튼은 사람이 직접** 다룬다.
3. 2단계에서 **한 사람이 말하는** 음성 파일을 고른다. 화자 분리는 하지 않으므로 한 사람만 나오는 녹음을 쓴다.
   휴대폰 녹음(**M4A/AAC**)·MP3·영상 파일도 그대로 올릴 수 있다. 서버가 ffmpeg로 24kHz 모노로
   바꾸며 쉼과 말하기 속도는 보존한다. 설치와 실패 구분은 [등록 웹 README](../Web/README.md)의
   '오디오 변환'을 따른다.
4. 3단계에서 사진을 고른다(선택). 없으면 3D 모델 없이 목소리로만 등록된다.
5. 4~7단계에서 채워진 설문을 확인하고 필요한 곳을 고친다.
6. 8단계에서 참조로 쓸 목소리를 **직접 들어본다**.
7. 9단계 **AI가 이렇게 알고 대화합니다**에서 문항 번호별 요약을 읽고, 고칠 곳은
   `고치기`로 해당 문항에 돌아가 고친다. 다 맞으면 아래 확인란을 누른다.
8. 10단계에서 `세션 시작`을 누른다. 세션 코드(UUID4)가 화면에 표시된다.
   가상 인물을 다른 인물로 바꾸거나 `설문 비우기`를 누르면 **이전에 고른 사진·음성 선택도
   함께 비워진다.** 이전 사람의 얼굴·목소리가 새 인물에 붙지 않게 하려는 것이며,
   2~3단계에서 파일을 다시 고르면 된다. 서버나 디스크의 파일을 지우지는 않는다.
9. Unity에서 `Tools > Dialogue > Open AI test scene`으로 AI 테스트 씬을 열고 Play 한다.
   Scene_2에서 체험할 때도 같은 등록 결과를 쓴다 — 등록한 인물이 **현재 체험 인물**로 선택되고,
   Scene_2의 체험 시작 흐름이 등록 API에서 그 인물과 GLB를 조회한다.
   Scene_2의 접속 설정은 AI 테스트 씬과 별개다. 각 씬의 설정을 서로 가져오지 않는다.
   Scene_2 쪽 순서와 문제 해결은 [Scene_2 웹설문 테스트](Scene_2_웹설문_테스트.md)를 본다.

설문을 고치면 9단계의 확인 내용과 확인란이 무효가 된다. 다시 읽고 다시 눌러야 등록할 수 있다.

## 2. 문항과 카드

10단계 구성은 그대로다. 각 입력 옆의 회색 번호가 `단계-문항` 번호이며 9단계 확인 화면과 같은 번호를 쓴다.

| 단계 | 내용 |
|---|---|
| 1 | 사별 기간(1-1), 동의 세 가지(1-2~4) |
| 2~3 | 음성(2-1), 사진(3-1) |
| 4 | 관계(4-1), 성별(4-2), 내가 부르던 말(4-3), 그분이 나를 부르던 말(4-4), 내 이름(4-5), 성격(4-6), 자주 하시던 말(4-7), 그분의 이름(4-8), 기억 속 시기(4-9), 지역·하던 일 카드(4-10), 떠나신 경위(4-11)·시점(4-12) |
| 5 | 추억(5-1), 취향·습관(5-2), 함께 아는 사람(5-3), 장소·활동(5-4), 그분이 알던 나(5-5) |
| 6 | 그리운 순간(6-1), 전하지 못한 말(6-2), 다시 듣고 싶은 말(6-3), 새 소식(6-4), 지켜줬으면 하는 점(6-5) |
| 7 | 대화 톤(7-1), 말투(7-2), 말투가 달라지는 상황·사투리(7-3), 실제로 하셨던 말(7-4) |
| 8~10 | 목소리 확인, 인물 확인, 등록 |

카드 항목(4-10, 5-1~5-5, 6-4)은 원하는 만큼만 추가한다.

- 항목마다 상태가 있다: **적겠습니다 / 잘 모르겠습니다 / 답하고 싶지 않습니다 / 실제로 없습니다**.
  앞의 셋은 서로 다른 상태로 저장되며 '없는 사실'로 바뀌지 않는다.
  '실제로 없습니다'만 사용자가 명시한 사실로 사전지식에 들어간다.
- 카드마다 **기억 정도**(정확히/대략/확실하지 않음)와 **언급 방식**(먼저 언급 가능 /
  내가 꺼낼 때만 / AI에 전달하지 않음)을 고른다.
- **누구 이야기인지(대상)는 문항이 정한다.** 5-2 취향·습관은 그분/나/함께 중에서,
  6-4 새 소식은 나/다른 사람 중에서 고른다. 나머지 문항은 대상이 하나로 정해져 있어
  화면이 그 대상을 알리기만 한다. 고른 대상은 사전지식 문장에 그대로 들어가며,
  5-3의 다른 사람이 인물 자신이나 나로 바뀌지 않는다.
- '내가 꺼낼 때만'은 대화 지침이다. 내용은 모델에 전달된다.
  '**AI에 전달하지 않음**'만 인물·사전지식·규칙·말투 예문·대기 리액션에서 완전히 빠진다.
  저장은 되므로 관리자 화면에서는 보인다.
- 입력칸의 흐린 글씨는 보기(placeholder)이며 저장되지 않는다. 빈 카드는 저장되지 않는다.
- **다시 듣고 싶은 말(6-3)은 사용자의 바람으로 전달한다.** 실제로 하셨던 말인지는
  확인되지 않은 것으로 두며, 하셨다고도 안 하셨다고도 말하지 않는다. 이 항목 하나로
  "그런 말을 한 적 없다"는 없던 사실을 만들지 않는다. 실제 기록이 있는 5-1의 인용과
  7-4의 대사는 그대로 실제 발언으로 남는다.

## 3. 이름과 말투

- **사용자 이름(4-5)과 그분의 이름(4-8)은 다른 칸**이다. 사용자 이름은 사전지식에
  "사용자의 이름"으로만 들어가고 캐릭터의 자기소개 예문에는 쓰지 않는다.
  v1은 되묻기 예문에 사용자 이름을 넣어 캐릭터가 자기를 사용자 이름으로 소개했다.
- 그분의 이름이 없으면 관계·호칭으로 부르고 이름을 새로 만들지 않는다. 확인 화면에서 알린다.
- **말투(7-2)는 관계와 독립된 선택**이다. 관계만으로 반말을 강제하지 않는다.
  존댓말을 쓰시던 어른도, 반말을 쓰시던 친구도 그대로 표현된다.
- `잘 모름`은 **부드러운 해요체**로 말한다고 확인 화면과 규칙에 명시한다.
  고르지 않은 상태를 실제 말투로 저장하지 않는다.
- 반말을 골랐을 때만 관계 갈래(어른·손위·손아래·또래)로 어미와 예문을 고른다.
- 말버릇(4-7)·실제 대사(7-4)가 고른 말투와 어긋나면 확인 화면에서 알린다.
  **원문은 그대로 둔다.** 사용자가 말투 선택이나 문장을 직접 고친다.

## 4. 저장 자료와 API

설문 원본(`answers`)과 등록 스냅샷(`compiled_snapshot`)을 같은 payload에 나눠 담는다.

```json
{"survey_schema_version": 2,
 "answers": {"consent": {...}, "bereavement_weeks": 52,
             "person": {"relation": "할머니", "person_name": "...", "user_name": "...", "traits": [], "quirks": []},
             "speech": {"form": "mixed", "samples": [], "tone_setting": "casual_recreation"},
             "sections": {"shared_memory": {"state": "answered", "cards": [{"id": "c1", "kind": "shared_memory",
                 "content": "...", "time": "...", "place": "...", "people": "...", "quote": "...",
                 "subject": "both", "certainty": "approximate", "mention_policy": "proactive"}]}},
             "heart": {...}, "care": {...}},
 "compiled_snapshot": {"compiler_version": "survey_v2_compile_3",
                       "survey_revision": "...", "preview_revision": "...",
                       "persona": "...", "knowledge": "...", "rules": "..."}}
```

- `survey_revision`은 설문 입력만의 해시다. 변환 결과를 포함하지 않는다.
- `preview_revision`은 변환기 버전과 최종 세 텍스트의 해시다. **인증 토큰이 아니다.**
- `/persona`는 `persona`, `knowledge`, `rules`, `review`, `issues`, 두 해시를 돌려준다.
- `/publish_direct`는 **설문 원문과 두 해시만** 받는다. 서버가 같은 설문에서 다시
  변환하고, 두 해시가 모두 일치할 때만 등록한다. 화면이 만든 인물 텍스트는 보내지 않는다.
  변환기를 새로 배포하면 오래 열어 둔 화면은 `preview_revision`이 달라져 다시 확인해야 한다.
- 등록은 기존 계약을 그대로 쓴다. 서버가 UUID4를 발급하고, 인물 조회는
  `schema_version=1`, `session`, `revision`, `persona`, `knowledge`, `rules`, `voice_sha256`이다.
- v1 화면의 신규 요청은 안내 문구와 함께 거부한다. **자동 이전은 없다.** 다시 작성해야 한다.
- 기존 v1 DB 행은 그대로 읽는다. 관리자 상세·JSON 내려받기·삭제가 v1/v2를 모두 처리한다.
  자료 폐기는 지금처럼 payload 전체를 비우므로 설문 원본과 등록 스냅샷이 함께 지워진다.
- 관리자·등록 화면은 참여자가 적은 글을 모두 이스케이프해서 표시한다.

## 5. 길이 상한

| 대상 | 상한 |
|---|---|
| 카드 개수(전체 합) | 20개 |
| 카드 본문·실제 대사 등 한 칸 | 200자 |
| **AI에 전달할 원문 합계** | **800자** |

합계에는 AI에 전달하는 사용자 자유 텍스트를 **모두** 넣는다 — 카드 내용과 부가 필드뿐 아니라
관계·그분 이름·내 이름·양쪽 호칭·기억 속 시기·성격·말버릇·실제 대사·말투 설명·사투리·
마음 문항·대화에서 지켜줬으면 하는 점까지다. `AI에 전달하지 않음`으로 고른 카드만 빠진다.

800자는 **실측으로 정한 값**이다. 기획 초안 2,000자와 그다음 1,200자는 실제 Gemma
`/tokenize`에서 추론 경로 예산 8,192를 각각 705토큰·69토큰 넘겼다(최대 기억 48건과 요약,
짧은 질문 기준). 줄마다 되풀이되던 사전지식 안내문도 같은 이유로 줄였다.
문자 수는 여전히 토큰 수를 보장하지 않으며, 상한을 바꾸면 실제 토크나이저로 다시 확인한다.
가상 예시 인물은 할머니 541자·친구 499자로 여유가 있다.

2026-09-17 `[재회]` 규칙이 더해지면서 **여유가 거의 사라졌다.** 같은 최악 조건의 추론 경로
여유가 269 → 14토큰이다(→ [8-1장](#8-1-고인-전제-변경의-검증-결과-2026-09-17)).
800자를 올리거나 공통 규칙을 더 늘리기 전에 반드시 실제 `/tokenize`로 다시 잰다.

넘으면 9단계에서 어떤 문항이 얼마나 넘었는지 알리고 등록만 막는다. **조용히 잘라내지 않는다.**
등록 경로에서도 같은 검사를 다시 하므로 화면을 우회해도 잘린 채 등록되지 않는다.
한 칸의 200자 제한은 보관하는 원문 자체의 상한이라 `AI에 전달하지 않음`으로 바꿔도 줄지 않는다.
그래서 그 경우에는 줄이거나 칸을 지우라고 안내한다.

설문 상한과 별개로, 아주 긴 사용자 발화처럼 대화 중 입력이 예산을 넘는 경우는
대화 서버의 기존 `ContextLimitError` 안전 차단에 맡긴다. 이 상한이 모든 길이·모든 입력에서
답변을 보장한다는 뜻이 아니다.

## 5-1. 고인이라는 전제와 떠나신 경위 (2026-09-17 추가)

**고인이라는 기본 사실과 개별 사망 원인·시점은 분리한다.**

- **기본 사실은 설문 항목이 아니다.** 이 체험 자체가 이미 세상을 떠난 분을 사용자의 기억으로
  다시 만나는 자리이므로, 대화 서버가 등록 체험에 `[재회]` 규칙을 항상 넣는다
  (`Server/persona_context.MEMORIAL_RULES`). 인물은 1인칭·관계·말투를 유지하고,
  "안 죽었다"·"살아 있다"고 하지 않으며, **일상 대화에서 먼저 죽음을 꺼내지도 않는다.**
  부활·사후 세계·지켜봐 왔다는 사실·떠난 뒤의 근황은 지어내지 않는다.
  층과 적용 범위는 [서버 음성 대화 구조](서버_음성대화_구조.md)의 '시스템 프롬프트의 층'에 있다.
  **이미 등록된 인물도 재접속만으로 적용된다.** 인물 파일과 DB는 고치지 않는다.
- **개별 경위는 4-11·4-12의 선택 입력**이다. 비워 두는 것이 기본이고, 적지 않으면
  AI가 원인을 지어내지도 유족에게 여쭤보지도 않는다.
- 상태는 **적겠습니다 / 잘 모르겠습니다 / 답하고 싶지 않습니다** 셋뿐이다.
  **'실제로 없습니다'는 두지 않는다** — 이 체험의 전제가 고인이라 '사망 사실이 없다'가 되는
  선택지를 만들 수 없다. 상태를 되돌리면 적어 둔 내용도 함께 비운다.
- 언급 방식은 **내가 꺼낼 때만 / AI에 전달하지 않음** 둘이다.
  **'먼저 언급 가능'을 두지 않는다** — 일상 대화에서 먼저 꺼내지 않는 것이 기본이기 때문이다.
  'AI에 전달하지 않음'은 인물·사전지식·규칙·말투 예문·대기 리액션에서 완전히 빠지고,
  9단계의 'AI에 전달하지 않는 내용'과 관리자 화면에만 남는다.
- 적은 경위는 `[사전지식]`에 두 줄로 들어간다 — "세상을 떠난 경위는 사용자가 알려준 대로
  이렇다: …", "세상을 떠난 시점은 …이다." `[인물별 추가 규칙]`에는 먼저 꺼내지 않는다는 한 줄이 붙는다.
- **`bereavement_weeks`(1-1)는 지금도 모델에 넣지 않는다.** 사별 경과 주에서 정확한 사망일을
  역산하지 않기 위해서다. 시점을 알리려면 사용자가 직접 적는 4-12를 쓴다.
  2026-08-28에 '사별 시점을 넣으면 판정기가 모른다 쪽으로 기울었다'는 기록이 있으나
  **현재 모델에서 다시 확인한 적은 없으므로 제외 근거로 쓰지 않는다.**
- 4-11의 원문은 다른 칸과 같은 200자 상한을 받고, 전달되는 경우에만 800자 합계에 들어간다.
- **설문에 적은 경위가 대화 중의 정정보다 우선하지 않는다.** `[재회]` 규칙이 "[사전지식]과
  사용자가 이 대화에서 알려주거나 고쳐 준 것"을 근거로 삼는다. 사용자가 대화에서 고치면
  고친 내용을 따른다. 대화에서 알려준 내용은 그 연결 안에서만 유지되고 설문 DB를 고치지 않는다.
- **'일상' 대화 예시에서 인물의 지금 생활을 묻는 짝을 뺐다.** 예전 예문
  ("뭐 하고 있었어?" → "그냥 앉아서 텔레비전 보고 있었지.")을 모델이 그대로 베껴,
  세상을 떠난 인물의 근황 질문 답변이 두 차례 실행 각각 9/9(2026-09-17 실측 3인물 × 3회)로
  떠난 뒤의 생활을 말했고, 그중 이 예문과 거의 같은 문장이 실행마다 2건씩 있었다.
  인물이 사실대로 답할 수 없는 질문은 본보기로 주지 않는다. 7-1 `평소 대화 재현형`의 설명도
  '생전에 하던 그대로' → '생전에 쓰던 말투 그대로'로 고쳐 지금 생활이 이어지는 것으로 읽히지
  않게 했다. **이미 등록된 인물의 구형 예문**은 대화 서버가 따로 처리한다
  → [서버 음성 대화 구조](서버_음성대화_구조.md)의 '구형 말투 예시 처리'.
- `compiler_version` 을 `survey_v2_compile_3` 로 올렸다. 오래 열어 둔 화면은
  `preview_revision` 이 달라져 인물 확인을 다시 해야 한다. `passing` 을 보내지 않는 요청은
  거부하지 않고 '모름'으로 정규화하며, 그 결과 `survey_revision` 도 달라진다.
  **이미 저장된 DB 행은 그대로 읽는다** — 관리자 상세는 `passing` 이 없으면 그 줄을 그리지 않는다.

## 6. 대화 쪽 변경

대기 리액션 준비 입력에서 `knowledge`와 `rules`를 뺐다. 리액션은 인물의 성격·말투만 쓴다.
새 근황·언급 조건·피할 주제가 v2의 `rules`에 들어가므로, 그대로 두면 리액션 생성 입력으로 샜다.

응답 ID·턴·재생 확인·취소·기억 추출 계약은 바꾸지 않았다.

2026-09-17 등록 경로에만 `[재회]` 층이 하나 더 붙었다(→ [5-1장](#5-1-고인이라는-전제와-떠나신-경위-2026-09-17)).

`test_mode`의 테스트 인물에도 붙지 않는다.

## 7. 한계

- **사진이 없으면 3D 모델이 없다.** 목소리와 대화는 그대로 된다.
- **대화 기억은 연결 단위다.** 대화에서 사용자가 알려주거나 정정한 내용은 그 연결 안에서만
  유지되고 설문 DB를 고치지 않는다. 다시 접속하면 설문에 적힌 것부터 다시 시작한다.
- 등록 후 같은 인물을 편집·재게시하는 기능과 서버 임시 저장은 아직 없다. 수정은 등록 전에 한다.
- 브라우저를 새로 고치면 입력이 사라진다. 복원은 제공하지 않는다.
- 문자 수 상한은 토큰 예산을 보장하지 않는다. 800자는 최대 기억·짧은 질문 조건의 실측값이며,
  더 긴 발화나 다른 기억 상태까지 보장하지 않는다. 그 경우는 대화 서버가 안전하게 거부한다.
- 화자 분리와 여러 사람 자동 판별은 제공하지 않는다. 여러 사람이 섞인 녹음은
  한 사람만 나오는 구간을 사람이 잘라서 올린다.
- M4A/AAC·영상 변환은 ffmpeg가 있어야 한다. 없으면 그 형식만 503으로 거절하며, WAV 경로는
  영향을 받지 않는다. 실제 서버에서의 변환·등록 확인은 메인이 따로 수행한다.
